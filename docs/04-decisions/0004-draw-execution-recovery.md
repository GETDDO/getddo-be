# ADR-0004: 기존 실행 행을 이용한 추첨 실패·예약·중단 복구

## 배경

GD-87은 프로세스 재시작 후에도 자동 재시도 횟수·예약과 운영자 대기를 보존해야 한다. 기존 draw_failures는 발생한 실패 이력이며 예약·진행 중 시도 소유권을 표현하지 않는다. GD-86 자동 시작과 GD-138 재추첨 시작·재개가 같은 실행을 사용할 때 중복 확정과 운영자 대기 우회를 막아야 한다. 사용자는 기존 구조를 최대한 재사용하도록 요청했다.

## 결정과 이유

별도 실행 제어 테이블 대신 기존 draw_runs에 attempt_id, lease_until, retry_at, retry_cycle_started_at을 추가하는 구현안을 작성했다. 상태 enum과 실패 이력 구조는 유지하고 횟수·최근 실패는 이력에서 조회한다. FAILED에 예약이 없으면 운영자 대기다. 시도 소유권 토큰은 동일 실패 기록의 ID로 재사용한다.

이벤트 → 실행 잠금 아래 소유권을 별도 커밋하고 입력 고정·선정·실패 저장을 별도 서비스 트랜잭션으로 수행한다. 선정 실패에도 저장 입력을 보존한다. 만료 복구는 실제 처리 트랜잭션의 이벤트 잠금 해제를 기다린 뒤 상태·토큰을 다시 확인한다. 등록 커밋 후 시작 전에 중단된 실행도 같은 ID로 회수한다.

기존 이벤트 선잠금·유일 제약·JPA 실행 엔티티·공용 감사 서비스를 재사용한다. 잠금 순서와 Controller/Repository의 업무 트랜잭션 부재를 유지한다. 기술 구현 세부 계약은 [저장 설계](../03-database/drawing-selection-storage.md#gd-87-공통-실행실패재개--구현과-검증)를 따른다. 이 ADR은 담당자 확인 없이 채택으로 표시하지 않는다.

## 검토한 대안

- 별도 draw_execution_controls 테이블: 원래 제안했으나 사용자에게 필요성·다른 작업 영향을 설명한 뒤 최소 변경 요청에 따라 철회했다. 실행과 제어 상태가 1:1이므로 기존 행에 보관하는 안으로 좁혔다.
- 기존 상태와 실패 이력만 사용: 미래 예약·실제 처리 중인 시도와 중단된 시도를 충분히 구분할 수 없어 제어 정보를 추가했다.
- 프로세스 메모리만 사용: 재시작 보존 요구를 충족하지 못한다.

## 영향과 재검토 조건

GD-86·GD-138은 공통 실행 서비스로 연결하고 GD-137은 이력·상태 조회 계약을 연결해야 한다. 최초 후보·결과 이력과 다른 담당자의 원본 모델은 변경하지 않는다. V019는 임시 MySQL 통합 테스트에 적용했다. 운영 적용은 미수행이며 번호·순서는 동시 작업과 확인해야 한다.

5분 임대와 10/30/60초 예약 간격은 현재 구현 수치다. 긴 실행·큰 후보 명단·시계 차이·다중 인스턴스·실패 저장 DB 장애의 실제 검증은 남아 있다. 이후 사용자 승인으로 관련 단위·HTTP·MySQL 통합 테스트를 실행해 통과했다. 전체 test/build 결과는 작업 기록에 별도로 기록한다. 실행 성능이나 운영 안정성을 검증 완료로 표현하지 않는다.
