# ADR-0007: 추첨 후속 작업의 단계별 구현

- 상태: 제안
- 작성자 / 날짜: Codex / 2026-10-14
- 검토자: 사용자 구현 방향 선택 — 문서 담당자 확인 전
- 관련 작업 기록 / PR: [공용 작업 기록 PR #86](https://github.com/Uplus-GETDDO/getddo-be/pull/86), GD-86·GD-131·GD-140·GD-199 / PR 없음
- 대체한 ADR / 대체된 ADR: 해당 없음

## 배경

자동 추첨, 실제 응모 연동 검증, 사용자 결과 조회를 병렬로 진행하되 초기 구현은 V1 기능·복구에 집중하고 조회 인덱스 개선은 V2 후속으로 두기로 했다. 공용 정책과 사용자 API 계약은 [getddo-spec](https://github.com/Uplus-GETDDO/getddo-spec)의 요구사항·추첨 규칙·API를 원본으로 사용한다.

## 결정과 이유

### GD-86: V1은 가벼운 스케줄러

- 확인 주기는 10초로 시작하고 설정값으로 조절할 수 있게 한다. 대상 이벤트 ID를 제한된 건수로 조회하고 이벤트별로 순차 처리한다. 정확한 조회 건수는 기존 코드와 데이터 범위에 맞춰 구현 시 정한다.
- 스케줄러는 기존 실행 등록·추첨 서비스를 호출하며 공개 서비스를 자동 호출하지 않는다. 추첨 로직을 스케줄러 안에 다시 만들지 않는다.
- 최초 공개는 GD-199의 명시적 관리자 요청에서 처리한다. V1 스케줄러의 공개 재호출은 제외한다. 이미 확정된 추첨 결과를 다시 선정하거나 새 실행을 만들지 않는다.
- 기존 추첨 실패의 재시도 소진·운영자 대기를 스케줄러가 강제로 해제하지 않는다. 확정 결과를 공개로 간주하지 않는다. 이 제한은 추첨 실패 복구에 대한 것이며 스케줄러의 공개 재시도 기능은 제공하지 않는다.
- 중복 실행 방지, 이벤트별 오류 격리, 서버 재시작 후 놓친 대상 탐색은 V1에도 포함한다. 순차 처리와 10초 주기만으로 누락·중복 방지가 보장된다고 가정하지 않는다.
- 10초는 확인 주기이며 추첨의 정확한 시작 시각이나 최대 지연을 보장하는 값은 아니다. 처리 시간과 앞선 이벤트 대기를 함께 고려한다.

### V2 조회 성능 개선은 후속 작업

| 단계 | 범위 | 확인할 조건 |
| --- | --- | --- |
| V2 | 대상 조회 쿼리·실행 계획을 확인하고 필요한 인덱스 추가 | 실제 조회가 느리면 V1 완료를 기다리지 않고 앞당긴다. 새 Flyway로 추가하며 기존 파일은 수정하지 않는다. |

V2는 GD-86 V1의 필수 완료 범위가 아니다. 실제 쿼리·운영 데이터를 확인해 필요한 인덱스 개선을 별도 티켓으로 이관한다. 티켓 번호는 아직 정하지 않았다.

### GD-131: 기존 응모 계약 대조와 실제 서비스 검증

- 새로운 응모·마감 정책을 정하지 않는다. 최신 spec의 접수 완료 기준이 실제 EntryService의 시각 판정·트랜잭션·잠금과 어떻게 대응하는지 먼저 확인한다.
- 정상 응모의 후보 수량·등급별 가중치·차감 근거, 마감 경계와 동시 요청, 접수·차감·원장의 함께 롤백, 확정 스냅샷 재사용을 실제 서비스로 검증한다.
- GD-145 PR #83 반영 후에는 ACCEPTED만 후보·차감 집계에 포함되는지 확인한다. 업무 거절 뒤 별도 트랜잭션으로 남는 REJECTED 이력은 부분 접수·차감 잔존과 구분한다. 거절 이력에 응모자·차감 연결이 없는지 검증한다. PR은 아직 열려 있으므로 병합·적용 상태를 다시 확인한다.
- 스냅샷 준비를 1분 늦추는 방식으로 동시성 검증을 대신하지 않는다. 필요한 이벤트 상태는 검증 데이터에서 준비하되 실제 이벤트 생명주기 연결 완료와 구분한다.
- 추첨 측 결함과 응모 담당 측 결함을 구분한다. 다른 담당의 계약·잠금·처리 흐름 변경은 확인 후 진행한다.

### GD-140과 이벤트 상태 연결

- 사용자 조회의 E08·E09 계약, 개인정보 표시와 이번 제외 범위는 [공용 추첨 API](https://github.com/Uplus-GETDDO/getddo-spec/blob/main/05-api/drawing.md)를 따른다. 백엔드 문서에서 별도 정책을 확정하지 않는다.
- 이벤트 담당자가 제공할 상태 변경 서비스를 기다리는 동안 86·131·140의 독립 부분은 진행할 수 있다. 서비스 제공 후 실제 메서드·예외·잠금·트랜잭션 계약을 대조해 연결한다.
- 상태 변경 서비스는 추첨 저장과 같은 트랜잭션에 참여하도록 요청했다. 새 PUT·PATCH API는 요구하지 않는다. 기존 GD-169에서 미연결로 남긴 내용을 자동으로 완료 처리하지 않는다.
- 기존 재추첨 시작 상태 갱신과 새 서비스 호출이 중복되지 않도록 확인하고, 최종 합동 검증에서 확정·공개·상태·알림·사용자 조회를 함께 확인한다.

## 검토한 대안

- 5분 주기 조회는 마감 후 실행 가능한 대상의 발견이 늦어질 수 있어, 초기 설정으로 10초 확인을 선택했다.
- 이벤트별 예약은 서버 재시작·일정 변경 때 예약 복구·갱신이 필요하다. 초기에는 DB 기준 대상 탐색으로 구현한다.

## 영향과 재검토 조건

- 10초 조회의 운영 성능은 측정하지 않았다. 현재 확인한 이벤트 마이그레이션에서는 종료 시각 탐색용 인덱스를 확인하지 못했다. 실제 쿼리·데이터량·서버 수에 따라 V2를 앞당긴다.
- 전체 조회·대량 후보 적재·긴 잠금을 폴링마다 반복하지 않도록 구현 시 확인한다. 여러 서버의 중복 요청은 기존 DB 제약과 실행 소유권 계약으로 처리한다.
- V1은 기능·복구를 확인하고 V2는 별도 개선으로 기록한다. 이 문서는 구현·배포·검증 완료를 의미하지 않는다.
- 사용자의 테스트 중단 요청을 유지한다. 이번 문서 작업에서 테스트·빌드·Docker는 실행하지 않는다. 이후 요청 시 공통 Docker 잠금과 자원 제한으로 검증한다.
- `@Transactional`은 서비스 계층에 선언하고 `var`는 사용하지 않는다. 워크로그는 날짜 공용 브랜치로 공유하며 기능 커밋에서 제외한다.

## 2026-10-14 수동 공개로 범위 변경

이 문서의 초기 공개 재호출 안은 사용자 결정으로 폐기했다. GD-86은 자동 추첨 V1, GD-199는 정상 최초 결과 확인·수동 공개 및 확인 시 자동 반영 연결 제거를 맡는다. GD-140은 실제 공개 기준 조회이며 GD-131의 응모 연동 검증은 유지한다. V2는 자동 추첨 대상 조회의 성능 개선 후속으로 유지한다. 공용 정책은 spec ADR-022와 drawing 문서를 따른다.
