# ADR-0003: 추첨 후보 재사용과 실행·결과·공개 이력 분리

## 배경

추첨 ERD 검토에서 최초 후보의 가중치·응모 근거를 유지하면서 재추첨 실행마다 실제 사용한 명단을 보존해야 한다는 점을 확인했다. 이전 초안은 재추첨마다 후보 상세 정보와 두 JSON 스냅샷을 반복 저장했다. 응모자 10,000명 중 5명이 당첨되고 추가 제외자가 없다면 재추첨 후보는 9,995명이며, 재추첨마다 상세 정보가 반복될 수 있다. 수만 행 자체를 문제로 판단한 것이 아니라 원본 정보와 실행별 소속의 중복을 줄이는 것이 이번 변경의 목적이다. 저장 용량·성능은 실제 측정하지 않았다.

선정 결과와 공개 명단도 구분해야 한다. 내부에서 새 당첨자를 확정했더라도 관리자 확인 전에는 사용자 조회에 반영할 수 없다. 공용 정책과 API 초안은 [SPEC 추첨 규칙](https://github.com/GETDDO/getddo-spec/blob/main/02-domain/drawing.md)과 [SPEC 추첨 API](https://github.com/GETDDO/getddo-spec/blob/main/05-api/drawing.md)를 원본으로 사용한다. 이 ADR은 백엔드 저장·조회 제안을 기록하며 운영 코드나 Flyway 적용 완료를 뜻하지 않는다.

## 결정과 이유

### 최초 후보 정보와 실행별 명단

- `draw_candidates`는 최초 실행의 후보 상세 정보·원래 가중치·응모 및 자격 스냅샷을 보존한다. 재추첨마다 상세 정보를 복제하지 않는다.
- `draw_run_candidates`는 `(draw_run_id, candidate_id)` 복합 PK로 실제 실행에 사용한 최초 후보를 연결한다. PK는 실행 안의 후보 중복을 방지한다. 조회 때마다 명단을 다시 계산하지 않고 실행별 연결을 보존한다.
- `draw_results`의 `(draw_run_id, candidate_id)` 복합 FK는 이 연결 테이블을 참조한다. 재추첨 실행 ID와 최초 후보 생성 실행 ID가 다르므로 기존 후보 테이블을 직접 참조하는 복합 FK를 교체한다. 미충원 결과의 `candidate_id`는 NULL을 허용한다.
- FK만으로 같은 이벤트·원본 실행 종류·명단 불변을 보장하지 못한다. 서비스는 같은 이벤트의 INITIAL 후보인지 검증하고, 확정한 연결·가중치·조건을 변경하지 않으며 동일 실행 재시도에 재사용해야 한다. 동일 이벤트의 실행 직렬화·잠금은 관련 담당과 구현 전에 확인한다.

### 취소와 실행의 근거

`draw_results`는 경품 자리별 선정 또는 미충원 결과이며 확정 후 불변으로 보존한다. `award_cancellations`는 선정 결과 하나의 취소 사실·처리자·사유·시각과 보충 실행 연결을 보존한다. 취소됐다고 원래 결과를 삭제하거나 수정하지 않는다.

취소 테이블의 실행 FK로 하나의 재추첨에 연결된 취소를 목록으로 조회한다. 최초 실행은 빈 목록, 재추첨은 한 건 이상이며 이 관계가 일괄 취소 API나 취소를 모아 기다리는 정책을 의미하지 않는다. 원래 실행은 취소 → 원래 결과 → 해당 실행으로 추적한다. 취소 처리자·사유를 실행자 한 명·사유 하나로 치환하지 않는다. 다른 관리자의 시작·재개 행위는 별도 감사 연계가 필요하다.

정상 취소 API의 취소 저장·재추첨 실행 등록·FK 연결은 같은 트랜잭션에서 커밋하고 등록 실패 시 취소도 롤백하는 방식으로 제안한다. nullable FK는 트랜잭션 내부 INSERT 순서를 허용한다. 성공한 취소만 실행 미연결 상태로 커밋하는 용도로 사용하지 않는다. 커밋 후 서버가 실행을 즉시 시작하며 선정 실패는 기존 실행에 기록하고 같은 실행을 재개한다. 재요청은 기존 취소·실행을 반환한다.

### 실패·검증 이력

`draw_failures`는 동일 실행의 실패 한 번을 한 행으로 보존한다. 실패 횟수와 최근 실패는 이력에서 조회하며 실행 행에 집계 값을 중복 저장하지 않는다. 관리자 문구는 실패 코드를 변환해 제공하므로 원문 사유 컬럼을 추가하지 않는다. 진단 로그는 추적 ID로 연계하며 원문 예외·스택 트레이스를 저장하거나 응답하지 않는다.

`draw_checks`는 후보·조건·결과 정합성 검증과 처리자·시각·검증 항목을 보존한다. 난수를 다시 실행해 같은 당첨자를 재현하는 기능으로 해석하지 않는다.

### 선정과 공개의 분리

`draw_publications`는 실제 공개 버전·반영 실행·확인 근거를 보존한다. 현재 제안의 조회는 해당 공개 버전까지 반영된 실행의 결과에서 경품·자리별 최신 결과를 구성한다. 전체 실행의 최신 결과를 곧바로 노출하면 미확인 당첨자가 공개되므로 공개된 범위만 조회해야 한다. 이전 공개 버전과 비교해 변경 전후를 조회한다.

관리자 결과 조회의 공개 이력 여부와 취소 여부는 별도로 구성한다. 공개 후 취소된 결과는 둘 다 참일 수 있다. 공개 이력 여부는 해당 결과가 실제 공개 명단에 포함됐는지 판단해야 하며, 실행 전체의 공개 여부만으로 최초 공개 전 취소된 결과까지 공개된 것으로 처리하지 않는다. 이를 위한 새 상태 컬럼은 이번에 추가하지 않는다.

## 검토한 대안

- 실행마다 후보 상세 정보 복사: 실행별 보존은 가능하지만 변하지 않는 가중치·두 스냅샷을 중복 저장한다. 최초 상세 정보와 실행별 연결을 분리하기로 했다.
- 전체 후보를 한 JSON으로 저장: 후보 개별 참조·중복 방지·결과 FK를 처리하기 어려워 후보별 행을 유지한다.
- 재추첨 때마다 후보를 조회만 하기: 이후 당첨·제외 기록에 따라 같은 실행의 명단이 바뀔 수 있어 실제 사용 명단을 연결 행으로 고정한다.
- 결과와 공개 테이블 통합: 선정 직후의 내부 결과와 관리자 확인 후 공개 사실의 차이를 별도로 표현해야 하므로 분리를 유지하는 제안이다. 테이블 수를 줄이는 것만을 선택 기준으로 삼지 않았다.

## 영향과 재검토 조건

- [ERDCloud용 SQL](../03-database/drawing-erd-reviewed-erdcloud.sql)은 설계 초안이다. 운영 스키마·통합 DBML·Flyway·서비스는 이번 문서 갱신에서 변경하지 않았다. 실제 반영은 새 마이그레이션과 동시성·재시도 검증이 필요하다.
- **최초 공개 전 재추첨의 공개 저장은 보완이 필요하다.** SPEC에서는 유지 결과와 확인된 대체 결과를 합쳐 첫 명단을 공개하고 준비·확인이 늦으면 발표를 지연하기로 했다. 현재 SQL은 공개 버전당 `source_draw_id` 하나와 INITIAL 확인자·시각 NULL을 전제로 하므로, 여러 실행의 결과 포함과 사전 관리자 확인 이력을 충분히 보존하지 못한다. 아래 공개 조회 예시만으로 이 요구를 충족한다고 판단하지 않는다. 후속 ERD 검토에서 포함 결과·실행 및 확인 기록을 설계해야 한다.
- 최초 공개 전 확인 API, 발표 지연 안내, 발표 후 취소자의 중간 화면 표시와 어뷰징 검토 근거 연결은 SPEC의 후속 사항을 따른다. 이 ADR에서 계약을 임의로 확정하지 않는다.
- 실제 시작·재개 행위의 감사 연계는 A/C, 이벤트·경품·응모 및 잠금 경계는 관련 담당 확인이 필요하다. 해당 구현은 변경하지 않았다.
- 원본 후보 재사용을 변경하거나 후보 가중치 재산정이 필요해지면 이 제안을 재검토한다. 저장·조회 성능, 다중 서버·강제 종료 및 재시도는 미검증이다.
