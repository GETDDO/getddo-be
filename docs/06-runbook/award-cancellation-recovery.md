# 개별 당첨 취소·재추첨 확인과 복구

- 구현: [GD-138 저장 설계](../03-database/award-cancellation-storage.md)
- 공통 실패·예약·중단 복구: [GD-87 실행 복구](draw-execution-recovery.md)

## 요청 결과 확인

AD05는 활성 관리자의 UUID Idempotency-Key와 사유를 받아 취소·REPLACEMENT 등록을 함께 커밋한 뒤 서버에서 실행한다. 성공 응답의 cancellationId와 replacementDrawRunId를 보존한다. 202는 미확정 상태이며 실행 성공을 뜻하지 않는다.

응답을 받지 못했으면 같은 관리자·winId·키·사유로 AD05를 재요청한다. 같은 처리는 기존 취소·실행을 사용하며 키나 사유를 바꿔 새로운 취소를 만들지 않는다. 등록 자체가 실패하면 취소도 남지 않는다. 등록 뒤 실제 실행이 실패하면 취소와 실행은 보존되며 같은 실행에서 복구한다.

## 같은 실행 시작·재개

`POST /api/v1/admin/cancellations/{cancellationId}/redraws`를 활성 관리자 문맥으로 호출한다. 본문과 새 멱등 키는 필요하지 않다. AD09는 이미 연결된 실행만 시작·재개한다.

- PREPARING/READY: 기존 등록 실행을 시작한다.
- 진행 중: 기존 진행 상태를 반환한다.
- FAILED: GD-87의 운영자 재개를 호출한다. 실제 재개 관리자는 취소 관리자와 별도로 감사에 남는다.
- CONFIRMED: 같은 저장 결과를 200으로 반환하며 다시 선정하지 않는다.

실행 불가 이벤트·상태는 409다. 만료된 시도를 복구한 요청이 즉시 새 선정까지 수행한다고 가정하지 않는다. 실패 원인·예약·운영자 대기와 복구 조건은 GD-87 기록을 확인한다. 실행 ID·취소·고정 입력·실패 이력을 수동으로 복제하거나 수정해 복구하지 않는다.

같은 이벤트에 미확정 재추첨이 있는 동안 다른 당첨의 새 취소는 409다. 기존 실행을 먼저 확인·복구한다. 취소·선정이 확정돼도 새 공개 명단이 자동 반영되는 것은 아니다. 공개 확인·반영은 GD-139 기능에서 처리한다.

## DB 확인 범위

award_cancellations의 draw_result_id·draw_run_id·request_key와 관리자·사유·시각을 확인한다. draw_runs의 실행 종류·차수·고정 입력·현재 상태는 공통 저장 설계를 따른다. 기존 실행 연결이 NULL인 과거 행은 상태 충돌이며 자동으로 새 실행을 만들지 않는다.

V020은 V019 뒤에 적용하는 새 멱등 키 마이그레이션이다. 테스트는 임시 MySQL에 적용하며 운영 DB 적용 완료로 보고하지 않는다. 운영 적용 전 통합 브랜치에서 마이그레이션 번호 중복과 Flyway 상태를 확인한다.
