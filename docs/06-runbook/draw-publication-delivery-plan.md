# 추첨 공개 알림 연결·장애 확인

- 상태: 검토 대기
- 담당: 석종수(추첨 호출 연결), 전민규(기존 알림 처리) / 2026-10-13
- 작성 도구: Codex / 담당자 검토 전
- 관련 작업: [GD-169](https://ureca4.atlassian.net/browse/GD-169)

## 처리와 책임

공개 서비스는 새 공개 버전과 실제 명단·실행별 확인 근거를 저장하고 같은 트랜잭션에서 기존 알림 작업을 등록한다. 최초 공개에는 RESULT_PUBLISHED, 명단 갱신에는 RESULT_CHANGED를 사용한다. 발생 키는 `draw-publication:<publicationId>`이며 payload에 실제 공개 ID와 고정 수신 목록·문구·결과 확인 링크를 보존한다. 재요청은 기존 버전을 반환하고 새 작업을 만들지 않는다.

작업 등록 실패는 아직 커밋되지 않은 공개와 새 확인까지 롤백한다. 커밋 이후 기존 NotificationJobService 및 작업 처리기가 생성·모의 발송을 수행하며, 해당 실패는 공개를 되돌리거나 당첨자를 다시 선정하지 않는다. 운영 DB 적용·스케줄러 연결은 이 문서 검증 범위가 아니다.

## 장애 확인 순서

1. `draw_publications`에서 event_id·revision·id·published_at을 확인한다. 실행 CONFIRMED만으로 공개 완료를 판단하지 않는다.
2. `notification_jobs.occurrence_key`가 `draw-publication:<공개 UUID>`인 행을 조회한다. payload.publicationId와 고정 입력·예약 시각을 대조한다. 원자적으로 등록되는 새 공개에 작업 행이 없으면 구버전 공개 여부와 코드 적용 범위를 확인한다.
3. 작업 status·attempt_count·next_attempt_at·lease_until·last_error를 확인한다. `notifications.job_id`로 사용자별 생성·발송 상태를 확인한다. 새 공개를 만들거나 이력을 삭제하여 재전달하지 않는다.
4. 생성·발송 재시도와 관리자 재개는 [기존 알림 복구 절차](notification-worker.md)를 따른다. payload를 임의 변경하거나 새로운 수신 목록으로 같은 키를 재등록하지 않는다.
5. 관리자 추첨 상세의 최근 실패·예약·운영자 대기와 실패/실행 감사 페이지를 대조한다. 추첨 실패 재개와 알림 작업 재개는 별개다.

## 검증 범위

공개 등록 실패 롤백, 중복 확인·공개 재요청, 다중 미충원 실행의 확인 근거, 생성·모의 발송 및 발송 실패 후 재시도는 실제 MySQL 연결 테스트로 검증한다. 운영 DB 적용·실제 외부 발송은 검증 범위에 포함하지 않는다. 전체 검증 실행 방법은 [테스트 실행 자원 제한](../01-conventions/test-execution.md)을 참고한다.

수신 목록은 기존 알림 작업 payload의 JSON에 고정 저장한다. 현재 코드에는 수신자 수에 대한 별도 상한이 없으며, 응모자 수가 늘면 조회 메모리와 payload 크기도 함께 증가한다. 대규모 운영을 적용할 때는 알림 담당과 분할 전달 계약을 별도로 검토한다. 이 문서에서 새 수치 한도나 대상 제외 정책을 정하지 않는다.

## 이벤트 상태 경계

기존 취소 등록의 REDRAWING 갱신을 재사용한다. 최초 확정·공개 시 상태 변경은 재사용 가능한 기존 함수가 없어 미연결이다. 사용자 결정에 따라 신규 이벤트 상태 변경 코드를 만들지 않았다. 공개 여부는 실제 공개 버전으로 판단하고 이벤트 담당과 후속 연결을 확인한다.

## 2026-10-14 수동 최초 공개 정책 후속


GD-199에서 관리자 확인과 실제 공개를 분리한다. 스케줄러는 공개를 호출하지 않는다. 실제 공개 기록이 저장된 이후의 기존 알림 전달·발송 재시도는 유지하며, 알림 실패 때문에 공개를 새로 생성하거나 추첨하지 않는다. 이벤트 담당의 상태 서비스 계약이 제공되면 같은 트랜잭션의 확정/공개 연결을 대조한다. 이 추가 기록은 새 흐름의 구현·운영 적용 완료가 아니다.

# GD-169 공개 알림 연결·복구 계획

- 상태: 구현 전 계획 / 검토 대기

## 확인한 기반

origin/dev 1417664에는 공개 Service·실행 Service·기존 NotificationJobService가 있다. register는 원본 업무 트랜잭션에 참여하고 저장 작업의 생성/발송 처리는 분리돼 있다. NotificationJobRequest에는 occurrenceKey·type·eventId·publicationId·제목/본문/링크·scheduledAt·recipientIds가 있다. 이 파일은 실제 추첨 생산자 연결 완료나 운영 복구 절차의 검증 완료를 뜻하지 않는다.

## 구현할 연결

1. 실제 공개 버전이 새로 저장될 때 같은 트랜잭션에 전달 근거를 보존한다. 기존 알림 작업 등록 기반을 우선 재사용하고 수신 대상·payload·발생 키를 해당 담당 계약에 맞춘다.
2. 커밋 이후 기존 작업 처리 기능이 생성·발송하도록 연결한다. 최초 공개·명단 갱신을 구분하고 공개되지 않은 결과로 알림을 만들지 않는다.
3. 같은 공개의 재요청·전달 재시도는 고정 발생 키·동일 payload를 재사용한다. 다른 업무와 키가 충돌하지 않도록 기존 규칙을 확인한다.
4. 전달·발송 실패는 기존 알림 재시도·관리자 복구 계약을 따른다. 알림 실패로 공개 결과를 롤백하거나 당첨자를 다시 선정하지 않는다. 기존 알림 저장/생성/발송 코드는 담당 영역에 유지한다.

## 복구 시 확인할 근거

공개 ID·revision·실제 공개 시각, 같은 공개의 작업 등록 유무, 발생 키·고정 입력, 작업 처리/발송 상태를 대조한다. 새 공개를 만들거나 공개 이력을 삭제해 재전달하지 않는다. 처리 상태 조회·재개 API는 기존 알림 담당 기능을 확인하고 재사용한다. 실제 명령·설정·조회 경로는 구현 및 검증 후 기록한다.

## 검증 계획

공개 롤백 시 전달 기록 없음, 커밋 직후 중단에도 기록 보존, 재시작 후 처리, 반복 공개/중복 전달, 실패 재전달, 미확인 결과 비노출을 실제 MySQL로 검증한다. Docker 테스트는 공통 잠금 아래 직렬 실행한다. 이 문서 작업에서는 테스트·빌드·Docker·운영 DB 적용을 실행하지 않았다.

## 이벤트 상태 경계

상태 변경은 기존 담당 코드가 있을 때만 연결한다. 없으면 미연결 목록에 기록하고 신규 Service·API·DB 상태 변경 기능을 만들지 않는다.
