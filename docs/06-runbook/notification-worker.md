# 알림 작업 처리·장애 확인

GD-68의 내부 실행 방식과 확인 절차다. 공용 정책의 원본은 [알림 도메인 규칙](https://github.com/GETDDO/getddo-spec/blob/main/02-domain/notification.md)이다.

## 등록과 실행

- 호출 담당자는 실제로 확정할 발생 사실의 식별키·수신자 UUID 목록·문구를 `NotificationJobRequest`로 전달한다. 수신 자격과 실제 발생 여부는 호출 담당자가 판정하며, 작업 등록은 `NotificationJobService.register()`로 한다.
- 등록은 호출자의 트랜잭션에 참여한다. 업무 변경과 작업 등록을 함께 처리하려면 호출자의 Service도 트랜잭션을 열어야 한다. 원본 업무를 롤백하면 알림 작업도 롤백된다.
- 식별키는 전역에서 발생 건을 구분한다. 같은 키·같은 입력은 기존 ID를 반환하며 다른 입력은 `NOTIFICATION-004`로 거절한다. 수신자 순서·중복과 시각의 마이크로초 정밀도는 정규화한다.
- 내부 `payload` 버전 1에 제목·내용·링크·수신자 UUID 목록을 저장한다. 재시도에서는 저장된 대상을 사용한다. 이벤트 시작 알림은 생성 시점에 수신 자격을 판정한 후 등록하며, 등록 시점의 목록을 예약 대상처럼 미리 고정하지 않는다.
- `NotificationWorker`는 기본 1초 간격으로 생성 작업·모의 발송 각각 최대 20건을 처리한다. 동기 HTTP 요청 안에서 알림 전체 생성을 기다리지 않는다.
- `getddo.notification.worker.enabled=false`로 이 워커만 중지할 수 있다. `getddo.notification.worker.poll-delay`는 조회 주기(밀리초)이며 기본값은 `1000`이다. 기존 YAML 파일은 변경하지 않았다.
- 배포 시 V014 인덱스 마이그레이션을 적용한다. 과거 사용 후 제거된 V012·V013의 번호는 재사용하지 않는다. 기존 V010은 수정하지 않는다. 새 브로커나 Spring Batch 의존성은 추가하지 않는다.

## 처리와 재시도

- 작업 선점과 사용자별 생성은 짧은 별도 트랜잭션이다. 사용자 알림과 처리 위치를 함께 저장하며, 중간 실패 시 이미 생성된 알림은 보존한다.
- `occurrence_key`와 `(job_id, user_id)`의 기존 UNIQUE 제약으로 중복을 막는다. 이미 생성된 알림의 ID·문구·생성 시각·읽음·발송 결과를 덮어쓰지 않는다.
- 2026-10-01 사용자 확인 기준: 생성·모의 발송 각각 최초 1회와 최대 3회 재시도, 간격은 10초·30초·60초다. 일시적 DB 접근·연결 오류와 모의 발송 일시 실패만 자동 재시도한다. 입력·제약 오류 등은 최종 실패로 남긴다.
- 생성 실패는 `notification_jobs.last_error`, 발송 실패는 `notifications.last_delivery_error`에 안전한 오류 코드만 기록한다. 예외 원문·SQL·사용자 문구는 실패 필드에 저장하지 않는다.
- 선점 제한 시간은 60초다. 생성은 사용자별 저장 시 연장한다. 장애로 선점이 만료되면 다음 처리자가 차수를 올려 이어 처리한다. 만료된 4번째 시도도 최종 실패로 전환해 무한 반복을 막는다.
- 모의 발송은 `next_delivery_attempt_at`을 선점 제한 시각으로도 사용한다. 성공 시 비우고 실패 시 재시도 시각 또는 null을 저장한다. 선점 차수를 함께 검사하므로 이전 처리자의 늦은 결과가 새 결과를 덮어쓰지 못한다.
- 모의 발송이 60초를 넘더라도 다른 처리자가 재선점하지 않았다면 성공 결과를 저장한다. 재선점 후에는 이전 차수의 성공·실패 결과를 저장하지 않는다.
- 모의 발송 성공은 `SENT`·발송 시각만 기록한다. 읽음 여부는 사용자 API만 변경한다. 현재 모의 발송기는 성공을 반환하며, 장애 테스트는 발송 Bean을 대체한다.

## 장애 확인

1. DB 연결과 워커 실행 여부를 확인한다. DB 접근·실패 기록 자체가 불가능한 동안에는 저장된 선점의 만료 후 처리가 복구된다.
2. 생성·발송의 상태와 차수·다음 시각·안전한 오류 코드를 확인한다. 아래 조회에 알림 내용이나 개인정보는 포함하지 않는다.

```sql
SELECT HEX(id), status, attempt_count, scheduled_at,
       next_attempt_at, lease_until, last_error
FROM notification_jobs
WHERE status IN ('PENDING', 'PROCESSING', 'FAILED');

SELECT HEX(id), mock_delivery_status, delivery_attempt_count,
       next_delivery_attempt_at, last_delivery_error
FROM notifications
WHERE mock_delivery_status IN ('PENDING', 'FAILED');
```

3. 최종 실패는 자동 재시도하지 않는다. 입력·연결·원본 참조 등의 원인을 먼저 확인한다. 관리자 조회·최종 실패 재처리 API는 GD-72의 후속 범위이며 현재 제공하지 않는다.

## 적용 범위와 한계

- DB 선점은 여러 서버의 동시 처리와 프로세스 종료 후 복구를 지원한다. 외부 발송은 수행하지 않으므로 외부 시스템과의 발송 exactly-once 계약은 만들지 않는다.
- 각 생성 작업의 수신자 목록은 한 번에 읽고 사용자별로 저장한다. 대규모 수신자에서 목록 저장·조회 및 재시도 비용은 별도 성능 측정이 필요하다.
- 이벤트 시작·일정 변경·결과 발표의 실제 생산자 연결은 GD-69~GD-71이다. 공동 업무 코드와 공개 API는 이 기반 구현에서 변경하지 않는다.
