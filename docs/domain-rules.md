# 도메인 규칙

기능이 "무엇을 하는가"가 아니라 "정확히 어떤 조건에서 어떻게 판정하는가"를 정의합니다. 각 담당자는 자신의 절만 채웁니다.

---

## 응모권 · 일회성 미션 · 게임 (담당: 윤태형)

### 응모권 적립·사용 규칙

| 규칙 | 내용 |
|---|---|
| 원장 모델 | 적립은 양수 delta, 사용은 음수 delta로 원장에 append. 원장 행은 어떤 경우에도 UPDATE/DELETE 되지 않는다(DB 트리거로 거부). |
| 전역 단일 지갑 | 응모권은 회원 단위 전역 지갑이다. 원장·잔액의 단위는 `(user, event)`가 아니라 `user` 하나뿐이며, 여러 이벤트가 동시에 열려 있어도 잔액은 공유된다. |
| 소멸 없음(이벤트 단위) | 이벤트가 종료돼도 잔여 응모권은 소멸하지 않는다. 응모권은 전역 지갑에 남아 다음에 열리는 이벤트에도 쓸 수 있다. |
| 소멸 있음(달력 단위) | 매달 초기화 시점에 그 시점의 잔여 응모권은 소멸한다(`reason_code=MONTHLY_RESET`). 위 "소멸 없음"과 다른 층위의 규칙이다 — 하나는 이벤트 경계, 하나는 달력 경계. 이미 성립한 응모(사용 완료분)는 이 규칙과 무관하다. |
| 화폐는 1개 | 응모권 하나뿐이다. 별도 화폐(포인트)는 존재하지 않는다. |
| 원장 append 단일 진입점 | 잔액 갱신은 하나의 함수(전역 지갑 append 로직)를 통해서만 이루어진다. 다른 도메인(출석, 응모, 게임, 이벤트 취소 환급, 월간 초기화)은 전부 이 함수를 호출하는 쪽이지, 잔액을 직접 갱신하지 않는다. |
| 무료 응모 | `tickets_per_entry = 0`인 이벤트·경품은 응모권을 요구하지 않는다. 무료 응모는 원장에 아무 기록도 남기지 않는다(응모권이 관여하지 않으므로). |
| 이벤트 취소 환급 | 이벤트가 취소되면 그 이벤트의 유효 응모 전체가 보정 원장(양수)으로 환급된다(원본 원장 수정 금지, 보정 행만 추가). 어뷰징으로 이미 제외된 응모는 환급 대상이 아니다 — 원래부터 무효였기 때문이다. |
| 월말 무제한 이벤트 | 매월 말 잔여 응모권 소진 기회를 위해, 투입 상한이 없는(`max_tickets_per_user = NULL`) 이벤트를 열 수 있다. |

### 중복 판정 기준

| 행위 | "같은 행위"의 정의 | 강제 수단 |
|---|---|---|
| 출석/미션 적립 | `(user_id, mission_id, business_date)` 조합이 동일하면 같은 행위 | DB UNIQUE 제약(`ONCE` 미션은 `business_date`를 `1970-01-01` 센티넬로 고정) |
| 응모권 추가 투입 | 클라이언트가 발급한 `Idempotency-Key`가 동일하면 같은 행위 | `ticket_ledger.idempotency_key` UNIQUE |

### 미션 규칙

| 규칙 | 내용 |
|---|---|
| 유형 | `ACTION`(단순 행동) / `QUIZ`(정답 일치 시에만 지급) / `SURVEY`(제출 시 지급, 정오답 없음) / `REFERRAL`(친구 초대) / `EXTERNAL_VERIFY`(기업 시스템 연동 확인). 전부 자동 판정 — 퀴즈=정답비교, 설문=제출여부, 초대=코드매칭, 기업연동=Mock API 응답, 행동=클릭 즉시 자기신고. |
| 자동 판정 원칙 | 관리자 승인 큐(제출→대기→승인/반려)는 어떤 형태로도 채택하지 않는다. **최종 결정이며 재검토하지 않는다.** 사진 인증처럼 사람 또는 AI의 사후 판단이 필요한 미션 유형은 전부 범위에서 제외한다. 미션은 예외 없이 동기적으로, 그 자리에서 자동 판정된다. |
| 노출 범위 | 미션의 `event_id`는 nullable이며, 지급 화폐를 결정하지 않는다(화폐가 하나뿐이므로) — 순수하게 "어느 이벤트 페이지에 노출되는가"만 결정한다. `event_id = NULL`이면 홈 화면에 항상 노출되는 플랫폼 전체 미션. |
| 플랫폼 전체 미션 유일성 | 플랫폼 전체 미션(`event_id IS NULL`)은 정확히 1개의 행으로만 존재한다. 이벤트마다 복제 등록하지 않는다. |
| `REFERRAL` 제약 | `ONCE` 전용 — 초대한 사람 수와 무관하게 이벤트당 최초 1건의 초대 성공에만 보상한다. 항상 이벤트 소속(`event_id` 필수). |
| `EXTERNAL_VERIFY` 제약 | QUIZ의 정답 비교와 완전히 동일한 위치·방식으로 기업 API(Mock)를 동기 호출해 true/false만 확인한다. `false`면 완료 행 미생성, 재시도 가능. 항상 이벤트 소속(`event_id` 필수). 판정은 가상 회원의 `persona_tag`로 결정론적 대체(`헤비유저`→true, 그 외→false). |
| 출석은 이 목록 밖 | 출석(Attendance)은 미션 유형이 아니다. 판정·기록은 다른 팀원 담당이며, 이 도메인은 지급 함수만 제공한다. |
| 게임은 이 목록 밖 | 게임(Game)도 미션 유형이 아니다. 완료 여부가 아니라 매 플레이의 점수를 서버가 판정해 누적·최고점으로 쌓는 구조라 데이터 모양이 근본적으로 다르다 — 별도 도메인. |

### 게임 규칙

| 규칙 | 내용 |
|---|---|
| 공개 방식 | 여러 종류의 게임을 순환 없이 동시에 전체 공개한다. |
| 기록 | 게임별 점수를 기록하며, 유저·게임별 개인 최고점과 누적 점수를 함께 보관한다(성공 여부와 무관하게 항상 갱신). |
| 점수 판정 주체 | 점수는 서버가 판정한다 — 클라이언트가 점수를 그대로 주장하는 것을 신뢰하지 않는다. |
| 지급 조건 | 차등 지급 없음, 단 최소 성공 조건은 있다. 게임 전체를 통틀어 하루 1장으로 제한한다(게임별이 아님). 지급 조건은 "그냥 플레이"가 아니라 **그 게임의 성공 기준을 넘긴 플레이가 오늘 1건 이상 있어야** 한다 — 실패한 플레이는 몇 번을 해도 지급하지 않고, 성공하면 그날 몇 번을 더 하든 추가 지급은 없다. |
| 성공 기준 | 게임마다 다르게 정의될 수 있다(점수 커트라인, 퍼즐 완료 여부 등). [추가 검토 필요] 게임 종류·규칙이 정해진 뒤에만 구체적 기준을 확정한다. 판정 결과는 `score`(통계용)와 별개의 `success`(boolean, 지급용)로 나뉜다 — 지급 여부는 오직 `success`만 본다. |
| 어뷰징 | 감지 방식은 추후 검토(비정상 참여 탐지 프레임워크에 합류할 가능성). |

### 개인정보 마스킹 — 참고 (이 도메인 소관 아님, 응모권 이력 표시에 간접 관련)

응모권 이력 조회 API는 원본 개인정보를 포함하지 않는다(가상 회원 체계이므로 실제로는 마스킹 대상 필드 자체가 이 도메인 응답에 없음).
