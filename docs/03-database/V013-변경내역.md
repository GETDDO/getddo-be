## 5. FOREIGN KEY 교체 6개

단일 컬럼에서 복합으로 바꾼다. 총 개수는 104개로 같다.

```
quiz_answers
  fk_quiz_answers_1  (submission_id)      → (submission_id, mission_id)
                                            → mission_submissions(id, mission_id)
  fk_quiz_answers_2  (quiz_question_id)   → (quiz_question_id, mission_id)
                                            → mission_quiz_questions(id, mission_id)
  fk_quiz_answers_3  (selected_option_id) → (selected_option_id, quiz_question_id)
                                            → quiz_question_options(id, quiz_question_id)

survey_answers
  fk_survey_answers_1 / _2 / _3            동일 구조
```

`selected_option_id`는 NULL을 허용하며, MySQL은 복합 FK의 컬럼 중 하나가 NULL이면 제약을 만족한 것으로 처리한다. 따라서 보기를 고르지 않는 단답·자유 입력 답변은 영향을 받지 않는다.

## 왜 필요한가 — 항목별 근거와 재현

V012 스키마에 실제로 INSERT를 실행해 확인했다. 아래 8건은 전부 통과했다.

### 7-1. 출석 일일 중복

`attendances`는 `id`, `users_id`, `created_at` 셋뿐이고 UNIQUE가 없었다. 같은 사용자·같은 날 두 번째 출석이 그대로 들어간다.

- `attendance.md` — "같은 사용자의 같은 출석 기준일에는 출석을 한 번만 인정하고 보상도 한 번만 지급한다"
- `attendance.md` — "버튼 연타·새로고침·동시 요청·날짜 변경 경계에서도 같은 출석은 한 번만 반영한다"

`created_at`은 UTC 시각이라 KST 업무일을 표현하지 못한다. 동시 요청은 애플리케이션 락으로 막을 수 없다.

GD-4의 완료 조건 "사용자·날짜별 출석과 사용자·월·단계별 보상의 중복을 방지한다" 중 앞쪽이 미충족 상태였다.

### 7-2. 퀴즈 보기 소속 검증 — 가장 위험

문항 1에 답하면서 **문항 2의 정답 보기 ID**를 넣으면 그대로 저장된다. 기존 `fk_quiz_answers_3`은 보기의 존재만 확인하고 그 보기가 해당 문항의 것인지는 보지 않는다.

채점이 `SELECT is_correct FROM quiz_question_options WHERE id = ?` 형태라면 정답으로 판정되고, 미션 완료와 응모권 지급까지 이어진다.

같은 방식으로 다른 미션의 문항에 답한 기록도 들어간다. 제출과 문항이 서로 다른 미션에 속해도 막히지 않는다.

이 문제는 ERD 메모에도 기록되어 있다. "선택지는 해당 문항에, 문항은 제출한 미션에 속하는지 확인합니다. ID 존재와 UNIQUE만으로는 이 소속 관계가 보장되지 않습니다." 애플리케이션 검증으로 두기로 한 것으로 이해했으나, V012에 이미 같은 목적의 복합 FK 3개가 들어가 있어 방식을 통일하는 것을 제안한다.

```
ticket_ledger      (wallet_id, user_id)                → ticket_wallets
game_reward_claims (game_play_id, user_id, game_id)    → game_plays
event_entries      (participant_id, event_id, user_id) → event_participants
```

### 7-3. 출석 보상 지급 형태

`reward_type = 'DAILY'`인데 연속 출석 정책과 `milestone_days`를 함께 채운 행이 들어간다. DBML Note에 "DAILY일 때 필수, STREAK는 NULL"로 적혀 있으나 CHECK가 없었다. 출석 5개 테이블에 CHECK가 하나도 없는 상태였다.

`event_participants`, `event_entries`, `ticket_ledger`에는 같은 성격의 형태 CHECK가 있다.

### 7-4. 연속 출석 단계 범위

`milestone_days = 99`, `reward_ticket_count = -5`가 통과한다.

- `attendance.md` — "단계 일수는 1~28일 범위에서 중복 없이 오름차순으로 설정한다"
- `attendance.md` — "월 단위로 초기화하므로 28일을 초과하는 단계는 두지 않는다"

기존 `uq_streak_policy_milestone (policy_set_id, milestone_days)`는 중복만 막고 범위는 보지 않는다. 오름차순은 행 사이의 관계라 DB로 막을 수 없어 애플리케이션 검증으로 남긴다.

### 7-5. 단답형 정답 누락

`question_type = 'SHORT_ANSWER'`인데 `correct_answer`가 NULL인 문항이 등록된다. 채점 기준이 없는 문항이 생긴다.

ERD 메모 기준으로 단답형 정답은 `correct_answer` 한 개이고 OX·객관식 정답은 `quiz_question_options.is_correct`에서 관리한다. 두 곳 중 어디에 정답이 있어야 하는지를 유형에 따라 강제한다.

### 7-6. 미션 운영 기간 역전

종료가 시작보다 앞선 미션이 등록된다. `events`에는 `chk_event_dates (ends_at > starts_at)`가 있으나 `missions`에는 없었다.

### 7-7. 빈 퀴즈 답변

선택지도 답변 문자열도 없는 답변 행이 들어간다. 채점 대상 답변은 둘 중 하나를 가져야 한다.

설문은 건너뛴 문항을 행 없음으로 표현하는지 양쪽 NULL 행으로 표현하는지가 확인되지 않아 `survey_answers`에는 같은 CHECK를 걸지 않았다. 확인 후 추가할 수 있다.

### 7-8. 시각 정밀도

38개 테이블의 시각 컬럼이 전부 초 단위였다.

- `entry.md` — "정확히 마감 시각부터는 응모할 수 없다"
- `attendance.md` — "날짜 변경 경계에서도 같은 출석은 한 번만 반영한다"

같은 초에 도착한 요청의 순서를 구분할 수 없다. 응모 접수 시각, 출석 경계, 추첨 실행 시각이 모두 해당된다.

## 검증 결과

### V001~V012 단독 (V013 이전 상태 확인)

전부 적용 성공. 41 테이블 / UNIQUE 48 / FK 104 / CHECK 22가 정상 생성된다. FK 104개도 순환 없이 붙는다.

생성 컬럼은 **2개**다. `reward_policies.open_guard`(VIRTUAL)와 `ticket_recovery_targets.active_guard`(STORED)는 정상 동작한다. 종료일 없는 ATTENDANCE 정책 2개를 넣으면 `uq_reward_policies_1`이 막는다.

`event_entries.single_entry_guard`는 생성 컬럼이 아니라 `int DEFAULT NULL`이다. 1로 채우면 `uq_event_entries_2`가 정상 차단하지만, NULL로 넣으면 1회 제한이 동작하지 않는다. 애플리케이션이 값을 채우는 방식을 유지하기로 했으므로 응모 구현 시 테스트로 확인한다.

### V001~V013

전부 적용 성공. 실패 0.

## 적용 시 주의

### MySQL의 컬럼 개명 제약

FK에 참여하는 컬럼을 `RENAME COLUMN`하면 `ALGORITHM=COPY`는 INPLACE를 쓰라고 하고 `ALGORITHM=INPLACE`는 COPY를 쓰라고 하며 양쪽 모두 거부한다.

```
ERROR 1846 ALGORITHM=COPY is not supported. Reason: Columns participating in a
           foreign key are renamed. Try ALGORITHM=INPLACE.
ERROR 1845 ALGORITHM=INPLACE is not supported for this operation. Try ALGORITHM=COPY.
```

`ticket_ledger.reward_claim_id`에서 이 문제가 발생해 제약을 떼고 개명한 뒤 다시 붙이는 방식으로 작성했다. 파일에 주석으로 표시해 두었다.

`attendances`와 `attendance_streaks`는 `ALGORITHM=INPLACE` 명시로 통과한다.

### 파일 위치

출석과 미션 두 도메인에 걸쳐 있어 도메인 폴더 하나에 넣기 어렵다. `V012__add_foreign_keys.sql`과 같이 `migration` 루트에 두는 방식을 제안한다. 다른 배치가 좋다면 그에 맞춘다.

## 참고 — 공유용 ERD와의 차이

`getddo-final-20260924.dbml` 기준 HTML을 이 저장소 DDL과 전수 비교한 결과 UNIQUE가 33 대 48이었다. ERD에 없는 15개 중 13개가 추첨·이벤트 영역이다.

| 테이블 | ERD에 없는 UNIQUE | 담당 |
| --- | --- | --- |
| `draw_results` | `(draw_run_id, event_prize_id, slot_number)`, `(draw_run_id, candidate_id)`, `(draw_run_id, selection_order)` | 추첨 |
| `current_awards` | `(event_id, user_id)`, `(event_prize_id, slot_number)`, `draw_result_id` | 추첨 |
| `draw_runs` | `(event_id, run_number)`, `idempotency_key` | 추첨 |
| `award_cancellations` | `draw_result_id`, `replacement_draw_id` | 추첨 |
| `draw_candidates` | `(draw_run_id, participant_id)` | 추첨 |
| `publications` | `event_id` | 추첨 |
| `event_prizes` | `(event_id, prize_rank)` | 이벤트 |
| `attendance_streaks` | `(users_id, streak_month)` | 출석 (본 문서 담당) |
| `attendance_reward_claims` | `(user_id, reward_type, source_key)` | 출석 (본 문서 담당) |

`current_awards (event_id, user_id)`는 이벤트 내 중복 당첨 방지다. ERD를 기준으로 DDL을 다시 만들면 사라진다.

기준을 `docs/03-database/schema.dbml` 하나로 통일하는 것을 제안한다. 현재 DDL이 이 파일에서 생성되었고, `AGENTS.md`도 DB는 이 저장소에서 관리한다고 정하고 있다.
