# GD-36 추첨 선정·발표 설계 검토

- 상태: 검토 대기 — 담당자 확인 전
- 범위: 최초 자동 추첨의 명단 확정, 선정, 저장, 재시도와 발표
- 공용 정책: `getddo-spec/02-domain/drawing.md`, `getddo-spec/03-decisions/013-linear-drawing-weight.md`
- 기준 코드: [이벤트 DDL](../../storage/db/src/main/resources/db/migration/event/V006__create_event_tables.sql), [추첨 DDL](../../storage/db/src/main/resources/db/migration/drawing/V007__create_drawing_tables.sql)

이 문서는 현재 SQL을 기준으로 한 백엔드 설계 검토다. DB 변경이나 선정 로직 구현이 완료됐다는 뜻은 아니다. 추첨 기회와 응모권 사용 상한은 위 공용 정책을 따른다.

## 후보 수량과 가중치

| 이벤트 방식 | `draw_candidates.ticket_count` | `draw_candidates.weight` |
| --- | --- | --- |
| 응모권 미사용 | 0 | 1 |
| 응모권 사용·가중치 미적용 | 접수 완료된 응모의 실제 차감 수량인 1 | 1 |
| 응모권 사용·가중치 적용 | 해당 이벤트에서 접수 완료된 응모의 실제 차감 수량 합계 | `ticket_count`와 동일 |

- 수량의 근거는 `event_entries.status = ACCEPTED`인 행의 `deducted_ticket_count`다. 추가 응모도 합산하고 `requested_ticket_count`와 거절 행은 제외한다. `event_participants.used_ticket_count`는 같은 이벤트·사용자의 누적 차감 수량을 대조하는 값으로 사용한다. 불일치 시 임의의 한 값을 채택하지 않고 정합성 오류로 다룬다.
- 후보는 해당 이벤트의 `event_participants`에서 추첨 대상 제외가 확정되지 않은 사용자로 한정한다. 후보의 계산된 가중치가 0이면 `READY` 확정 전 정합성 오류로 중단하고, 해당 후보를 `draw_candidates`에 고정하거나 선정하지 않는다. 모든 후보의 가중치가 0이어도 대상 없음으로 처리하거나 추첨을 진행하지 않는다. `draw_candidates`는 `(draw_run_id, participant_id)`가 유일하므로 후보당 실행별 한 행을 둔다.
- `ticket_count`는 현재 `BIGINT`, `weight`는 `DECIMAL(30,10)`이다. 선형 가중치는 정수 값으로 저장할 수 있고 별도 가중치 상한 컬럼이나 스키마 변경은 현재 정책상 필요하지 않다. 월말 소진용 이벤트에는 공용 정책상 수량 상한이 없으므로 구현에서 저장 자료형의 허용 범위와 합계 연산 오버플로를 검증해야 한다.

## 실행 스냅샷과 결과

- `draw_runs.status = READY`로 후보·조건을 고정할 때 실행별 후보의 응모권 수와 가중치를 `draw_candidates`에 저장한다. 같은 실행의 실패 후 재시도에서는 이 값을 다시 계산하지 않는다. 스냅샷 확정 전 실패라면 정합성을 다시 검사한 뒤 고정한다. 최초 추첨 뒤 새 재추첨 실행에는 공용 정책에 따라 최초 추첨 당시 가중치를 사용한다.
- 실제 선정은 상위 등수부터 진행하고, 선정된 사용자는 다음 자리의 후보에서 제외한다. `draw_results`의 `(draw_run_id, candidate_id)` 유일 제약은 한 실행 내 동일 후보의 중복 선정을 막는다. 후보가 부족한 자리는 `result_type = UNFILLED`로 남긴다.
- `draw_results`의 외래 키와 유일 제약만으로 후보·경품·실행이 같은 이벤트에 속하는지, 재추첨에서 이전 당첨자가 제외됐는지는 보장되지 않는다. 선정 결과를 확정하기 전에 이 관계를 검증해야 한다.

## 최초 실행과 마감 경합

- `events.ends_at + 5분`이 지난 뒤 최초 자동 실행을 시작한다. 서버 시각으로 마감·이벤트 취소 여부를 확인하고, 이벤트별 최초 실행의 `run_number`와 멱등 키를 고정한다. 스케줄러 중복 호출과 다른 인스턴스의 동시 실행은 이벤트 행 잠금과 실행의 유일 제약으로 직렬화한다.
- 응모 접수, 추첨 대상 제외 확정, 명단 확정은 **이벤트 행을 먼저 잠그는 동일한 순서**로 처리한다. 잠금을 얻은 뒤 마감 검증과 상태 검증을 다시 수행한다. 마감 전 접수가 커밋됐다면 스냅샷에 포함하고, 마감 후 접수는 거절한다. 제외는 명단 확정 전에 커밋된 결정만 반영하고, 명단 확정 뒤 결정은 이미 고정된 실행에 소급하지 않는다. 실제 잠금 범위와 순서는 D 담당 응모·차감 구현과 합의가 필요하다.
- 잠금 아래에서 `ACCEPTED` 응모의 실제 차감 합계와 참가자 누적 수량을 **후보 제외 여부와 관계없이** 대조한다. 차이가 있으면 `READY`·`CONFIRMED`·공개로 진행하지 않는다. 운영자가 원인을 수정한 뒤 같은 실행을 재시도한다. 불일치를 임의 보정하거나 임의의 수량을 선택하지 않는다.
- 후보·경품 조건·알고리즘 버전을 실행별 스냅샷으로 고정한다. 응모자 0명과 전원 제외는 각각 별도 종료 상태로 기록하고 당첨 결과를 생성하지 않는다. 경품 설정 인원은 고정된 조건을 사용한다.

## 선정과 원자적 확정

- 양의 정수 가중치를 합산하고, 암호학적으로 안전한 난수로 `[0, 총 가중치)`의 정수를 편향 없이 뽑는다. 누적 가중치 구간에 해당하는 후보를 선정한다. 월말 소진용 이벤트의 합계가 정수 표현 범위를 넘지 않도록 임의 정밀도 정수 또는 동등한 안전한 연산을 사용한다. 난수 시드·동일 결과 재현은 요구하지 않는다.
- `prize_rank` 오름차순, 같은 등수에서는 고정된 슬롯 순서대로 선정한다. 한 자리에 선정된 사용자는 이벤트 내 다음 자리의 후보에서 제거하고 남은 가중치로 다시 뽑는다. 후보가 소진되면 나머지 슬롯을 `UNFILLED`로 저장한다. 후보가 0명인 시작 상태는 위의 대상 없음 종료와 구분한다.
- `draw_results`의 슬롯·후보·선정 순서 유일 제약과 `current_awards`의 이벤트별 사용자·경품 슬롯 유일 제약을 함께 사용한다. 확정 전 후보·경품·실행의 이벤트 일치, 경품별 설정 인원, 중복 당첨, 기존 유지 당첨자와의 충돌을 검증한다. 결과와 현재 당첨 배정은 하나의 트랜잭션으로 확정한다. 중간 실패 시 부분 선정 결과를 확정된 결과로 보이지 않는다.
- `CONFIRMED`인 동일 실행의 재요청은 저장된 결과를 반환한다. `READY` 이후 일시적 실패를 재시도할 때는 저장된 스냅샷을 사용하되 아직 확정되지 않은 선정은 새 난수로 다시 수행할 수 있다. 확정된 결과를 재선정하지 않는다. 검증은 저장된 스냅샷과 결과의 관계를 확인하며 난수 재생을 요구하지 않는다.

## 실패, 재시도와 공개

- 최초 시도 후 일시적 오류에 한해 최대 3회 자동 재시도한다(총 최대 4회). 실패 횟수·코드·시각을 `draw_runs`에 남긴다. 트랜잭션이 롤백돼도 실패 기록은 별도 확정해야 한다. 재시도 예약이 유실되지 않도록 미완료 실행을 다시 찾을 수 있어야 한다. 재시도 간격과 실행 기술은 구현 시 정한다.
- 차감 수량 불일치 등 정합성 오류나 자동 재시도 소진은 운영자 확인 후 재개한다. 오류만으로 이벤트를 자동 취소하지 않는다. 재개는 같은 최초 실행을 대상으로 하며, 이미 `CONFIRMED`라면 저장 결과를 반환한다. 실패 분류와 운영자 재개 경로는 구현 시 운영 계약으로 구체화한다.
- 최초 공개는 예정 시각 이후 **확정된 결과에 대해서만** 자동 수행한다. 결과 확정 뒤 공개만 실패했다면 선정은 다시 하지 않고 저장된 결과의 공개를 재시도한다. 공개 여부는 서버의 `publications` 반영 상태로 판단하며, 중복 공개 요청은 동일 이벤트의 공개 이력·알림을 중복 생성하지 않도록 한다.
- 공개 완료 전에는 사용자 공개 결과를 `WAITING`, 본인 결과를 `PENDING`으로 유지하고 결과 배열·경품·당첨 여부를 반환하지 않는다. 예정 시각이 지난 지연 상태에는 “결과 확인 중”을 표시한다. 원인 복구 후 자동 공개한다. 응모자 없음·전원 제외는 정상 종료로 별도 표시한다. 최초 발표 이후의 재추첨 공개에는 공용 도메인의 관리자 확인 규칙을 적용한다.

## 구현 전 검증 시나리오

| 영역 | 시나리오와 기대 결과 |
| --- | --- |
| 가중치 | 고정 후보의 가중치 1:3에서 다수 반복 선정 시 확률이 비례하는지 통계 허용 범위로 확인한다. 난수 값 경계별 누적 구간 선택도 확인한다. |
| 0 가중치 | 후보 중 가중치가 0인 사용자가 하나라도 있으면 `READY` 확정 전에 정합성 오류로 중단한다. 전원 0인 경우에도 대상 없음으로 종료하거나 선정하지 않는다. 응모권 미사용 후보는 `ticket_count = 0`, `weight = 1`로 정상 처리한다. |
| 순서·부족 | 1등부터 슬롯을 채우고 당첨자를 다음 슬롯에서 제거한다. 후보보다 슬롯이 많으면 남은 슬롯만 `UNFILLED`; 후보 0명과 전원 제외는 각각 별도 종료한다. |
| 중복 | 같은 사용자에게 같은 경품 또는 다른 등수의 경품이 중복 배정되지 않고, DB 유일 제약 위반 시 전체 확정이 롤백된다. |
| 마감 경합 | 마감 직전 응모·제외 결정과 명단 확정의 커밋 순서를 이벤트 잠금으로 맞추며, 마감 후 응모는 포함하지 않는다. |
| 정합성 | `ACCEPTED.deducted_ticket_count` 합계와 `used_ticket_count` 불일치 시 확정·발표가 멈춘다. 복구 후 같은 실행에서 다시 검사한다. |
| 동시 실행 | 스케줄러 두 인스턴스가 같은 이벤트를 처리해도 최초 실행·확정 결과·공개 이력은 각각 하나다. |
| 실패 재시도 | 일시적 실패는 최초 시도와 최대 3회 재시도하고, 정합성 오류·재시도 소진은 운영자 재개를 기다린다. 확정 후 공개 실패는 재선정하지 않는다. |
| 재조회·비공개 | `CONFIRMED` 재조회는 저장된 결과와 순서를 반환한다. 공개 전과 발표 지연 중 사용자 API는 `WAITING`·`PENDING`을 유지하고 당첨 정보를 숨긴다. |

## 구현 전 확인

- D 담당과 이벤트 잠금 순서, `ACCEPTED` 실제 차감 수량 및 `used_ticket_count`의 원자적 갱신 계약을 확인한다. 해당 담당 영역 코드는 확인 전 변경하지 않는다.
- 프론트엔드 담당과 지연 중 “결과 확인 중” 표시 및 기존 `WAITING`·`PENDING` 응답 사용을 확인한다.
- 이 문서는 구현·테스트 완료 기록이 아니다. 스케줄링 기술, 오류 분류와 운영자 재개 API는 구현 전에 구체화한다.
