# 결과 공개·관리자 확인 저장

- 담당: GD-139, GD-169 연동. 공용 정책 원본은 [추첨 규칙](https://github.com/Uplus-GETDDO/getddo-spec/blob/main/02-domain/drawing.md)이다.
- 이 문서는 백엔드 저장·서비스 연결을 설명한다. 공용 HTTP 명세의 미확정 항목을 일괄 확정하지 않는다.

## 저장과 잠금

기존 V007의 `draw_publications`, `draw_publication_results`, `draw_result_confirmations`를 사용한다. GD-169는 V024의 `draw_publication_executions`로 공개 실행 근거를 추가한다. 기존 Flyway는 수정하지 않는다. 공개 버전과 실제 포함 결과는 불변 기록이다. 당첨 취소로 과거 포함 결과를 삭제하거나 바꾸지 않는다. `wasPublished(resultId)`는 실제 포함 이력을 뜻하며 현재 취소 여부와 별개다.

변경 트랜잭션은 서비스에만 선언한다. 이벤트 → 최초 실행 순서로 기존 잠금을 얻은 뒤 저장된 확정 결과·취소 연결·재추첨 확인을 읽는다. 같은 이벤트의 취소·실행 확정도 GD-87·GD-138의 이벤트 선잠금 계약을 지켜야 한다. 동일 실행의 확인 UNIQUE와 이벤트·공개 버전 UNIQUE는 DB에서 보조하며 서비스는 잠금 뒤 기존 확인과 최신 버전을 다시 조회한다.

관리자 확인과 공개 목록 저장은 같은 트랜잭션이다. 공개 저장 실패 시 새 확인도 롤백한다. 유지 결과는 원본 실행·기존 확인 ID를 그대로 참조하고 새 결과만 새 확인을 참조한다. 불변 엔티티 INSERT 후에는 detach·재조회로 실제 저장 시각을 읽는다. `refresh`는 사용하지 않는다.

## 서비스 연결

- `DrawPublicationService.publishInitial(eventId)`: 마감 +300초 이후 최초 결과를 공개한다. 준비·확인이 미완료이면 빈 Optional을 반환해 재호출을 기다린다. 이미 최초 공개됐으면 최신 버전을 반환한다.
- `DrawResultConfirmationService.confirmBeforeInitial(runId, actorId)`: 최초 공개 전 재추첨 확인. 예정 시각 전에는 확인만 저장한다. 최초 공개 후에는 기존 확인의 재요청만 허용한다.
- `confirmForPublication(runId, actorId)`: 최초 공개가 존재할 때만 재추첨 결과를 확인·반영한다. 기존 연결 취소 사유를 사용하며 별도 사유를 입력받지 않는다. 반환은 요청 실행의 가상 버전이 아닌 실제 최신 공개 버전이다.
- `confirmReplacement(runId, actorId)`: 기존 내부 확인 진입점. HTTP 단계 제한은 위 두 진입점에서 검사한다.
- `DrawPublicationQueryService.changes(eventId, actorId, PageQuery)`: 활성 관리자 확인 후 공개 버전을 최신순으로 조회한다. REPEATABLE_READ에서 총 건수·페이지·경계 이전 버전을 읽고, 포함 결과는 버전 ID 목록으로 일괄 조회한다.

최초 공개 전 취소·재추첨은 모든 연결 실행의 확정·관리자 확인을 기다린다. 전체 유지 명단과 확인된 새 결과를 함께 공개한다. 이후 갱신은 확인된 실행만 반영하고 미확인 실행의 기존 명단은 유지한다. 미공개 중간 결과를 취소한 후속 결과는 선행 확인까지 기다린다. 같은 실제 포함 결과를 다시 요청하면 버전·이력을 추가하지 않는다.

HTTP 연결은 2026-10-12 사용자 승인 범위(AD06 본문 없음, 최초 공개 전 확인 진입점, AD07 페이지 기본 1/20·size 1~100)를 따른다. 응답의 공개 식별자·시각은 실제 저장값을 사용한다. 최초 확인 응답에서 아직 미공개이면 공개 식별자·버전·시각은 null이다. AD06의 `drawRunId`는 반환된 최신 버전의 원본 실행이고, `publishedAt`·`updatedAt`은 해당 버전의 실제 공개 시각이다. AD07의 `id`·`publicationId`는 같은 불변 공개 버전 ID다. 정상 최초 공개 이력의 사유·확인자는 null일 수 있다.

승인 근거는 이 작업 대화에서 AD06의 `ReasonRequest`를 받지 않고 기존 연결 취소 사유를 사용하는 안, 본문 없는 `/result-confirmation` 경로, 관리자 권한·HTTP 상태·페이징을 함께 제안한 질문에 대한 사용자의 **“제안 계약으로 확정”** 답변이다. 인접 getddo-spec의 2026-10-13 계약 보완 문서에 승인 내용이 반영되어 있다. 2026-10-13 확인 시 해당 계약 보완은 인접 getddo-spec의 미커밋 문서에 있으며, 원격 main(`00f0d743`)에는 아직 반영되지 않았다. 초안의 `ReasonRequest`를 확정 정책으로 해석하지 않는다.

승인일은 2026-10-12이며 적용 범위와 공용 spec 동기화 후속은 [PR #59](https://github.com/Uplus-GETDDO/getddo-be/pull/59)에서 추적한다. 승인 근거에 대한 설명과 초안 기반 지적 철회는 [해당 리뷰 스레드](https://github.com/Uplus-GETDDO/getddo-be/pull/59#discussion_r4244759752)에 보존한다.

## 담당 경계와 검증 한계

GD-139는 실행 시작·선정·실패 재개·취소·새 재추첨을 수행하지 않는다. GD-87의 저장 결과와 GD-138의 연결 취소를 읽는 공개 전용 projection을 사용한다. 두 담당의 공용 모델·Repository·상태 흐름은 수정하지 않는다.

GD-86 자동 등록·예정 시각 및 지연 재호출과 GD-140 공개 버전 조회는 후속 작업이다. GD-169는 기존 `NotificationJobService.register`에 실제 공개 알림 작업을 연결했다. 알림 생성·발송·재시도는 기존 알림 담당 코드가 처리한다. 신규 이벤트 상태 전이는 추가하지 않는다.

단위 테스트의 동시성·롤백은 실제 서비스와 Spring 프록시 및 메모리 저장/잠금 대역으로 검증한다. MVC 테스트도 실제 사용자 문맥·권한·확인 서비스를 사용하되 공개 계산·저장은 대역이다. GD-139 MySQL 테스트 코드는 최초 입력·확정에 GD-84·85를 사용하고 취소·재추첨에는 SQL fixture를 사용한다. GD-139 작업 당시 Docker 금지 범위에서 MySQL 테스트는 실행하지 않았다. 실제 GD-87·GD-138·GD-139 전체 서비스 연결과 DB 잠금·원자성 검증은 GD-169에서 수행하며 대역 테스트를 실제 연동 완료로 보고하지 않는다.

## GD-169 연결과 조회 계약

상태: 백엔드 구현 검토 대기(PR #69). 아래는 현재 구현 설명이며 공용 DTO 계약을 새로 확정하지 않는다. 통합 테스트 통과는 구현 검증 결과이며 담당자 승인·운영 적용 완료를 뜻하지 않는다.

- 공개 버전과 결과 포함 행, 실행별 확인 연결, 기존 알림 작업은 같은 서비스 트랜잭션에서 저장한다. 작업 등록 실패는 새 공개·새 확인을 롤백한다. 커밋 뒤 생성·발송 실패는 공개를 되돌리지 않는다.
- AD07의 `executions`는 실행 번호 순으로 `runId`, `confirmationId`, `confirmedBy`, `confirmedAt`, `cancellations[{id,resultId,reason}]`를 제공한다. 취소 목록은 `canceled_at` 순, 같은 시각이면 ID 순이다. 실제 반영된 미충원 실행도 포함한다. 단일 사유·확인자 필드는 계기 실행의 정보다. `executions` 필드명과 구체 DTO는 원격 공용 `PublicListChange`에 반영되기 전 백엔드 제안이며 [PR #69](https://github.com/Uplus-GETDDO/getddo-be/pull/69)에서 검토한다. V024 도입 전 근거 연결이 없는 버전은 목록이 비어 있으며 현재 상태로 소급 추정하지 않는다.
- 공개 근거와 경계 이전 버전·포함 결과는 페이지 단위로 일괄 조회한다. 이후 취소나 확인은 저장된 과거 버전의 확인 연결을 덮어쓰지 않는다.
- 활성 관리자 검증은 실행·취소·확인에서 `DrawAdminAuthorization`을 공유한다. 관리자 조회는 공통 사용자 문맥에서 조회한 사용자를 같은 조건으로 검증한다. 각 업무 오류 코드와 처리자 없는 자동 실행은 유지한다.
- 최초 알림 대상은 접수 기록이 있는 이벤트 응모자 전원이다. 변경 알림 대상은 직전 공개 버전과 비교한 취소자·새 당첨자이며 유지 당첨자와 다른 응모자는 제외한다. 발생 키는 `draw-publication:<publicationId>`, payload의 공개 식별자·문구·링크·수신 목록·예약 시각은 등록 후 고정이다.
- 기존 `DrawPublicationEntity`, `DrawResultConfirmationEntity`의 UUID v7·업무 시각을 유지한다. BaseEntity 전환은 created_at 추가와 기존 데이터 채움의 별도 마이그레이션이 필요하다. [ADR-0001](../04-decisions/0001-common-entity-uuid-auditing.md)의 사용자 승인 예외를 따른다.
- 취소 등록의 기존 REDRAWING 변경은 유지한다. 최초 확정·실제 공개의 이벤트 상태 갱신에 재사용할 기존 코드가 없어 이번 작업에서 새 상태 변경 기능을 만들지 않았다. 추첨 상태와 실제 공개 행은 정상 처리되며 이벤트 담당과의 연결은 후속 확인이다.

GD-169 통합 테스트는 실제 취소·재추첨 실행·검증·관리자 확인·공개·기존 알림 생성/모의 발송을 연결한다. 초기 응모·보상 출처만 SQL 데이터이며 실제 연결을 대역 테스트로 대신하지 않는다. 리뷰 전 커밋 `2742c90`은 2026-10-13 제한 설정을 적용한 전체 test/build가 통과했다. 단위 816건, API 통합 114건, DB 통합 577건이며 GD-169 실제 연결 클래스는 21건이다. 실패·오류·스킵은 0건이다. 테스트 환경의 새 Flyway 적용과 운영 DB 적용을 구분한다.
