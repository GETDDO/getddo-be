# 결과 공개·관리자 확인 저장

- 담당: GD-139. 공용 정책 원본은 [추첨 규칙](https://github.com/GETDDO/getddo-spec/blob/main/02-domain/drawing.md)이다.
- 이 문서는 백엔드 저장·서비스 연결을 설명한다. 공용 HTTP 명세의 미확정 항목을 일괄 확정하지 않는다.

## 저장과 잠금

기존 V007의 `draw_publications`, `draw_publication_results`, `draw_result_confirmations`를 사용한다. 새 스키마 변경은 없으며 기존 Flyway도 수정하지 않는다. 공개 버전과 실제 포함 결과는 불변 기록이다. 당첨 취소로 과거 포함 결과를 삭제하거나 바꾸지 않는다. `wasPublished(resultId)`는 실제 포함 이력을 뜻하며 현재 취소 여부와 별개다.

변경 트랜잭션은 서비스에만 선언한다. 이벤트 → 최초 실행 순서로 기존 잠금을 얻은 뒤 저장된 확정 결과·취소 연결·재추첨 확인을 읽는다. 같은 이벤트의 취소·실행 확정도 GD-87·GD-138의 이벤트 선잠금 계약을 지켜야 한다. 동일 실행의 확인 UNIQUE와 이벤트·공개 버전 UNIQUE는 DB에서 보조하며 서비스는 잠금 뒤 기존 확인과 최신 버전을 다시 조회한다.

관리자 확인과 공개 목록 저장은 같은 트랜잭션이다. 공개 저장 실패 시 새 확인도 롤백한다. 유지 결과는 원본 실행·기존 확인 ID를 그대로 참조하고 새 결과만 새 확인을 참조한다. 불변 엔티티 INSERT 후에는 detach·재조회로 실제 저장 시각을 읽는다. `refresh`는 사용하지 않는다.

## 서비스 연결

- `DrawPublicationService.publishInitial(eventId)`: 마감 +300초 이후 최초 결과를 공개한다. 준비·확인이 미완료이면 빈 Optional을 반환해 재호출을 기다린다. 이미 최초 공개됐으면 최신 버전을 반환한다.
- `DrawResultConfirmationService.confirmBeforeInitial(runId, actorId)`: 최초 공개 전 재추첨 확인. 예정 시각 전에는 확인만 저장한다. 최초 공개 후에는 기존 확인의 재요청만 허용한다.
- `confirmForPublication(runId, actorId)`: 최초 공개가 존재할 때만 재추첨 결과를 확인·반영한다. 기존 연결 취소 사유를 사용하며 별도 사유를 입력받지 않는다. 반환은 요청 실행의 가상 버전이 아닌 실제 최신 공개 버전이다.
- `confirmReplacement(runId, actorId)`: 기존 내부 확인 진입점. HTTP 단계 제한은 위 두 진입점에서 검사한다.
- `DrawPublicationQueryService.changes(eventId, actorId, PageQuery)`: 활성 관리자 확인 후 공개 버전을 최신순으로 조회한다. REPEATABLE_READ에서 총 건수·페이지·경계 이전 버전을 읽고, 포함 결과는 버전 ID 목록으로 일괄 조회한다.

최초 공개 전 취소·재추첨은 모든 연결 실행의 확정·관리자 확인을 기다린다. 전체 유지 명단과 확인된 새 결과를 함께 공개한다. 이후 갱신은 확인된 실행만 반영하고 미확인 실행의 기존 명단은 유지한다. 미공개 중간 결과를 취소한 후속 결과는 선행 확인까지 기다린다. 같은 실제 포함 결과를 다시 요청하면 버전·이력을 추가하지 않는다.

HTTP 연결은 2026-10-12 사용자 승인 범위(AD06 본문 없음, 최초 공개 전 확인 진입점, AD07 페이지 기본 1/20·size 1~100)를 따른다. 응답의 공개 식별자·시각은 실제 저장값을 사용한다. 최초 확인 응답에서 아직 미공개이면 공개 식별자·버전·시각은 null이다. AD06의 `drawRunId`는 반환된 최신 버전의 원본 실행이고, `publishedAt`·`updatedAt`은 해당 버전의 실제 공개 시각이다. AD07의 `id`·`publicationId`는 같은 불변 공개 버전 ID다. 정상 최초 공개 이력의 사유·확인자는 null일 수 있다.

승인 근거는 이 작업 대화에서 AD06의 `ReasonRequest`를 받지 않고 기존 연결 취소 사유를 사용하는 안, 본문 없는 `/result-confirmation` 경로, 관리자 권한·HTTP 상태·페이징을 함께 제안한 질문에 대한 사용자의 **“제안 계약으로 확정”** 답변이다. 공용 spec에는 아직 이 승인 내용이 반영되지 않았다. 이 문서는 구현에 적용한 사용자 승인과 남은 공용 문서 동기화를 구분하며, 초안의 `ReasonRequest`를 확정 정책으로 해석하지 않는다.

## 담당 경계와 검증 한계

GD-139는 실행 시작·선정·실패 재개·취소·새 재추첨을 수행하지 않는다. GD-87의 저장 결과와 GD-138의 연결 취소를 읽는 공개 전용 projection을 사용한다. 두 담당의 공용 모델·Repository·상태 흐름은 수정하지 않는다.

GD-86의 자동 등록·예정 시각 및 지연 재호출, GD-140의 공개 버전 조회, GD-71의 실제 공개 완료 전달은 후속 연결이다. 알림 담당에는 불변 publicationId·eventId·revision·실제 포함 결과·publishedAt으로 최초 공개와 갱신을 구분하는 계약이 필요하다. 커밋 후 전달·재전달·중복 수신·대상/payload는 담당자 합의가 필요하며 이 구현은 알림·outbox·상태 전이를 추가하지 않는다.

단위 테스트의 동시성·롤백은 실제 서비스와 Spring 프록시 및 메모리 저장/잠금 대역으로 검증한다. MVC 테스트도 실제 사용자 문맥·권한·확인 서비스를 사용하되 공개 계산·저장은 대역이다. GD-139 MySQL 테스트 코드는 최초 입력·확정에 GD-84·85를 사용하고 취소·재추첨에는 SQL fixture를 사용한다. 이번 Docker 금지 범위에서 MySQL 테스트는 실행하지 않았다. 실제 GD-87·GD-138·GD-139 전체 서비스 연결과 DB 잠금·원자성 검증은 GD-169에서 수행하며 대역 테스트를 실제 연동 완료로 보고하지 않는다.

## 리뷰에서 남긴 결정 항목

- 검토 대기: 여러 재추첨을 한 버전으로 공개할 때 AD07의 단일 사유·확인자/시각 표현. 현재는 계기 실행의 확인·연결 사유를 반환하고 각 포함 결과는 해당 실행의 확인 ID를 보존한다. 이번에 반영한 모든 실행의 사유 결합 범위·순서와 확인 메타데이터 표현은 별도 승인이 필요하다. 기존 취소 사유·확인 기록 자체는 삭제되지 않는다.
- 담당 확인 대기: 채택된 ADR-0001은 BaseEntity 예외를 응모권 두 Entity로 한정한다. V007의 공개·확인 테이블에는 created_at이 없으므로 현재 두 엔티티에 BaseEntity를 추가하면 DDL과 충돌한다. 공통 담당 A에게 업무 시각을 사용하는 두 엔티티의 예외 확대를 확인해야 하며 채택 ADR이나 스키마를 독립 변경하지 않는다.
- 범위 결정 대기: GD-169의 실제 취소 등록·재추첨 실행·공개/AD07 전체 통합 검증을 GD-139 PR로 옮길지 여부. 현재 사용자 요청의 담당 경계와 Docker 없는 검증 범위를 유지한다. SQL fixture나 저장 매핑 테스트를 실제 연동 완료로 대체하지 않는다.
