## 고민과 판단

- `abuse_cases`의 원본 행위 연결은 기존 FK 네 개를 유지한다. 원본 기록이 있으면 해당 종류의 FK 하나만 채우고 나머지는 NULL로 둔다. 원본 기록이 없는 거절 요청은 네 FK를 모두 NULL로 두며 `request_id`와 `evidence`로 추적한다. 담당자가 A안을 선택했다.
- `abuse_cases` 검토가 끝나면 `ALLOWED`와 부정 확인 모두 `reviewed_by`, `reviewed_at`, `review_reason`을 필수로 기록한다. `PENDING`에서는 세 컬럼을 NULL로 둔다. 담당자가 A안을 선택했다.
- `abuse_cases.review_status`는 `PENDING / ALLOWED / CONFIRMED`로 정리한다. `CONFIRMED`는 부정행위 확인을 뜻하며, 이벤트 추첨 대상 제외는 `event_participants`에서 별도로 표현한다. 담당자가 A안을 선택했다.
- `event_entries`에서 거절된 응모의 `participant_id`는 기존 응모자가 있더라도 항상 NULL로 둔다. 성공한 응모만 `event_participants`에 연결한다. 담당자가 B안을 선택했다.
- 거절 코드에 관해, 전용 코드가 없는 업무상 거절에는 `OTHER`와 구체적인 `rejection_reason`을 쓰는 방안을 설명했다. `rejection_reason varchar(500)`은 검토용 DBML의 `event_entries`에 이미 있으므로 새 컬럼은 필요하지 않다. 예상 밖의 서버 오류는 업무상 거절과 구분해야 한다. `OTHER`의 사용 조건과 상태별 필드 조건 전체는 아직 담당자가 확정하지 않았다.

## 확인 결과 / 막힌 점

- 검토용 DBML을 읽고 위 대화에서 결정한 내용만 기록했다. ERD·DDL·애플리케이션 코드는 아직 변경하지 않았다.
- 남은 검토 항목은 응모 상태별 필드 조건과 시각 의미, 제외 결정의 출처, 추첨 실패·스냅샷·후보 입력, 결과·경품·당첨 취소·발표·공개 명단의 상태와 이력이다. 연결된 행이 같은 이벤트와 사용자를 가리키는지도 검증해야 한다.
- UNIQUE 제약은 별도 후속 항목이다. 탐지·응모 멱등 키, 이벤트별 응모자·실행 차수, 후보·결과·취소·발표·현재 당첨 배정의 중복 방지 범위를 일괄 검토해야 한다.
- 별도 사이드 챗 내용은 현재 대화와 사용 가능한 도구에서 확인할 수 없어 포함하지 않았다.
- 문서 기록만 추가했으므로 테스트와 빌드는 실행하지 않았다.
