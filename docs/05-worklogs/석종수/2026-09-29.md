## 고민과 판단

- `draw_candidates.ticket_count`와 `weight`는 현재 컬럼으로 선형 가중치를 표현할 수 있어 이번 설계에서는 스키마 변경을 제안하지 않았다.
- `event_entries.deducted_ticket_count`의 성공 건 합계와 `event_participants.used_ticket_count`가 일치해야 한다. 실제 응모 구현이 아직 없어 정합성 보장은 검증 전이다.
- 확정 결과는 재추첨하지 않고 저장값을 반환하며, 결과 확정 뒤 공개 실패 시에는 공개만 복구하도록 설계했다.
- 선정 난수는 `SecureRandom`의 범위 밖 값을 재추출해 편향을 피하고, 가중치 합계는 `BigInteger`로 계산해 `long` 합계 오버플로를 피했다. 후보 명단 확정·결과 저장·자동 실행은 이번 선정 로직 범위에 포함하지 않았다.

## 확인 결과 / 막힌 점

- GD-36 설계 단계에서는 현재 SQL·DBML을 정적으로 확인했다. 당시에는 DB 적용이나 Java 구현·테스트·빌드를 실행하지 않았다.
- GitHub DNS 연결 실패로 백엔드와 spec의 원격 최신 상태를 확인하지 못했다. 이 기록은 로컬 체크아웃 기준이다.
- 후속 작업에서는 원격 조회가 성공했다. `getddo-spec/main`은 원격과 동일했으며, 백엔드 `feat/GD-36`은 추적 브랜치가 없어 pull하지 않았다. 이 기록의 앞선 DNS 실패는 최초 작업 시점의 결과다.
- 후속 GD-56 구현 단계에서 추첨 선정 단위 테스트 8개, `./gradlew test`, `./gradlew build`가 모두 통과했다. WSL의 Windows 드라이브 파일 권한 문제로 Gradle 빌드 결과물은 `/tmp`에 두고 Linux JDK 21로 실행했다.
