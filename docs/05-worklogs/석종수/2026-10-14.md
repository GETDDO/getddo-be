### 추첨 후속 문서와 작업 계획

- 초기 스케줄러 계획을 작성한 뒤 사용자 확인에 따라 자동 추첨 → 관리자 명단 검토·필요시 개별 취소/재추첨 → 최종 확인 → 수동 최초 공개로 변경했다. 최초의 자동 공개 계획은 이 결정으로 대체됐다.
- GD-86은 자동 추첨만 담당한다. V1은 10초 주기·건수 제한·순차 처리와 기존 중복 방지·복구를 사용하고, V2 인덱스 개선은 후속으로 남겼다.
- GD-131은 실제 응모·차감 코드와 스냅샷 정합성을 검증한다. GD-140은 공개 결과 조회와 이름·전화번호 마스킹을 담당한다.
- GD-199를 만들어 관리자 확인과 최초 수동 공개를 분리할 구현 범위를 기록했다. 아직 해당 기능은 구현하지 않았다.
- Jira GD-86·140 범위, GD-139·169 후속 관계, GD-131 검증 경계, GD-178 후속 작업·이관 기록을 갱신했다.
- 바탕화면의 작업 계획·워크트리 흐름 HTML 2개를 같은 계획으로 갱신했다. 구현용 워크트리와 세션은 시작하지 않았다.
- 스펙 변경은 [7b7fd5f](https://github.com/Uplus-GETDDO/getddo-spec/commit/7b7fd5f)로 main에 공유했다. 공용 정책과 ADR-022는 스펙이 원본이며 알림 담당 문서 두 파일은 요청 범위에서 제외했다.
- 백엔드 후속 문서 4개는 [PR #89](https://github.com/Uplus-GETDDO/getddo-be/pull/89)로 분리했다. 워크로그를 이 PR에 포함하지 않았다. 새 ADR은 제안 상태다.

### 최신 문서와 다른 담당자 PR 확인

- 원격 dev와 spec main을 확인하고 기존 로컬 변경을 보존한 상태로 최신 원격 기준에서 문서를 정리했다. 로컬 dev를 reset하거나 대규모 병합하지 않았다.
- GD-145 PR #83의 ACCEPTED 필터와 문서를 대조했다. GD-131 검증 계획에 정상 접수·차감 롤백과 별도 REJECTED 이력 보존을 구분하고 거절 건의 후보·집계 제외를 추가했다. 미병합 변경을 dev의 구현 완료로 기록하지 않았다.
- [이벤트 상태 변경 PR #84](https://github.com/Uplus-GETDDO/getddo-be/pull/84)의 fed7066 기준 코드·문서·리뷰를 확인했다. 이벤트 ID, 예상 상태, 변경 상태를 받아 잠금 후 변경하는 서비스이며 추첨 측에서 연결할 수 있다.
- 기존 리뷰의 실제 MySQL 검증, 미존재·삭제 이벤트 처리, 잠금 보유 검사와 테스트 실행 기록 불일치는 최신 코드·문서·PR 설명에 반영됐다. 추첨 연결을 위해 필수로 추가 요청할 기능은 확인되지 않았다.

## 고민과 판단

- 명단 확인과 공개는 별도 작업이어야 하므로 기존 확인 시 자동 공개 연결은 GD-199에서 분리한다. 공개 시간 카운트다운과 자동 공개 재호출은 이번 계획에서 제외했다.
- 마감 후 일정 시간을 기다리는 것으로 GD-131의 잠금·트랜잭션 검증을 대신하지 않는다.
- PR #84의 상태 변경은 추첨 서비스의 기존 트랜잭션에서 호출해야 한다. 이미 목표 상태가 된 작업을 재시도할 때는 추첨 측에서 중복 호출을 처리해야 한다. 예상 상태를 이전 값으로 그대로 전달하면 충돌한다.
