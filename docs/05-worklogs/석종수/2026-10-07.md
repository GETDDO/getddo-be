## 고민과 판단

- 요구사항으로 필요한 정합성 조건과 DB에서 강제하는 방법을 구분했다. 원본 연결·중복 방지·공개 구성·확인 이력 보존은 근거가 있는 요구이며 복합 FK·CHECK 등은 이를 구현하는 선택이다. 다른 행의 작업 유형·과거 버전·상태 전이·전체 명단 중복 등은 DBML에 서비스 트랜잭션 검증 계약으로 기록했다.
- 현재 티켓 상태는 갱신되지만 이력의 상태·만료 시각은 해당 처리 완료 당시 값으로 유지한다. 버전 UNIQUE만으로 버전 연속성이나 현재값과 마지막 이력의 일치를 보장할 수는 없다.
- 재추첨 실행·재개 처리자는 당첨 취소자 또는 결과 확인자로 대체할 수 없음을 확인했다. 상세 감사 기록 방식은 구현 전 후속 작업으로 남겼으며 이번 작업에서 구현하지 않았다. 별도 재추첨 사유 입력을 추가하지 않고 확정 스펙의 연결 취소 사유를 업무 근거로 사용하는 규칙을 따랐다.
- 정상 최초 추첨은 자동 공개하며 최초 공개 전 재추첨이 발생하면 관리자 확인이 끝난 새 결과와 유지 결과를 함께 공개한다. 저장 설계 보완을 실제 서비스 구현 완료로 표현하지 않았다.

## 확인 결과 / 막힌 점

- 7일 검토 시 공용 스펙 main `d42b795`에 `git pull --ff-only`를 실행했고 이미 최신 상태였다.
- DBML 보완 당시 공식 DBML v2 파싱·FK 참조 테이블/컬럼 검사·MySQL 내보내기가 성공했다. 최종 설계는 테이블 44개, UNIQUE 57개, FK 91개, CHECK 54개다. 이는 실제 MySQL 적용이나 ERDCloud 가져오기 성공을 의미하지 않는다.
- 사용자 요청에 따라 SQL 보존·삭제 커밋 단계의 추가 검증은 생략했다. README 충돌 해결 시 `git diff --check`는 통과했고 GitHub에서 PR의 `MERGEABLE` 상태를 확인했다. 당시 리뷰·필수 체크에 따른 병합 대기는 남아 있었다.
- 운영 코드·Flyway·공개 API를 새 ERD에 맞춰 변경하지 않았다. 문서·설계 작업으로 Gradle 테스트·빌드와 실제 MySQL·서비스 동시성 검증은 실행하지 않았다.
- 작성 시점인 8일에는 두 저장소 원격을 확인했다. BE 로컬은 `d7684bc`, 원격 작업 브랜치는 `bbc985e`이며 로컬 upstream이 없어 자동 pull하지 않았다. 따라서 이 기록은 세션에서 수행한 7일 작업을 기준으로 하며 원격의 후속 작업을 이 세션의 성과로 포함하지 않는다.
- 공용 스펙은 작성 시점에 `2a61380`으로 fast-forward 최신화했다. 회수 제외 정책이 구현 범위·도메인 문서에 반영된 것을 확인했다. 관련 ADR-017은 여전히 제안 상태다. 7일 DBML의 공용 스펙 갱신 대기 주석은 이후 정리가 필요하다.
