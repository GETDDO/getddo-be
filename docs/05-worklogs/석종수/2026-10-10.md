## 고민과 판단

- JPA 전환은 추첨 테이블 영속성에 한정했다. 다른 담당자의 원본 모델·응모 서비스·이벤트 잠금 순서를 바꾸지 않았고, 전환 자체를 위한 새 마이그레이션은 추가하지 않았다.
- DB의 응모별 티켓 UNIQUE만으로는 서로 다른 추가 응모에 같은 티켓이 기록되는 것을 막지 못한다. 이력이 각각 다른 ID·버전이면 두 번 합산될 수 있어 추첨 입력 검증에서 거절하도록 했다. 원본을 수정하거나 가중치를 임의 보정하지 않는다.
- 실제 응모 서비스는 현재 저장소에 없으며 `EventRegistrationService`는 관리자 이벤트 등록 서비스다. CodeRabbit에 근거를 설명했고, 이번 PR에 응모 서비스를 새로 구현하라는 요구는 철회됐다. SQL 기반 잠금 계약 검증과 실제 응모 서비스 연동 검증은 구분한다.
- 복합 기본키의 `@EqualsAndHashCode`는 두 UUID 값으로 같은 키를 판단하기 위해 사용한다. setter는 없지만 JPA가 필드를 초기화하므로 언어 수준의 완전한 불변 클래스라고 표현하지 않는다. 비교 필드를 명시하는 대안도 검토했으나 해당 어노테이션 변경은 적용하지 않았다.
- PMD의 ResultSet 반환값·JPA 콜백 경고는 실제 검사와 생명주기 호출을 확인해 오탐으로 판단했다. 일률적인 주석 커버리지 80% 경고는 프로젝트의 주석 개수 강제 금지·의도 설명 지침과 대조해 전체 메서드 주석 추가로 대응하지 않았다.
