## 오늘 한 일

- 41개 테이블의 통합 DBML을 현재 공용 명세, 백엔드 문서, B 영역 작업 기록과 대조했다. 기존 기록의 수정 요청을 현재 파일의 반영 여부와 구분해 다시 확인했다.
- 사용자에게 전달받은 UNIQUE 목록 중 빠져 있던 `attendance_streaks(users_id, streak_month)`와 `attendance_reward_claims(user_id, reward_type, source_key)`를 추가했다. 나머지는 동일한 제약 또는 더 넓은 범위의 `draw_runs.idempotency_key` 단독 UNIQUE로 중복이 차단돼 있었다.
- 사용자 선택에 따라 `event_entries`의 단독 `idempotency_key` UNIQUE를 9월 24일 기록의 `(event_id, user_id, idempotency_key)` 복합 UNIQUE로 변경했다.
- 9월 24일 기록에 있는 조건을 DBML에 명시했다. `event_entries`의 `OTHER` 거절 사유 필수 조건, `event_participants`의 허용·제외 상태별 코드·상세 사유·시각 조건을 `CHECK` 주석에 추가했다. `event_prizes`에는 `winner_count > 0` 주석과 이벤트별 등수를 1부터 빈 번호 없이 구성한다는 설명을 추가했다.
- DBML을 `docs/03-database/schema.dbml`로 저장하고 [DB 문서 목록](../../03-database/README.md)에 연결했다. 사용자 지시에 따라 커밋 [`97ed484`](https://github.com/GETDDO/getddo-be/commit/97ed484155f281f732c02d23b30b09480156563b)을 `origin/dev`에 직접 push했다. 바탕화면의 원본 파일은 그대로 두었다.

## 고민과 판단

- 응모 멱등 키는 같은 사용자의 같은 이벤트 요청 재시도를 구별하며, 새로운 추가 응모에는 새 키를 사용한다. 9월 24일 기록의 복합 범위와 당시 DBML의 전역 범위가 달랐고, 이번 대화에서 사용자가 복합 범위를 선택했다.
- `CHECK`와 생성 칼럼에 관한 DBML 주석은 MySQL DDL로 자동 적용되지 않는다. 이번 변경은 설계 파일의 명시이며 DB 제약이나 애플리케이션 처리 완료를 뜻하지 않는다.
- 공용 요구사항은 출석·보상 기준일과 월에 KST를 적용하고, 두 이벤트 유형의 최초 추첨·발표를 마감 후 5분에 자동으로 시작한다. 백엔드 담당 문서의 UTC 기준일·미사용 이벤트 수동 최초 추첨 문구와 DB 설계 초안의 UTC 기준일 문구는 현재 공용 명세와 다르다. 이번 작업에서 해당 문서는 수정하지 않았다.

## 확인 결과 / 막힌 점

- 작업 시작 시 `getddo-be`의 원격 `dev`와 `getddo-spec`의 원격 `main`이 각각 로컬 HEAD와 같은 커밋임을 확인했다. 백엔드 저장소에 기존 미추적 26일 작업로그가 있어 pull·stash·reset은 하지 않았다.
- 저장소의 DBML과 바탕화면 원본의 SHA-256이 모두 `49bbefdc47deef022c4fba84cc2f61d85da43f8386b27b5621b086a06dddfc48`로 일치했다. 테이블 수는 41개였고, 커밋 전 `git diff --cached --check`가 통과했다. push 후 로컬 `dev`는 `origin/dev`와 일치했다.
- SQL DDL 생성, 실제 DB 제약 검증, 동시성 테스트 및 애플리케이션 테스트·빌드는 실행하지 않았다. 이번에는 설계 문서만 변경했다.
- 추첨 후보·경품·결과·공개 명단의 이벤트·실행·사용자 일치, 스냅샷 고정, 응모 접수·차감과 당첨 취소·재추첨·공개 명단 갱신의 원자성은 DBML의 FK·UNIQUE·주석만으로 검증되지 않는다. 전체 스키마의 `attendances`에는 KST 출석 기준일과 사용자·기준일 UNIQUE가 없어 일일 출석 중복 방지 구현 시 확인이 필요하다.
