## 고민과 판단

- 먼저 사용 가능한 추첨 운영 흐름을 만들고 이후 어뷰징 기능을 연결하는 방향을 사용자가 제안했다. 진행 순서는 다음과 같이 정리했다.

```text
v1 우선 구현 제안
추첨 실행·결과 확정(GD-35)
→ 결과 발표·조회
→ 관리자 당첨 취소·재추첨·공개 명단 갱신

후속 구현 제안
어뷰징 탐지·요청 빈도 제한
→ 관리자 어뷰징 검토·참여 허용·추첨 대상 제외
→ 추첨·당첨 취소·응모권 회수 흐름 연동
```

- v1의 당첨 취소·재추첨도 관리자가 자격 미달·부정을 확인하고 사유를 기록하는 정책을 따른다. 자동 탐지가 없다는 이유로 임의 재추첨을 허용하지 않는다. 기존 당첨자는 유지하고 취소로 빈 자리만 보충한다.
- GD-35의 확정 제외 상태 반영 경계는 유지해 후속 관리자 검토 기능을 연결할 수 있게 한다. 실제 검토·제외 API와의 통합 검증은 후속 작업에 포함한다.
- 공용 요구사항에는 어뷰징 탐지와 요청 빈도 제한이 포함돼 있다. 후순위 개발 제안과 기능 제외를 구분하며, v1 출시 범위는 팀과 확인한 뒤 공용 명세 관리 규칙에 따라 반영한다.

## 확인 결과 / 막힌 점

- Jira 재조회에서 GD-35·56·84~87은 `할 일`, GD-36은 `완료`로 확인했다. GD-56은 구현·병합 상태와 Jira 상태를 대조해 완료 처리할 필요가 있다.
- GitHub 앱을 통해 공용 요구사항·구현 범위·미결정 사항, 백엔드 담당 분담 및 추첨 저장 설계의 원격 본문을 확인했다. 일부 호출은 통신 오류가 났으나 관련 문서는 재호출로 조회했다.
- 로컬 저장소는 미커밋 변경이 없는 detached HEAD 상태로 시작했다. `git ls-remote origin refs/heads/dev`는 GitHub DNS 오류로 실패했으며, 로컬 체크아웃이 최신 원격 커밋과 일치하는지는 확인하지 못했다. 추적 브랜치가 없어 pull하지 않았다.
- 이번 워크로그 작성은 문서만 변경한다. 애플리케이션 테스트·빌드는 실행하지 않고 문서 형식·링크·diff를 검증한다. 앞선 기능의 테스트 결과를 이번 실행 결과로 기록하지 않는다.
- 멘토링 진행 사실과 작업 중단·ERD 수정 필요 사항을 사용자에게 전달받았다. 구체적인 ERD 수정 항목과 멘토 답변은 아직 이 기록에 추가하지 않았다.
