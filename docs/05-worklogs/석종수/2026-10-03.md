## 오늘 한 일

- 사용자가 전달한 10월 2일 ERD 멘토링 정리와 추가 음성 전사 내용을 바탕으로 추첨 영역의 검토 방향을 논의했다. 정확한 용어가 불명확한 발언은 특정 개념으로 단정하지 않았다.
- 업무 데이터, 감사 이력, 진단 로그를 목적에 따라 구분했다. 스냅샷은 당시 값을 보존하는 방식이며 업무 데이터나 감사 이력에 포함될 수 있음을 정리했다.
- 현재 추첨 ERD·Flyway DDL·선정 서비스와 로컬 공용 추첨 규칙·API 초안을 확인했다. 멘토링 관점과 API 구현 관점에서 테이블·컬럼 수정 후보를 비교했다.
- 이번 작업은 읽기 전용 설계 검토와 워크로그 작성이다. 코드·ERD·마이그레이션·공용 정책은 변경하지 않았다.
- 사용자 요청으로 기획 설계 에픽 GD-1 아래에 GD-93을 등록하고 담당자를 석종수로 지정했다. 기존 설계 이슈의 완료 상태는 변경하지 않았다. 원격 `dev` 기준으로 `docs/GD-93`을 생성·전환하고 오늘 워크로그를 보존했다.

## 고민과 판단

- 테이블 수나 과거 기록 여부로 필요성을 판단하지 않는다. 각 행의 의미, 생성·변경 시점, 사용하는 API와 정합성 유지 방법을 확인한다. 업무·감사·진단의 구분이 반드시 별도 테이블 세 개를 뜻하지는 않는다.
- 실행별 후보·조건 스냅샷과 이전 선정 결과는 추첨 근거·정합성 검증·재추첨에 필요한 업무 데이터로 검토했다. 단순 로그로 옮길 대상으로 판단하지 않았다.
- 멘토링 관점에서는 `award_cancellations`의 결과 테이블 통합과 `current_awards`의 Query 대체 가능성을 검토했다. API 관점에서는 취소 건 ID·중복 재추첨 방지, 내부 확정 결과와 관리자 확인 후 공개 명단의 차이 때문에 별도 테이블을 유지할 근거도 확인했다. 어느 안도 확정하지 않았다.
- 컬럼 수정 후보는 다음과 같다. 실제 삭제·이동·분리는 사용처와 대체 설계를 확인한 뒤 결정한다.

| 대상 | 검토할 내용 |
| --- | --- |
| `draw_runs.original_draw_id` | 이전 실행 관계로 구할 수 있는 정보와 중복되는지, 최초 가중치 조회에 직접 참조가 필요한지 비교 |
| `draw_runs.last_failure_reason` | 재시도·운영 판단용 오류 요약과 상세 진단 로그의 경계 정의 |
| `draw_results.publication_status` | 공개 상태와 당첨 유효성을 나타내는 `EXCLUDED`가 섞인 의미 정리 |
| `current_awards`의 이벤트·사용자·경품·자리 컬럼 | 결과에서 유도 가능한 값과 중복되지만 DB 유일 제약에도 사용되므로 축소 시 대체 제약 확인 |
| `draw_candidates`의 JSON 스냅샷 | 당시 보존해야 할 항목과 불필요한 중복 항목 구분 |

- 처리자·시각·사유는 업무 근거이면서 감사 정보일 수 있으므로 감사 성격만으로 업무 테이블에서 제거하지 않는다.

## 확인 결과 / 막힌 점

- 로컬 ERD에는 추첨 실행, 후보 스냅샷, 선정 결과, 당첨 취소, 현재 공개 명단, 발표 상태와 공통 감사 로그가 구분되어 있다. 분류만을 이유로 전면 개편해야 한다는 결론은 내리지 않았다.
- 추첨 API 문서는 검토 대기 초안이다. AD04 검증 결과의 보관 여부, AD07 공개 명단 변경 이력의 감사 로그 저장·조회 형식, 취소·재추첨 중 사용자 표시 상태는 추가 확인이 필요하다.
- 백엔드와 `getddo-spec`의 작업 트리는 원격 확인 시 미커밋 변경이 없었다. 두 저장소의 `git ls-remote origin HEAD`는 `Could not resolve host: github.com`으로 실패했다. 백엔드 `feat/GD-56`에는 추적 브랜치도 없어 pull하지 않았으며, 로컬 자료의 원격 최신 여부는 확인하지 못했다.
- 브랜치 생성 단계에서는 GitHub 앱으로 원격 백엔드 `dev`의 커밋 `aecf9ac2f3d66628683f39c50a7e27b2bd1d8240`을 확인했고, 로컬 `origin/dev`와 일치했다. 이 커밋에서 GD-93 브랜치를 분기했다. 셸의 DNS 문제와 공용 명세의 원격 최신 여부 미확인은 별도로 남아 있다.
- 문서만 추가하므로 애플리케이션 테스트·빌드는 실행하지 않는다. 이 기록의 형식·참조 링크·diff를 검증한다.

## 다음 할 일

- 최초 추첨 → 최초 발표 → 당첨 취소 → 재추첨 확정 → 관리자 확인 → 공개 명단 갱신 흐름별로 테이블의 INSERT·UPDATE와 조회 근거를 정리한다.
- 수정 후보마다 유지안과 대체안을 비교하고, 중복 저장의 원본·갱신 시점·DB 제약을 명확히 한다.
- API 초안의 미확정 항목과 공용 감사 로그 연계는 관련 담당자와 확인한다. 공개 API·데이터 모델·공동 처리 경계 변경은 확인 후 진행한다.
- ERD 변경안을 확정하기 전까지 후속 추첨 저장 구현은 선행하지 않는다. 이번 기록을 확정 정책이나 스키마 변경 승인으로 사용하지 않는다.
