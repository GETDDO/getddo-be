- 실행의 요청자·사유는 연결된 당첨 취소 내역에서 조회하도록 중복 컬럼을 줄였다. 같은 실행 재시도와 새로운 재추첨의 행 단위를 구분했다.
- 동시 재추첨으로 같은 사용자가 중복 선정될 수 있는 위험을 검토하고, 후보 확정부터 결과 확정까지 이벤트별 처리 순서를 보장하는 서비스 계약 제안을 SQL 주석에 남겼다. DDL만으로 동시성이 보장된다고 표현하지 않았다.
- 이 기록의 ERD 관련 산출물은 위 SQL 한 파일로 한정한다. 운영 코드·Flyway 마이그레이션·공용 정책은 변경하지 않았다.

## 고민과 판단

- `draw_runs` 한 행은 추첨 실행 한 번이다. 최초 실행과 새로운 재추첨은 별도 행이며, 실패 재시도는 같은 실행을 사용한다.
- `draw_results` 한 행은 실행에서 처리한 경품 자리 하나의 선정 또는 미충원 사실이다. 재추첨은 취소된 자리의 새 결과를 추가하며 이전 확정 결과를 덮어쓰지 않는다.
- 후보·조건 스냅샷은 실제 선정과 검증·재추첨의 근거다. 과거 데이터라는 이유만으로 진단 로그로 분류하지 않는다.
- 공개 명단은 공개된 실행들의 결과를 조합한다. 전체 실행 중 최신 결과를 조회하면 비공개 재추첨 결과가 노출될 수 있으므로 공개 버전을 조회 기준으로 사용한다.
- 처리자·사유·시각에는 감사 역할이 있지만 업무에 필요한 기록일 수도 있다. 물리적으로 분리할 때 원본·조회 경로·트랜잭션 보장을 함께 정해야 한다.

### 워크로그 작성 이후 작업과 현재 중단 지점

- 여러 취소를 재추첨 하나에 묶는 구조를 검토했다. 별도 연결 테이블을 사용한 뒤, 현재 관계가 취소 여러 건과 실행 하나의 관계임을 확인해 취소 테이블에 FK를 두는 방식으로 단순화했다.
- 현재 SQL에는 `award_cancellations.draw_run_id`를 nullable FK로 추가하고 별도 연결 테이블을 제거했다. 취소를 먼저 저장할 때는 NULL, 재추첨 등록 시 실행 ID를 채우며 최초 연결 이후 변경·해제는 금지하도록 서비스 계약을 명시했다. 실행 ID에는 UNIQUE를 두지 않아 여러 취소가 같은 실행을 참조할 수 있다.
- 같은 이벤트인지, 연결 실행이 `REPLACEMENT`인지, 취소 묶음을 등록할 수 있는 준비 상태인지 서비스에서 검증한다. 실행 등록과 취소들의 FK 연결을 한 트랜잭션으로 처리하고, 동시 연결을 잠금으로 제어하는 제안을 주석에 기록했다. 실제 서비스 구현이나 DB 수준 불변 보장은 추가하지 않았다.
- 사용자 요청으로 미커밋 DBML·SQL 초안을 정리하고 문서 링크를 현재 SQL로 정리했다. 추적 중인 통합 스키마와 Flyway 마이그레이션은 보존했다.
- 현재 SQL은 추첨 7개·외부 참조 4개 테이블, 총 60개 한글 코멘트 컬럼·18개 FK다. `draw_runs`는 11개 컬럼이다. 취소 FK의 NULL 허용·비유일성, 별도 연결 테이블 제거, 다른 테이블 정의 유지 및 FK 참조 대상의 정적 검사를 통과했다. 실제 MySQL·ERDCloud·서비스 동시성 검증은 미실행이다.
- 다음 검토 대상은 `draw_candidates`다. 현재 구조는 실행의 유효 후보 한 명당 한 행이며, 유효 후보가 1만 명이면 1만 행이 생성된다. 재추첨 후보도 실행별로 기록한다. 전체 명단을 JSON으로 저장하면 행 수는 줄지만 후보 데이터 자체가 사라지는 것은 아님을 논의했다.
- JSON 대안은 후보별 검색·중복 검증·참조 정합성을 서비스에서 처리할 범위와, 현재 `draw_results.candidate_id` FK를 어떻게 대체할지 함께 검토해야 한다. 저장 방식은 미결정이며 성능 측정이나 JSON 전환은 하지 않았다. 이 지점에서 검토를 멈추고 내일 이어간다.
- 이번 워크로그 갱신에서도 두 저장소 원격 확인은 GitHub DNS 오류로 실패했다. 원격 최신 여부는 확인하지 못했고 기존 변경은 보존했다.
