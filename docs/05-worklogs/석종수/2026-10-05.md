## 오늘 한 일

- 후보별 행과 전체 후보 JSON 저장을 비교하고, 성능 검증은 후속으로 미룬 채 후보별 행 유지 검토를 마쳤다. 이후 최초·재추첨의 저장 흐름을 검토하면서, 최초 후보 정보를 재사용하고 실행별 후보 명단은 중간 테이블로 보관하는 방향을 선택했다.
- `draw_results`는 경품 자리별 선정·미충원 결과, `draw_publications`는 공개 버전과 반영 실행의 기록이라는 역할 차이를 검토했다. 공개 테이블의 유지·통합 여부는 이번에 확정하지 않았다.
- `draw_run_candidates`(추첨 실행별 후보)의 두 컬럼·복합 PK·FK와 결과 FK 변경 구조를 검토하고, 중간 테이블을 도입하기로 했다.
- 중간 테이블과 결과 FK 변경을 반영한 [ERDCloud 가져오기용 추첨 SQL](../../03-database/drawing-erd-reviewed-erdcloud.sql)을 작성했다. 처음에는 별도 파일로 작성한 뒤 기존 SQL 초안에 통합했으며, 운영 코드·Flyway는 변경하지 않았다. ERDCloud의 실제 반영 여부와 관계 설정은 가져오기용 SQL 작성과 별도로 확인한다.

## 고민과 판단

- 기존 초안은 재추첨 실행마다 후보 행과 두 JSON 스냅샷을 다시 저장한다. 응모자 10,000명 중 5명이 당첨되고 한 명의 당첨이 취소되면, 추가 제외자가 없는 재추첨 후보는 9,995명이다. 기존 방식에서는 최초 10,000행에 재추첨 후보 9,995행이 추가되며 응모 근거 등의 데이터도 반복 저장될 수 있다.
- 수만 행이라는 수량만으로 기존 구조가 잘못됐다고 판단하지 않았다. 저장 공간 추정은 설명용이며 실제 MySQL 성능·용량을 측정하지 않았다. 이번 선택 이유는 행 수 제거보다 최초 후보의 불변 상세 정보와 실행별 후보 소속을 분리해 스냅샷 중복을 줄이는 것이다.
- 전체 후보 JSON으로 합치면 개별 후보 참조와 중복 제약을 별도로 처리해야 한다. 후보별 행을 유지하면서 최초 후보를 재사용하면 기존 가중치·근거 조회 구조를 유지할 수 있다.
- 재추첨 후보는 최초 후보에서 해당 이벤트의 모든 실행에서 한 번이라도 당첨된 사용자와 이후 제외 확정자를 뺀다. 당첨 취소자도 제외되며, 이전 재추첨의 취소자 역시 기존 결과·취소 기록으로 확인할 수 있다. SELECTED 결과의 사용자 기준으로 제외하며 UNFILLED는 사용자 당첨 기록이 아니다.
- 조회만으로 재추첨 명단을 매번 계산하면 이후 당첨·제외 기록에 따라 같은 쿼리의 결과가 바뀐다. 실행별 중간 테이블은 실제 사용한 후보 명단을 고정하기 위해 둔다. 최초 추첨에도 같은 연결 구조를 사용한다.
- 중간 테이블에는 실행 ID와 최초 후보 ID만 저장한다. 당첨·취소·제외 사유를 다시 복사하는 것은 이번 선택에 포함하지 않는다. 기존 판단 기록의 보존·조회 가능성은 실제 구현 시 확인한다. 실행 당시 후보 명단과 최초 후보의 가중치·스냅샷은 연결로 보존한다.

### ERDCloud 작성 기준

| 테이블 / 컬럼 | 논리명 | 타입 | 제약 / 의미 |
| --- | --- | --- | --- |
| `draw_run_candidates` | 추첨 실행별 후보 | — | 실행 하나에 참여한 최초 후보 하나의 연결 |
| `draw_run_id` | 추첨 실행 ID | `BINARY(16)` | NOT NULL, 복합 PK 구성, FK → `draw_runs.id` |
| `candidate_id` | 최초 후보 ID | `BINARY(16)` | NOT NULL, 복합 PK 구성, FK → `draw_candidates.id` |

- PK는 `(draw_run_id, candidate_id)` 하나로 설정한다. 실행 내 같은 후보의 중복 등록을 DB에서 방지한다.
- `draw_candidates`의 기존 컬럼은 유지한다. `draw_run_id`는 최초 후보 정보 생성 실행을 의미하며, 상세 정보는 재추첨마다 새로 만들지 않는다. `(draw_run_id, participant_id)` UNIQUE는 최초 명단의 후보 중복을 방지한다. 테이블·컬럼 설명의 실행별 복사 및 재추첨 스냅샷 표현은 새 역할에 맞춰 갱신해야 한다.
- 기존 결과 FK `(candidate_id, draw_run_id) → draw_candidates(id, draw_run_id)`는 재추첨 실행과 최초 후보 생성 실행이 달라 새 구조에 맞지 않는다. `(draw_run_id, candidate_id) → draw_run_candidates(draw_run_id, candidate_id)`로 교체해 결과가 해당 실행의 후보만 참조하게 한다.
- `draw_results.draw_run_id → draw_runs.id`와 경품 FK, 기존 자리·후보 유일 제약은 유지한다. 결과의 `candidate_id`는 UNFILLED를 위해 NULL 허용을 유지한다. 후보와 선정 순서의 SELECTED·UNFILLED별 필수·NULL 조건도 유지한다.
- PK·FK만으로 명단 확정 후 추가·수정·삭제 금지나 이벤트 일치를 보장할 수는 없다. 서비스의 상태 검사·트랜잭션·잠금으로 명단 고정과 동시 실행을 제어하고, 후보의 원본 실행이 INITIAL인지 및 연결 실행과 같은 이벤트인지 검증한다. 같은 실행 재시도는 이미 고정한 명단을 사용한다.
- 같은 이벤트의 응모자 한 명에 대해 최초 후보 행이 중복 생성되지 않아야 사용자 중복 방지 의미도 유지된다. 최초 실행의 유일성과 후보 중복 제약을 함께 검증한다.

### ERD SQL 산출물 정리

- ERD용 SQL을 `drawing-erd-reviewed-erdcloud.sql` 한 파일로 통합하고 중간 테이블·결과 FK 변경을 반영했다. 요청에 따라 별도 후보 연결 SQL과 메인 ERD용 SQL 두 파일을 삭제하고 README·워크로그 링크를 정리했다. Flyway 마이그레이션과 통합 스키마 DBML은 변경하지 않았다.
- 제공된 메인 ERD 이미지를 확대해 중간 테이블 배치와 연결을 검토했다. 결과 테이블에 `draw_run_id2`, `candidate_id2`가 추가되고 기존 후보 직접 관계가 남아 있는 것을 확인했다. 기존 결과 컬럼을 중간 테이블의 복합 FK에 매핑하고 중복 컬럼·기존 후보 직접 FK를 제거해야 한다. 지정 SQL에는 중복 컬럼 없이 새 관계를 반영했다. 이미지로는 실제 복합 FK 설정·유일 제약까지 검증할 수 없어 ERDCloud 설정 또는 내보낸 DDL로 확인해야 한다.

## 확인 결과 / 막힌 점

- 현재 SQL의 후보·결과 정의와 복합 FK, 실행 직렬화·공개 조회 주석을 확인했다. 로컬 공용 추첨 규칙의 실행별 후보 보존과 최초 가중치 유지 규칙을 기준으로 설명했다. 기존 결과에서 후보·응모자·사용자를 찾는 경로는 새 구조에서도 유지된다.
- 두 저장소의 `git ls-remote origin HEAD`는 `Could not resolve host: github.com`으로 실패했다. 원격 최신 여부는 확인하지 못했다. 현재 브랜치의 기존 미추적 SQL 두 파일은 보존했고 pull·stash·reset하지 않았다.
- 통합한 추첨 SQL은 추첨 8개·외부 참조 4개 테이블과 20개 FK를 포함한다. 정적 검사에서 FK 참조 대상·컬럼 존재·열 수, 결과의 중간 테이블 복합 FK와 candidate_id NULL 허용을 확인했다. 실제 MySQL 실행·ERDCloud 가져오기·서비스 동작·성능 검증은 수행하지 않았다.
- 문서 형식·로컬 링크·공백 검사는 통과했다. 운영 코드 변경 없이 워크로그와 ERDCloud 가져오기용 DDL만 작성하므로 Gradle 테스트·빌드는 실행하지 않았다.
