## 고민과 판단

### 테이블별 ERD 변경

- `abuse_cases`: 원본 행위가 있으면 `event_entry_id`·`attendance_id`·`mission_submission_id`·`game_play_id` 중 하나만 채운다. 원본 기록이 없는 거절 요청은 네 FK를 모두 NULL로 두고 `request_id`, `evidence`로 추적한다. `review_status`의 `EXCLUDED`를 부정행위 확인을 뜻하는 `CONFIRMED`로 바꾸고 추첨 제외는 `event_participants`에서 나타낸다. `PENDING`의 검토자·시각·사유는 모두 NULL, 완료 상태에서는 모두 필수다.
- `event_entries`: 거절 건의 `participant_id`, `accepted_at`은 NULL이며 성공 건만 응모자에 연결한다. 모든 업무상 거절에 `rejection_code`를 남기고, 전용 코드가 없으면 `OTHER`와 기존 `rejection_reason`에 구체적인 사유를 기록한다. 예상 밖의 서버 오류는 업무상 거절과 구분한다. `requested_at`은 요청 수신, `processed_at`은 결과 기록 시각이며 성공 건의 `accepted_at=processed_at`으로 정했다. 실제 접수 성립과 마감 판정은 응모·차감 기록의 트랜잭션 커밋을 기준으로 한다.
- `event_participants`: `EXCLUDED`는 추첨 대상 제외를 뜻한다. 제외 사유·시각의 상태별 필수 조건을 명시한다. 여러 탐지 건을 연결하는 새 테이블은 만들지 않고 `exclusion_reason`과 `audit_logs`를 사용한다.
- `draw_runs`: 실패 후 재시도는 같은 행과 같은 `run_number`를 사용한다. 새 재추첨은 새 행·다음 차수를 사용하고 업무상 사유를 `reason`에 기록한다. `READY`부터 후보·규칙·알고리즘 입력을 고정하고 `snapshot_fixed_at`을 기록한다. 실패 시도 전체 이력 테이블 대신 `failure_count`(기본값 0), `last_failure_code`, `last_failure_reason`, `last_failed_at`을 추가한다. 성공 후에도 마지막 실패 요약을 유지한다.
- `draw_candidates`: 후보 입력 순서를 저장할 확정 근거가 없어 `input_order`를 삭제한다. `entry_snapshot`, `eligibility_snapshot`은 유지하며 구체적인 JSON 키는 구현 시 정한다. 응모권 미사용 후보는 `ticket_count=0`, `weight=1`로 기록한다. 이는 응모권 사용 이벤트의 가중치 계산식을 확정한 뜻이 아니다.
- `draw_results`: 후보가 부족한 자리도 `UNFILLED` 행으로 보존하고 `candidate_id`·`selection_order`·`publication_status`는 NULL로 둔다. `selection_order`는 해당 실행 전체에서 1부터 시작하는 실제 선정 순서다. `slot_number`는 경품별 자리 번호이며 재추첨은 취소된 기존 자리를 채운다. 당첨 취소 시 `publication_status=EXCLUDED`를 취소 기록과 함께 갱신한다. 여기서 `EXCLUDED`는 내부 취소 판정이며 관리자 확인 전 공개 명단은 기존 `current_awards`를 기준으로 유지한다.
- `event_prizes`: `prize_rank`는 1부터 빈 등수 없이 설정한다. 공용 요구사항의 동일 등수 한 종류 경품 규칙을 따르며 같은 경품의 당첨 인원은 `winner_count`로 나타낸다. 이벤트 시작 후 경품 정보 변경은 기존 이벤트 도메인 규칙에서 금지한다.
- `award_cancellations`: 취소와 대체 재추첨 실행을 함께 만들므로 `replacement_draw_id`를 NOT NULL로 바꾼다. 취소 한 건마다 대체 실행 한 건을 연결하고, 실행 실패 후에도 해당 실행을 재시도한다.
- `publications`: `published_at`은 예정 시각이 아닌 실제 최초 공개 시각(UTC)이다. 최초 발표는 이벤트당 한 행이며 관리자 확인 후 공개 명단이 바뀔 때 `revision`·`updated_by`·`updated_at`을 갱신한다. 변경 전후·처리자·시각·사유는 `audit_logs`에 남긴다.
- `current_awards`: 최초 자동 공개 또는 재추첨 결과에 대한 관리자 확인 시에만 공개 명단을 갱신한다. 확인 전 새 결과는 비공개다. 기존 행을 새 당첨 결과로 교체할 수 있으며 변경 이력은 감사 로그에 남긴다. 이번 변경에 개인정보 스냅샷 컬럼을 추가하지 않는다.

### 확정한 UNIQUE 제약 — 17개

괄호 안에 여러 컬럼이 있으면 조합 전체에 UNIQUE 하나를 건다.

| 테이블 | UNIQUE 컬럼 |
| --- | --- |
| `abuse_cases` | `(detection_key)` |
| `event_entries` | `(event_id, user_id, idempotency_key)` |
| `event_entries` | `(event_id, user_id, single_entry_guard)` |
| `event_participants` | `(event_id, user_id)` |
| `draw_runs` | `(event_id, run_number)` |
| `draw_runs` | `(idempotency_key)` |
| `draw_candidates` | `(draw_run_id, participant_id)` |
| `draw_results` | `(draw_run_id, event_prize_id, slot_number)` |
| `draw_results` | `(draw_run_id, candidate_id)` |
| `draw_results` | `(draw_run_id, selection_order)` |
| `event_prizes` | `(event_id, prize_rank)` |
| `award_cancellations` | `(draw_result_id)` |
| `award_cancellations` | `(replacement_draw_id)` |
| `publications` | `(event_id)` |
| `current_awards` | `(event_id, user_id)` |
| `current_awards` | `(event_prize_id, slot_number)` |
| `current_awards` | `(draw_result_id)` |

- `draw_runs.idempotency_key`는 단독 UNIQUE로 선택했으므로 새로운 추첨 실행 요청마다 전역에서 유일한 키를 발급하고, 동일 요청의 재시도에는 같은 키를 재사용한다.
- `event_entries.single_entry_guard`는 1회 제한 이벤트의 성공 응모만 1, 나머지는 NULL이다. `draw_results.candidate_id`와 `selection_order`는 `UNFILLED`일 때 NULL이다. 실제 DB에 제약을 적용할 때 NULL 처리 방식과 기존 중복 데이터를 확인한다.
- `award_cancellations.replacement_draw_id`의 UNIQUE는 취소 한 건당 대체 실행 한 건이라는 앞선 결정에서 도출했다. `draw_results.selection_order`, `current_awards.draw_result_id`의 UNIQUE는 원본 목록 재검토 후 사용자 답변으로 확정했다.

## 확인 결과 / 막힌 점

- 원본 DBML과 최신 `getddo-spec`의 응모·추첨·이벤트 규칙을 대조했으며 위 변경과 직접 충돌하는 확정 규칙은 찾지 못했다.
- FK와 UNIQUE만으로 서로 연결된 응모·후보·경품·결과·공개 명단이 같은 이벤트·사용자를 가리키는지, 재추첨에서 기존 당첨자를 제외하는지, 등수에 빈 번호가 없는지는 모두 보장되지 않는다. 해당 정합성 검증을 ERD 설명과 구현 단계에 반영해야 한다.
- 제외 결정에 사용한 여러 `abuse_cases` ID를 연결 테이블 없이 `audit_logs`의 어느 필드에 어떤 형식으로 기록할지는 사용자가 보류했다. 이 형식을 정하기 전에는 탐지 건별 제외 근거를 정확히 역추적할 수 있다고 주장하지 않는다.
- 응모권 사용 이벤트의 가중치 계산식·값 상한·추가 배율, 공개 명단 마스킹 세부 규칙과 개인정보 파기 후 근거 보존 방식은 공용 문서의 기존 후속 사항이다. `detection_type`·`rejection_code`의 구체적 코드 목록과 후보 JSON 필수 키도 이번 ERD 검토에서 확정하지 않았다.
- 두 저장소의 원격 상태를 확인하고 `git pull --ff-only`를 실행했으며 모두 이미 최신 상태였다. 문서만 수정했으므로 애플리케이션 테스트와 빌드는 실행하지 않았다.
