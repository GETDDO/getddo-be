## 고민과 판단

- 기존 Flyway 파일 수정은 사용자의 명시적인 초기 세팅 요청에 따른 예외다. 실제 DB 적용 이력은 확인하지 못했으며 적용된 DB의 업그레이드 SQL로 사용하지 않는다. 데이터 전환·삭제·Flyway repair는 수행하지 않았다.
- 이번 변경은 초기 DDL에 한정한다. 기존 지갑·원장 기반 Entity·Repository와 변경된 컬럼을 사용하는 기능 코드는 사용자가 확인한 후속 작업으로 남긴다. DBML의 서비스 검증 계약이나 미결정 사항을 임의로 구현하지 않았다.
- 번호 연속성은 Flyway의 기술적 동작으로 설명하고, 정수·세부 번호·타임스탬프 중 팀이 사용할 방식과 PR에서 최종 번호를 배정하는 절차는 합의가 필요한 제안으로 구분했다.
- 날짜별 워크로그 PR에는 워크로그만 포함하는 것이 기본 규칙이다. 2026-10-09 사용자가 DB README 변경까지 8일 워크로그 PR에 함께 포함하도록 명시적으로 요청해 이번 PR에는 두 문서를 함께 담는다.

## 확인 결과 / 막힌 점

- 초기 DDL 작업 전 원격을 확인하고 백엔드 `git fetch origin`을 수행했다. 당시 `docs/GD-93`은 upstream이 없고 `origin/dev`보다 7커밋 뒤였다. 관련 DBML·SQL은 원격과 차이가 없었다. 공용 명세 로컬 HEAD와 원격 main은 `2a613805`로 같았으며, 이 확인 단계에서는 pull·브랜치 변경·커밋·push를 하지 않았다.
- 로컬에 있는 `@dbml/core`로 현재 DBML을 MySQL SQL로 내보냈다. 정적 대조에서 모든 테이블·컬럼의 타입·NULL·기본값·PK·인덱스·CHECK·FK가 일치했고 MySQL 문법 파싱도 통과했다. 모든 FK의 참조 컬럼과 부모 PK/UNIQUE도 확인했다. 실제 MySQL 실행 성공을 의미하지 않는다.
- `MySqlMigrationTest`: 실제 MySQL 8.4에서 4개 테스트 모두 통과했다. V001~V011 적용·재실행·Flyway 검증, 44개 테이블, 주요 PK·UNIQUE, 출석 티켓의 브론즈 등급·지급 소유자 및 이력 버전 중복을 확인했다.
- 전체 `test`: API 109개, core 172개, storage:db 4개, 총 285개가 모두 통과했다.
- 전체 `build`: 실패했다. API 통합 테스트 33개 중 2개, storage:db 통합 테스트 86개 중 60개가 실패했다. 이벤트 등록은 기존 코드가 삭제된 `events.created_by`를 저장하려다 실패했다. 출석·응모권 통합 테스트는 기존 Entity가 사용하는 `ticket_ledger`가 없어 스키마 검증에서 컨텍스트 초기화에 실패했고, 후속 테스트는 컨텍스트 재시도 제한으로 실패했다. 마이그레이션 자체의 4개 테스트는 전체 실행에서도 통과했다.
- 실행 환경: 기본 Java가 없어 `/tmp/getddo-jdk21`과 캐시된 Gradle 9.7.1을 사용했다. wrapper 캐시의 읽기 전용 잠금 파일·샌드박스 네트워크 인터페이스 제한·Windows 경로의 파일 모드 설정 오류를 확인한 뒤, 기존 캐시 및 `/tmp` 산출물 경로로 `:storage:db:integrationTest --tests com.getddo.db.migration.MySqlMigrationTest`, `test build --continue`를 `--offline --no-daemon`으로 실행했다. 저장소의 빌드 설정은 변경하지 않았다.
- `git diff --check` 및 변경 문서의 로컬 링크 검증을 통과했다. 실제 대상 DB의 적용 이력은 검증용 빈 MySQL과 별개로 확인하지 못했다.
- 이후 사용자 요청으로 `5b789f7`을 커밋·push하고 `dev` 대상 PR #29에 `skip-review` 라벨을 적용했다. 추가 요청으로 `docs/GD-93`에 원격 `dev`를 충돌 없이 pull·병합해 `1c89f3b`를 만들었고, 이 병합 커밋은 push하지 않았다.
