## 오늘 한 일

- 제공된 전체 ERD SQL에서 티켓 영역을 검토하고, 기존 지갑·원장·출처 배분 중심 구조를 실제 응모권 한 장 중심으로 다시 설계했다.
- ERDCloud 가져오기용 SQL 초안을 작성·수정했다. 티켓 테이블은 `tickets`, `ticket_operations`, `ticket_operation_items`, `ticket_refunds`, `ticket_recoveries` 5개이며, 외부 참조 6개는 관계 설명용 축약 정의로 포함했다. 실제 DB 마이그레이션은 작성하지 않았다.
- 테이블·컬럼의 한국어 설명을 작성하고, 처리 유형의 지급 표현을 `GRANT`로 정리했다. 처리 대상 사용자와 실제 처리자인 `actor_id`를 구분하고 업무 처리 사유를 유지했다.
- `RETURNED`를 반환 후 사용 가능한 상태로 표현했다. 반환 상태와 별도로 원본 사용 상세와 반환 상세를 연결하는 `ticket_refunds`를 두어 반복 사용·반환을 추적하도록 수정했다.
- `idempotency_key`를 제거하고 보상 청구·개별 응모·원본 사용 상세의 UNIQUE로 중복을 방지하는 초안을 구성했다. 보상 청구 자체의 업무 UNIQUE도 함께 제안했다.
- 회수 결정과 실제 회수 이력을 분리했다. 원본 지급 건, 이전 결정, 결정 수량을 보존하고 하나의 결정에 여러 실제 회수 작업을 연결할 수 있도록 구성했다.
- 현재 지급·출석·조회 구현과 공용 스펙을 대조하고, 새 티켓 테이블을 전체 ERD에 통합할 때 영향을 받는 보상·응모·추첨·알림 연계를 검토했다. 사용자는 새 구조에 맞춰 API도 수정하는 방향을 제시했다.

## 고민과 판단

- 반환된 상태만으로는 어떤 사용을 되돌린 것인지 구분할 수 없어 원본 사용 상세 연결을 유지했다. 한 티켓에 반환 내역은 없거나 여러 건일 수 있고, 같은 사용 상세의 반환은 한 번만 허용하는 구조다.
- 회수 대상은 현재 잔여량만이 아니라 최초 지급 건이다. 이미 사용한 부정 지급분도 회수 결정을 보존하고, 제외에 따른 반환과 실제 회수를 같은 트랜잭션으로 처리하는 조건을 SQL 주석에 명시했다.
- FK·UNIQUE만으로 작업 유형, 사용자 일치, 결정 연결의 순환 금지, 처리 수량과 상태 전이를 모두 보장할 수는 없다. 서비스 검증과 잠금·트랜잭션 구현이 별도로 필요하다.
- 확정 스펙의 원본 연결 정정 이력이 새 초안에 빠져 있음을 확인했다. `CORRECTION`과 정정 대상 연결 보완을 제안했지만 SQL에는 아직 반영하지 않았다.
- 반환 진행·실패·재시도 조회를 유지한다면 성공 반환 연결과 처리 요청을 별도 테이블로 구분하는 방안을 제안했다. 해당 관리자 API는 초안이며, 테이블 추가는 결정하거나 구현하지 않았다. 실패 기록은 반환 트랜잭션의 롤백과 별도로 보존할 경로가 필요하다.
- 출석 등급, 반환 등급, 기존 무등급 티켓 전환, 차감 등급 선택은 공용 미결정 항목으로 남겨 두었다. SQL의 nullable 등급을 확정된 사용 정책으로 해석하지 않는다.

## 확인 결과 / 막힌 점

- 로컬 검토 기준은 BE `docs/GD-93`의 `40672ec`, 최종 공용 스펙 `main`의 `e9e8a71`이다. 검토 중 깨끗한 스펙 저장소를 `git pull --ff-only`로 최신화했다. 이후 원격 재확인은 두 저장소 모두 GitHub DNS 오류로 실패했으므로 마지막 검토 시점의 추가 원격 변경 여부는 확인하지 못했다. BE는 추적 브랜치가 없고 SQL 초안이 미추적 상태여서 pull하지 않았다.
- SQL 정적 검사에서 11개 테이블, 62개 컬럼, 21개 FK를 확인했다. 괄호·따옴표, 키·참조 컬럼, 참조 타입과 UNIQUE 대상, 컬럼 설명을 검사했다. 이는 실제 MySQL 실행이나 ERDCloud 가져오기 성공 검증이 아니다.
- 기존 43개 테이블에서 티켓 5개만 새 5개로 교체하고 외부 테이블의 전체 정의를 유지하는 정적 대조를 수행했다. 새 FK의 참조 대상 테이블은 모두 존재했다. 기존 전체 SQL에는 UNIQUE가 없고 FK도 2개뿐이므로 실제 Flyway의 외부 영역 제약과 추가 대조가 필요하다.
- 현재 `TicketGrantService`와 저장소는 기존 지갑·원장·배분 테이블에 의존하며 출석도 해당 지급 서비스를 호출한다. `TicketQueryRepositoryImpl`은 기존 원장의 지갑 ID·수량·처리 직후 잔액을 조회하므로 DB만 교체하면 기존 구현이 동작하지 않는다.
- 전체 통합 시 보상 청구의 업무 UNIQUE 병합, 게임·미션 1장 지급 검증, 실제 응모 장수와 등급 가중치의 분리, 추첨 후보 스냅샷의 등급·가중치 근거 보존, 기존 응모 요청 중복 방지 유지, 실제 회수량 기준 알림 연계가 필요함을 확인했다.
- ERDCloud 실제 가져오기와 MySQL 실행은 수행하지 않았다. Docker 실행은 환경의 입출력 오류로 사용할 수 없었고 MySQL 실행 환경도 확보하지 못했다. 서비스 동시성·롤백·월 경계 동작은 아직 실행 검증하지 않았다.
- 운영 코드·기존 Flyway·공개 API를 변경하지 않았다. SQL 초안과 문서 작업으로 진행했으며 `./gradlew test`, `./gradlew build`는 실행하지 않았다. 커밋·push는 수행하지 않았다.
