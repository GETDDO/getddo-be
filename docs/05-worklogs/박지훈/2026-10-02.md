- 기존 V001~V011, 테이블·컬럼, API·조회 SQL은 유지했다. BE의 DBML과 DB 문서에 인덱스를 표시했으며 공용 spec은 수정하지 않았다.
- 기존 마이그레이션 통합 테스트를 V011에서 이벤트·경품을 저장한 뒤 V012로 업그레이드하는 흐름으로 확장했다. 인덱스 컬럼 순서, 기존 데이터 유지, 검증과 재실행 시 추가 적용 없음까지 확인한다.
- 담당자 요청에 따라 공통 페이징·날짜 변환 메서드의 재사용 여부를 확인했다. 이벤트는 이미 `PageQuery`·`PageResult`와 `TimeProvider.toUtc()`를 사용한다. 확인한 로컬과 원격 dev에는 페이지 응답의 `map()`이나 날짜 문자열 검색 범위 변환을 대체할 공통 메서드가 없다.
- 후속 담당자 요청으로 관리자 검색의 날짜 경계 계산·UTC 변환을 `EventQueryService`로 옮겼다. API는 형식·실제 날짜 여부만 확인해 `LocalDate`를 담은 core의 `AdminEventQuery`를 전달한다. 서비스는 공통 `TimeProvider`로 UTC 조건을 만들고 범위를 검증한다. 요청·응답 DTO 변환은 API에 유지한다.
- 담당자 요청으로 이벤트 목록·건수·상세·경품 일괄 조회를 `EntityManager`의 네이티브 쿼리에서 `NamedParameterJdbcTemplate`으로 전환했다. 조회 SQL·공개 상태 판정·정렬·페이지 계약을 유지하고 `Tuple`·`addScalar`를 제거했다. 이벤트 등록의 JPA와 다른 담당 영역의 저장소는 변경하지 않았다.

## 고민과 판단

- 모든 목록에 적용되는 삭제 제외 조건과 생성 시각·ID 정렬을 지원하는 인덱스 하나를 추가했다. 상태·유형·기간·제목 검색의 조합별 인덱스를 일괄 추가하지 않았다.
- 날짜 문자열의 표현 형식은 API 책임으로 유지하고, KST 날짜 검색의 양끝 포함 정책과 유효 범위 검사는 조회 서비스에서 함께 관리하도록 정리했다. 기존 `EventQueryFilter`는 저장소에 전달할 UTC 검색 조건으로 유지한다. 새 입력은 불변 core 클래스이며 HTTP DTO가 아니다.
- 페이징 기본값·상한은 API 계약이고 실제 offset 계산과 응답 구조는 공통 모델을 재사용한다.
- JDBC 전환은 SQL 실행·결과 매핑 도구의 변경이며 SQL 자체를 없애거나 성능 향상을 보장하는 변경이 아니다. 기존 공통 `UuidBinary`를 재사용하고, 시간대가 없는 MySQL `DATETIME(6)`은 `LocalDateTime`으로 바인딩·조회한 뒤 UTC `Instant`로 명시적으로 해석한다. 경품은 페이지 ID로 한 번에 조회해 불변 결과에 결합한다.
