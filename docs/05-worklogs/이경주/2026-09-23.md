## 고민과 판단

- TimeProvider는 Spring 어노테이션이 없는 일반 Java 클래스로 유지했다. Spring에서 객체를 관리하는 설정은 api에 두고, core는 생성자로 Clock을 받아 단독으로 테스트할 수 있게 했다.
- 테스트에서 원하는 시각을 고정할 수 있도록 Clock을 주입한다. 날짜와 월은 전달받은 동일한 Instant에서 계산해, 계산 사이에 자정·월 경계를 넘는 문제를 피한다.
- `toUtc(LocalDateTime)`는 입력을 한국 시각으로 해석한다. 오프셋이 이미 있는 입력은 오프셋을 제거하지 않고 해당 값의 `toInstant()`를 사용하도록 Javadoc에 안내했다.
- Bean 간 의존성을 메서드 인자로 주입하므로 `@Configuration(proxyBeanMethods = false)`를 사용했다. 여기서 직접 호출이란 `TimeConfig`의 `clock()` 같은 `@Bean` 메서드를 호출하는 것이다. 서비스에서 주입받은 `TimeProvider`의 `now()`를 호출하는 것과 구분한다.

현재 Config는 다음처럼 Clock을 인자로 주입받는다. `new TimeProvider(clock)`은 전달받은 Clock으로 객체를 생성하는 것이며, `clock()` 메서드를 호출하는 코드가 아니다.

```java
@Bean
public TimeProvider timeProvider(Clock clock) {
    return new TimeProvider(clock);
}
```

서비스에서는 생성자로 주입받은 TimeProvider를 정상적으로 사용한다. 아래 호출에는 설정 클래스의 Bean 메서드 프록시가 필요하지 않다.

```java
Instant now = timeProvider.now();
LocalDate date = timeProvider.businessDate(now);
```

반대로 Config의 Bean 생성 코드에서 아래처럼 작성하면 `TimeConfig.clock()`을 직접 호출하게 된다.

```java
return new TimeProvider(clock());
```

Spring이 관리하는 Config에서 `proxyBeanMethods = true`이면 이런 Bean 메서드 호출을 가로채 컨테이너의 해당 Bean을 조회한다. `false`이면 일반 Java 메서드로 실행하므로, 직접 호출한 `clock()`은 테스트에서 선택한 고정 Clock 대신 시스템 Clock을 반환할 수 있다. 현재처럼 메서드 인자로 주입받으면 직접 호출이 없어 프록시를 생략할 수 있다. 옵션을 생략해 기본값 `true`로 두어도 현재 구현은 정상 동작하며, `false`에서도 Spring의 Bean 등록·싱글톤 관리·의존성 주입은 유지된다.

## 확인 결과 / 막힌 점

- 각 테스트를 먼저 작성하고 TimeProvider·TimeConfig가 아직 없어 컴파일이 실패하는 것을 확인했다. 구현 후 개별 테스트는 각각 10개·2개 모두 통과했다.
- `./gradlew test --no-daemon`: 기존 테스트를 포함한 전체 26개 통과, 실패·오류·건너뜀 0건. KST 자정·월말·연말·윤년, 나노초 정밀도, 다른 시간대의 Clock, Spring의 고정 Clock 주입을 검증했다.
- `./gradlew build --no-daemon`: 전체 빌드 성공. 직전 전체 테스트가 성공한 상태에서 테스트 태스크는 UP-TO-DATE였다.
- 독립 코드 리뷰에서 Critical·Important·Minor 지적사항이 없었다. core JAR의 `jdeps --list-deps` 결과는 `java.base`뿐이었고, 실행 JAR에 시간 설정·구현이 포함되며 시간 테스트 클래스는 포함되지 않는 것을 확인했다.
- 이후 Javadoc만 추가해 실행 코드가 그대로임을 확인하고 `./gradlew :core:javadoc :api:javadoc --no-daemon`을 실행했다. 문서 생성은 성공했으며, 기존 코드와 TimeConfig의 암시적 기본 생성자에 문서 누락 경고가 남았다. 주석 변경 후 전체 테스트는 재실행하지 않았다.
- 커밋 전 `git diff --cached --check`를 통과했다. 원격 CI 결과는 별도로 확인하지 않았다.
