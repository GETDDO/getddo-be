## 오늘 한 일

### GD-51 사용자 도메인과 조회 기반 구현

- [GD-51](https://ureca4.atlassian.net/browse/GD-51)에 User·역할·상태·멤버십 모델, 조회 Service와 Repository 인터페이스를 구현했다. Controller·HTTP DTO·사용자 헤더 처리는 [GD-52](https://ureca4.atlassian.net/browse/GD-52)로 구분했다.
- [UserService](../../../core/src/main/java/com/getddo/core/user/service/UserService.java)의 필수 조회는 `User findById(UUID)`로 정리했다. Repository는 `Optional<User>`를 반환하고, Service에서 null ID는 `USER-001`·400, 미등록 ID는 `USER-002`·401의 `UserException`으로 처리한다. DB 오류는 미등록 사용자 오류로 바꾸지 않는다.
- INACTIVE 상태와 null 멤버십은 조회한 값을 그대로 보존한다. 조회 Service에 로그인·필터·전역 권한 검사나 사용자 자격 판정을 추가하지 않았으며 시연 데이터 입력과 배포도 진행하지 않았다.
- 사용자가 지정한 `gm-be`의 Service·예외·enum·Entity·Mapper·Repository 구현을 읽고 작성 방식을 맞췄다. `UserException`·`UserErrorCode`를 `user/exception`에 두고, enum은 값만 선언했다. Lombok으로 생성자를 정리하고 MapStruct Spring Bean으로 Entity의 11개 필드를 User에 매핑한다.
- 사용자가 Flyway 미적용 상태와 기존 CREATE 수정 방향을 확인하여 [V001](../../../storage/db/src/main/resources/db/migration/user/V001__create_user_tables.sql)의 회원 멤버십을 대문자로 변경했다. `@Enumerated(EnumType.STRING)`으로 매핑하고 필요 없어진 Converter와 전용 테스트를 제거했다. [DBML](../../03-database/schema.dbml)도 회원 컬럼에 맞췄다.

## 고민과 판단

- 미등록 예외는 조회 결과가 필수인지 판단하는 Service에서 처리하고, Repository의 Optional 계약은 유지했다. 참고 저장소의 404와 달리 이 프로젝트의 미등록 401은 사용자 확인에 따라 유지했다.
- 실제 테이블은 `users`이므로 `@Table(name = "users")`는 유지했다.
- 회원 멤버십의 DB 값과 enum 이름을 일치시켜 Converter를 제거했다. 이벤트의 별도 소문자 멤버십 컬럼은 수정하지 않았고, 알림 저장소에서 사용하는 소문자 비교 조건이 변경된 회원 테이블에서도 동작하는지 MySQL로 검증했다.
- Service와 영속성 구현을 서로 다른 커밋으로 나누면 중간 상태에서 Repository 빈이 없어 앱 기동이 깨지므로 같은 기능 커밋에 묶었다. 스키마와 매핑, 해당 테스트도 함께 포함했다.
- PR 제목 검사에서 Bash의 공백 분류로 전각 공백만 있는 설명이 통과하는 문제를 발견했다. Python의 유니코드 정규식 검사로 바꾸고 서로 다른 locale에서 재검증했다.
