- `UserException`·`UserErrorCode`를 `user/exception`에 두고, enum은 값만 선언했다. Lombok으로 생성자를 정리하고 MapStruct Spring Bean으로 Entity의 11개 필드를 User에 매핑한다.
- 사용자가 Flyway 미적용 상태와 기존 CREATE 수정 방향을 확인하여 [V001](../../../storage/db/src/main/resources/db/migration/user/V001__create_user_tables.sql)의 회원 멤버십을 대문자로 변경했다. `@Enumerated(EnumType.STRING)`으로 매핑하고 필요 없어진 Converter와 전용 테스트를 제거했다. [DBML](../../03-database/schema.dbml)도 회원 컬럼에 맞췄다.

## 고민과 판단

- 미등록 예외는 조회 결과가 필수인지 판단하는 Service에서 처리하고, Repository의 Optional 계약은 유지했다. 미등록 사용자의 401 응답은 사용자 확인에 따라 유지했다.
- 실제 테이블은 `users`이므로 `@Table(name = "users")`는 유지했다.
- 회원 멤버십의 DB 값과 enum 이름을 일치시켜 Converter를 제거했다. 이벤트의 별도 소문자 멤버십 컬럼은 수정하지 않았고, 알림 저장소에서 사용하는 소문자 비교 조건이 변경된 회원 테이블에서도 동작하는지 MySQL로 검증했다.
- Service와 영속성 구현을 서로 다른 커밋으로 나누면 중간 상태에서 Repository 빈이 없어 앱 기동이 깨지므로 같은 기능 커밋에 묶었다. 스키마와 매핑, 해당 테스트도 함께 포함했다.
- PR 제목 검사에서 Bash의 공백 분류로 전각 공백만 있는 설명이 통과하는 문제를 발견했다. Python의 유니코드 정규식 검사로 바꾸고 서로 다른 locale에서 재검증했다.

### 고민과 판단

- 필요한 사용자 파라미터만 처리하는 MVC Resolver를 사용했다. 로그인·필터·인터셉터·토큰 발급은 추가하지 않았다.
- 헤더는 DB 값과 대조하는 시연용 입력이다. 호출자의 신원 인증을 제공하지 않으며, 전역 사용자 저장소도 두지 않는다. Resolver는 INACTIVE 상태를 보존하고 업무별 자격 판단은 해당 Service가 수행한다.
- 공통 오류를 분리할 때 외부 응답 값은 유지했다. core가 api를 참조하지 않도록 HTTP 헤더 오류는 API 공통 계층에, 업무 오류는 해당 도메인에 배치했다.
- 기존 알림 API 연결에 따라 역할 헤더와 USER의 멤버십이 필수가 되고 사용자 문맥 오류는 공통 `USER-*` 코드로 바뀐다. 프론트엔드 호출과 공용 명세를 맞추는 후속 작업이 필요하다. 공용 명세의 확정 상태는 이 일지에서 변경하지 않는다.
- WSL의 E: 드라이브 I/O 오류 당시 Windows 원본과 Docker가 동작함을 확인했다. 동일 기준의 임시 작업본에서 구현한 뒤 Windows Git의 apply 검증을 거쳐 원본에 반영했고, 최종 테스트는 원본에서 실행했다. GD-52에서 DB 스키마·실제 데이터·배포 설정을 변경하지 않았다.
