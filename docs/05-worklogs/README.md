# 백엔드 작업 일지

각자가 작업한 날의 진행 상황, 고민, 확인 결과와 다음 할 일을 기록합니다. 한 사람이 자신의 작업 흐름을 돌아보고, 팀원이 필요한 도움과 맥락을 파악할 수 있도록 짧게 작성합니다.

## 폴더 구조

```text
05-worklogs/
├── README.md
├── 2026-09-21-reward-tables.md  기존 작업별 기록
├── 박지훈/
├── 석종수/
├── 윤태형/
├── 이경주/
└── 전민규/
```

폴더명은 성을 포함한 본인의 이름으로 통일하고, 사전순으로 안내합니다. GitHub ID, 별명, AI 도구 이름은 담당자 폴더명으로 사용하지 않습니다. 일지는 각 폴더 안에 `YYYY-MM-DD.md`로 작성합니다. 빈 폴더의 `.gitkeep`은 첫 일지를 추가할 때 제거합니다.

## 작성 방법

1. [일지 양식](../templates/worklog.md)을 복사해 `성명/YYYY-MM-DD.md`를 만듭니다. 작업한 날 하루 한 파일을 사용하고, 같은 날짜의 파일이 있으면 이어서 작성합니다.
2. 오늘 한 일, 고민과 판단, 확인 결과·막힌 점, 다음 할 일을 정리합니다. 3~5분 안에 작성할 수 있는 분량을 목표로 하며, 고민과 판단은 내용이 있을 때만 남깁니다.
3. 같은 날 여러 작업을 했다면 항목이나 소제목으로 구분하고, 관련 이슈·PR을 연결합니다. 공동 작업은 각자 맡은 부분과 관점을 기록하고 같은 이슈·PR을 참조합니다.
4. 실제로 실행한 검증과 결과를 적고, 미실행·실패·미확인을 구분합니다. 도움이 필요한 문제는 요청 대상과 내용을 적고 바로 공유합니다.
5. AI 초안에는 도구명과 `담당자 확인 전`을 표시합니다. 담당자가 확인한 뒤 표시를 갱신하고, 확인되지 않은 내용을 완료로 바꾸지 않습니다.

작업의 현재 상태는 이슈에서 관리합니다. 백엔드 확정 설계는 해당 설계 문서에, 중요한 기술적 결정과 이유는 [ADR](../04-decisions/README.md)에 남기고 일지에서 연결합니다. 공용 요구사항과 도메인 정책은 아래 관리 범위에 따라 공용 명세에서 관리합니다.

일지는 아래 일일 공용 브랜치와 PR로 공유합니다. 별도의 작업 보고서나 수동 일지 목록을 중복 작성할 필요는 없습니다.

## 브랜치와 PR 운영

백엔드 워크로그는 일반 작업 브랜치의 `docs/<Jira 이슈 키>` 형식 대신 날짜별 `docs/YYYY-MM-DD` 브랜치를 사용합니다. 필요한 경우 `docs/YYYY-MM-DD-설명`처럼 접미사를 붙일 수 있습니다. 예를 들어 `docs/2026-10-10`, `docs/2026-10-10-worklog`가 가능합니다. 접미사는 비어 있지 않아야 하며 공백·슬래시를 포함하거나 하이픈으로 시작할 수 없습니다. 날짜는 실제 달력 날짜여야 합니다.

이 형식의 브랜치에서는 PR 제목을 `[docs] 작업 설명`으로 작성할 수 있으며 Jira 이슈 키는 선택입니다. 예: `[docs] 2026-10-10 공용 워크로그`. 기존 `[docs] GD-93 작업 설명` 형식도 사용할 수 있습니다. 일반 작업 브랜치에는 기존 `[타입] GD-번호 작업 설명` 규칙을 그대로 적용합니다. 제목 검사의 예외 여부는 브랜치명으로 판단하며 변경 파일 경로는 검사하지 않습니다.

1. `dev`에서 해당 날짜의 브랜치를 하나 만들고, 팀원 5명이 같은 브랜치를 함께 사용합니다. 이미 브랜치가 있으면 기존 브랜치에서 작업합니다.
2. 각자 공용 브랜치의 최신 변경을 반영한 뒤 본인의 당일 워크로그를 작성하고 커밋·push합니다.
3. 당일 작업을 가장 먼저 끝낸 사람이 `dev` 대상 PR을 열고, CodeRabbit 자동 리뷰가 생성되지 않도록 `skip-review` 라벨을 추가합니다.
4. 나머지 팀원도 같은 브랜치에 워크로그를 업데이트하여 기존 PR에 반영합니다. 사람별로 별도 PR을 만들지 않습니다.
5. 당일 작업을 마지막으로 끝낸 사람이 자신의 워크로그를 업데이트하고, 팀원들의 당일 기록이 모두 반영됐는지 확인한 뒤 기존 PR을 `dev`에 병합하여 마무리합니다.

이 브랜치와 PR에서는 워크로그만 변경합니다. 기능 코드나 다른 문서 변경은 별도 작업 브랜치와 PR에서 처리합니다. `skip-review`는 CodeRabbit 자동 리뷰를 제외하기 위한 라벨이며, 기존의 팀원 리뷰와 CI 병합 요건은 유지합니다.

## 관리 범위

- 백엔드 기능 구현 과정
- 내부 아키텍처와 코드 구조
- 데이터베이스와 API 구현 세부사항
- 테스트, 성능, 빌드, 배포와 장애 대응
- 백엔드에만 적용되는 기술적 선택과 후속 작업

## 관리하지 않는 내용

- 공용 요구사항
- 도메인 정책과 용어
- 프론트엔드와 백엔드가 함께 사용하는 공용 문서와 협업 규칙

공용 문서와 요구사항에 관한 작업은 [getddo-spec의 `04-worklogs`](https://github.com/GETDDO/getddo-spec/tree/main/04-worklogs)에 기록합니다.
