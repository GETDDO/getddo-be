## 고민과 판단

- 사용자 문맥 공통 처리는 이경주 담당 영역이다. 현재 알림 코드에서 헤더 해석과 사용자·멤버십 확인을 구현했지만, 담당자 간 경계 합의가 확인된 상태로 기록하지 않는다. 공통 처리와의 통합 범위는 명시적으로 확인해야 한다.
- 공통 API 초안과 다시 대조해 UUID 형식 오류를 400으로, 선택적 멤버십의 DB 불일치를 409로 수정했다.
- `getddo-spec/05-api`의 경로·응답·오류 코드는 담당자 확인 전 초안이다. 현재 N01~N03 초안을 구현 기준으로 사용했으며, 확정 계약으로 기록하지 않는다.
- MySQL의 `notifications` 초기 테이블을 그대로 사용했다. 기존 Flyway 마이그레이션은 수정하지 않았다.
- 공통 API 초안 재대조 후 UUID 형식·멤버십 오류와 목록 응답 직렬화 검증을 보강하고, 신규 코드의 공개 책임과 읽음 처리 이유를 Javadoc으로 설명했다.
- 작성 규칙 재검토에서 `rudwnlee2`의 공통 시간·응답·오류·Entity 구현을 기준으로 비교했다. 입력·반환값·실패 조건 JavaDoc을 보강하고, 신규 테스트에 한국어 `@DisplayName`과 `given / when / then` 구분을 적용했다.
- Controller 내부의 읽음 응답 record를 `dto/response`의 `NotificationReadResponse`, `NotificationReadAllResponse`로 이동했다. HTTP 경로와 JSON 필드는 유지했다.
- 알림 Entity의 ID·생성 시각은 채택된 `BaseEntity`를 재사용하고, Entity→도메인 변환은 `NotificationMapper`에 배치했다. 기존 SQL과 사용자 공통 코드는 변경하지 않았다.
