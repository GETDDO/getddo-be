## 고민과 판단

- 공용 정책은 `getddo-spec` 원격 `main`의 `ed8b69e` 기준으로 확인했다. 시작 10분 전 1회 알림과 최소 멤버십 이상의 사용자 대상 규칙을 참고했다.
- 사용자가 이벤트·사용자 담당 코드를 변경하지 않는 연결 방식, 놓친 알림은 시작 전까지만 신규 등록하는 기준, 활성 일반 사용자 대상 기준을 확인했다. 공용 spec을 이번 작업에서 변경하지 않았다.
- 기존 이벤트 시작 시각을 예약 기준으로 사용해 별도 예약 테이블을 만들지 않았다. 이벤트 행 잠금과 작업 등록을 묶고 기존 작업·발생 키를 확인해 중복을 막는다.
- 수신자는 이벤트 등록 때 고정하지 않고 알림 생산자가 실제 실행되는 시점에 조회한다. 이후 사용자별 저장과 재시도에서는 최초 목록을 유지한다.

## 확인 결과 / 막힌 점

- `git diff --check`와 이번 작업의 신규·수정 파일 10개에 대한 줄 끝 공백·마지막 개행 검사를 통과했다. 이는 실행 검증이 아니다.
- 사용자의 테스트 직접 실행 요청에 따라 테스트·빌드는 실행하지 않았다. 작성된 테스트의 성공 여부는 미확인이다.
- 작업 등록과 사용자별 저장은 별도 단계다. 적체가 있으면 알림이 늦어질 수 있고, 이미 등록한 작업은 시작 시각 이후에도 기존 재시도 흐름으로 처리한다.
- 후보 조회 전용 이벤트 인덱스는 추가하지 않았다. 데이터가 많을 때 조회 비용과 잠금 범위는 성능 검증이 필요하다.
- 기존 사용자 변경인 `docs/03-database/README.md`는 유지했다. 초기 구현 `066d0e6`을 커밋·push하고 [PR #37](https://github.com/GETDDO/getddo-be/pull/37)을 생성했다.
- 초기 구현의 [GitHub Actions 빌드·테스트](https://github.com/GETDDO/getddo-be/actions/runs/37901254903)는 통과했다. 로컬 테스트·빌드는 실행하지 않았다.
- 코드레빗의 중복 보장 설명 요청에 따라 이벤트 잠금은 동시 처리를 줄이는 장치이며 최종 중복 방지는 발생 키 UNIQUE·멱등 등록이 담당함을 주석과 런북에 명시했다. 동시 폴링 테스트는 동일 입력 재등록의 반환값 조합을 제한하지 않고 최종 작업 행 1개를 검증한다. 이 후속 변경의 실행 결과는 아직 미확인이다.
