### 오늘 한 일

- 사용자가 내부 서비스 등록 방식과 생성·모의 발송 각각 최초 1회＋10초·30초·60초 재시도 3회, 일시적 오류만 자동 재시도하는 기준을 확인했다.
- `NotificationJobService`·`NotificationJobRepository`에 작업 등록·선점·사용자별 생성·실패·모의 발송 처리를 추가했다. 요청 수신자 목록은 중복·순서를 정규화하고 DB에 저장해 재시도에 재사용한다.
- 같은 발생 키·다른 입력은 전용 ErrorCode와 Exception으로 거절한다. 생성·발송의 읽음 상태는 변경하지 않는다. 새 enum은 별도 파일에 두고 core의 반복 getter·생성자는 Lombok을 사용했다.
- 원본 업무와 작업 등록은 같은 트랜잭션에 참여하며, 비동기 처리와 실패 기록은 별도 트랜잭션으로 확정한다. 이미 저장한 사용자 알림은 유지한다.
- 기존 UNIQUE와 MySQL 행 잠금·SKIP LOCKED를 재사용했다. 선점 차수와 60초 제한으로 장애 후 복구와 이전 처리자의 늦은 저장을 방지한다.
- `NotificationWorker`를 추가했다. 기본 1초마다 생성·발송 각각 최대 20건을 처리하고 운영 속성으로 중지·조회 주기 조정이 가능하다. 기존 YAML·공개 API·다른 담당자의 업무 코드는 변경하지 않았다.
- 새 V014에 조회 인덱스 3개를 추가했다. 과거 제거된 V012·V013의 버전 번호를 재사용하지 않았으며 기존 마이그레이션은 수정하지 않았다.
- [알림 작업 runbook](../../06-runbook/notification-worker.md), README와 스키마 대응 문서를 갱신했다. 공용 정책은 spec 링크를 기준으로 유지했다.
- 바탕화면 `프로젝트 설명용/알림/알림-생성-비동기-GD68.md`에 파일별 역할·처리 흐름·중복 방지·재시도·검증 결과를 기록하고 기존 알림함 설명 문서에 참고 링크를 추가했다.

### 고민과 판단

- 새 브로커·Spring Batch·변환 Mapper를 추가하지 않았다. 기존 DB와 스케줄러로 작업을 복구할 수 있으며, 실제 외부 발송은 제외 범위다.
- 등록 payload의 JSON 문구는 MySQL `JSON_OBJECT`로 이스케이프한다. 배열에는 입력 검증한 UUID 문자열만 전달해 새 JSON 직렬화 의존성이 필요하지 않다. JDBC 저장의 UUID v7 생성은 기존 BaseEntity와 같은 Hibernate 생성기를 재사용했다.
- 사용자별 생성과 진행 위치는 함께 저장한다. 생성 중 실패해도 이전 사용자 알림을 되돌리지 않으며 재처리는 UNIQUE의 no-op INSERT로 기존 ID·읽음·발송 결과를 보존한다.
- 모의 발송에는 기존 `next_delivery_attempt_at`을 처리 제한 시각으로도 사용했다. 현재 상태와 차수를 함께 검사하며 새 스키마 컬럼은 추가하지 않았다.
