- GD-70 일정 변경·취소 알림 구현을 진행했다. 기존 시작 작업의 남은 생성을 중지하고, 이미 시작 알림이 생성된 사용자에게 별도 안내 작업을 등록하는 서비스·저장소와 테스트 코드를 작성 중이다. 현재 미커밋 상태이며 실제 이벤트 수정·취소 업무의 호출 연결은 남아 있다.
- 팀원 [출석 보정 PR #44](https://github.com/GETDDO/getddo-be/pull/44), [추첨 결과 저장 PR #46](https://github.com/GETDDO/getddo-be/pull/46), [이벤트 조회 GD-59 / PR #16](https://github.com/GETDDO/getddo-be/pull/16)을 검토했다. 공통계약, 접근자 이름, 어노테이션과 코드 책임 배치를 비교하고 리뷰 의견을 정리했다. GitHub에 리뷰를 직접 등록하지는 않았다.

## 고민과 판단

- DB의 같은 행인지 확인하는 ID 비교와 요청 내용이 같은지 확인하는 값 비교는 목적이 다르다. 알림 중복 요청 검사는 발생 키뿐 아니라 전체 입력의 동일성도 유지해야 한다.
- 코드 리뷰에서는 확정된 계약 위반, 확인이 필요한 정책, 읽기 쉽게 만드는 개선 제안을 구분했다. 명시적 생성자나 getter가 있다는 이유만으로 Lombok 사용을 강제하지 않았다.
- GD-59의 `NO_ELIGIBLE_ENTRANTS` 조회 테스트는 신규 전원 제외 종료를 사용하지 않는 최신 정책과 대조했다. 과거 데이터 조회 호환성은 별도 검토 사항이므로 바로 삭제할 오류로 단정하지 않고 담당자 확인 항목으로 남겼다. 기준은 [이벤트 API 명세](https://github.com/GETDDO/getddo-spec/blob/853343889589cebbbea9b18e3f968603ddd766fa/05-api/event.md#L22)다.
- GD-70은 알림 서비스 구현과 이벤트 담당자의 실제 호출 연결을 구분한다. 변경 ID와 최초 입력 보존, 이벤트 수정·취소·반환과 같은 트랜잭션에서 호출하는 경계는 연결 전에 확인해야 한다.
