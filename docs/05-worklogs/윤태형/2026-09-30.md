## 고민과 판단

- **멱등키는 `GRANT:{type}:{claimId}`이고 지갑 ID를 넣지 않았다.** 지갑은 지급 시각의 KST 월로 정해진다. 월 경계에서 같은 청구가 재처리되면 다른 지갑이 선택되어 키가 달라지고 이중 지급이 가능해진다.
- **지갑은 비관적 잠금으로 갱신하고 `version`을 서비스가 직접 올린다.** `@Version` 낙관적 잠금은 충돌 시 호출자 트랜잭션 전체를 롤백시킨다. 지갑이 없을 때는 `INSERT ... ON DUPLICATE KEY UPDATE`로 먼저 만든 뒤 `FOR UPDATE`로 잠근다. `FOR UPDATE`를 먼저 하면 없는 행의 갭 락을 두 트랜잭션이 함께 잡았다가 둘 다 INSERT하는 교착이 생긴다.
- **`grant`는 `Propagation.MANDATORY`로 선언했다.** 청구 INSERT와 원장 GRANT가 한 트랜잭션이어야 미션 수행 기록과 지급 결과가 일치한다. 청구 UNIQUE 위반은 청구 저장이나 `grant` 호출 중 어디서든 나올 수 있고, 어느 쪽이든 호출자가 트랜잭션 전체를 롤백한 뒤 새 트랜잭션에서 다시 처리한다.
- **응모권 Entity는 `BaseEntity`를 상속하지 않았다.** `AuditingEntityListener`가 영속화 시점의 시각으로 `created_at`을 덮어써서, KST 월 경계 직전에는 만료 시각을 계산한 `grantedAt`과 어긋날 수 있다. 한 번의 지급에서 만드는 모든 행이 같은 `grantedAt`을 쓰도록 이 예외를 응모권 Entity에 한정했다. 공통 `BaseEntity`는 수정하지 않았다.
- **잠그지 않은 지갑의 갱신을 막는 방식이 한 번 실패했다.** 처음에는 `getLockMode`가 `PESSIMISTIC_WRITE`인지로 검사했다. Hibernate가 UPDATE를 flush한 뒤 잠금 모드를 `WRITE`로 바꿔서, 한 트랜잭션에서 같은 지갑에 두 번 지급하는 정상 흐름이 거절됐다. 트랜잭션 리소스에 잠근 지갑 ID를 기록하는 `LockedWallets`로 바꿨고, 이전 트랜잭션에서 잠근 지갑과 `REQUIRES_NEW` 안쪽 트랜잭션의 갱신을 거절하는 테스트를 추가했다.
- **지급 시각을 마이크로초로 자른다(GD-46 리뷰에서 발견).** `DATETIME(6)`은 마이크로초 아래를 반올림해 저장한다. 나노초 시계로 확인하니 `grant` 응답의 `grantedAt`과 `findGrant`·DB 값이 달랐고, `2026-09-30T14:59:59.9999996Z` 지급은 9월 지갑에 들어가면서 원장 생성 시각이 만료 시각인 10/1 00:00 KST로 저장됐다. `truncatedTo(MICROS)`로 고치고 회귀 테스트 2건을 추가했다.
- **T01 지갑 상태는 저장값이 아니라 조회 시각 기준이다.** 만료 배치가 늦어져도 만료된 잔액을 사용 가능으로 보여 주지 않는다는 API 명세 때문이다.
- **T02 커서의 동점 처리.** 같은 트랜잭션의 지급은 생성 시각이 같을 수 있어 `id`로 순서를 고정했다. InnoDB 보조 인덱스 `(user_id, created_at)`에 기본 키가 붙어 있어 이 정렬도 인덱스 순서로 처리된다.
- **변경을 성격별 커밋 4개로 나눴다.** 오류 코드 이동, record 제거, 조회 구현, 지급 시각 수정이다. 중간 커밋 3개도 각각 컴파일과 core 단위 테스트가 통과하는 것을 임시 worktree에서 확인했다.

## 확인 결과 / 막힌 점

- `./gradlew build --rerun-tasks`가 `origin/dev`(1bc0ce8) 병합 뒤에 통과했다. core 51, api 단위 13, api 통합 3, `storage:db` 통합 31개가 실패 0, 건너뜀 0이다. 통합 테스트는 `mysql:8.4` 컨테이너로 실행했다.
- 동시성 테스트: 지갑이 있을 때 다른 청구 2건은 잔액이 합산되고 `version`이 겹치지 않는다. 지갑이 없을 때 8건을 한꺼번에 시작해도 지갑 1개, 잔액 8, `version` 1~8이 이어지고 교착이 없었다. 같은 청구 2건은 한쪽만 성공하고 다른 쪽은 멱등키 UNIQUE 위반으로 롤백된다. 순서가 중요한 테스트는 뒤 트랜잭션이 MySQL에서 잠금 대기 중인 것을 확인한 뒤 앞 트랜잭션을 커밋한다.
- 월 경계: KST 9월 30일 23:59:59.999와 10월 1일 00:00:00 지급은 다른 지갑(`expiry_month` 9/1, 10/1)을 쓴다.
- 호출자 계약: 트랜잭션 없이 `grant`를 호출하면 실패한다. flush 전 청구도 `grant`가 찾는다. 청구 UNIQUE 위반으로 롤백한 뒤 새 트랜잭션에서 다시 처리하면 `replayed=true`로 같은 결과를 받는다.
- 코드 리뷰(`/code-review high`)에서 MEDIUM 1건과 LOW 4건이 나왔다. 청구 UNIQUE 위반 위치 설명·테스트, 지갑 잠금 확인, 테스트 단언 강화는 반영했다. 만료된 지갑 입금 오류 처리는 만료 기능으로, Hibernate 내부 SPI(`UuidVersion7Strategy`) 의존은 유지로 남겼다.
- 컨테이너 없이 돌리는 `./gradlew test`만으로는 통합 테스트가 실행되지 않는다. CI와 로컬에서 Docker가 필요하다.
- 이번 작업과 무관하게 `dev`에서 e823f78이 이미 V006을 직접 수정하고 V012를 지웠다. 예전 V006·V012를 적용한 로컬 DB는 Flyway 체크섬 검증에서 실패하므로 스키마를 드롭하고 다시 생성해야 한다.
- GD-46: `origin/dev`(f3eb6e8, PR #7 알림 포함) 반영 후 `./gradlew build`가 통과했다. core 76, `storage:db` 통합 44, api 단위 18, api 통합 6개가 실패 0이다. PR #9 CI 빌드·테스트도 통과했다.
- GD-46 T01·T02 검증: 지급 후 사용 가능 잔액 = 지갑 잔액 = 원장 합계, 10/1 00:30 KST 기준 9월 지갑(ACTIVE 저장)과 EXPIRED 지갑의 잔액 제외, 생성 시각이 같은 이력 묶음의 커서 이동에서 중복·누락 없음, 기간 경계(시작 포함·끝 제외), 청구 종류별 파생 필드, 사용자 격리.
