## 오늘 한 일

### 담당 범위 재확인과 V003·V004 검토

- ERD 검토 분담과 달리 구현 담당은 출석·일회성 미션까지 포함한다(`docs/01-conventions/backend-feature-assignments.md`). 이에 맞춰 미션·출석 테이블을 새로 검토했다.
- 실제 MySQL 8.0.46에 초기 스키마를 순서대로 적용했다. 전부 통과했고 41개 테이블과 UNIQUE 48개, FK 104개, CHECK 22개가 정상 생성된다. GD-4와 GD-22에 남아 있던 "실제 MySQL 적용 검증" 항목을 이 결과로 해소할 수 있다.
- 스키마가 막아준다고 가정했던 항목 8건에 직접 INSERT를 넣어 전부 통과하는 것을 확인했다. 정합성 보강 마이그레이션 초안을 작성해 같은 컨테이너에서 검증한 뒤 근거 문서와 함께 전달했다.

### 초기 스키마 통합본 검증

- 전달한 마이그레이션이 별도 파일로 커밋된 뒤, 외래 키 마이그레이션과 함께 도메인별 초기 스키마 안으로 통합됐다. 통합본을 빈 DB에 적용해 통합 전 검증본과 전수 비교했다.
- 테이블·UNIQUE·FK·CHECK 개수, 컬럼의 이름·타입·NULL 허용·생성식, 인덱스 정의, CHECK 식 내용, FK 104개의 참조 관계가 모두 일치했다. 위반 8건 차단과 정상 동작 6건 통과도 동일하다. 통합 작업은 내용 손실 없이 됐다.

### 내가 넣은 제약 하나 정정

- `chk_streak_days`를 `consecutive_days BETWEEN 0 AND 28`로 걸었는데 틀렸다. `attendance.md`의 "28일을 초과하는 단계는 두지 않는다"는 연속 출석 단계(`milestone_days`)의 상한이며 실제 연속 일수의 상한이 아니다.
- 연속 출석은 같은 달 안에서 판정하므로 31일까지 도달한다. 기존 제약에서는 29일째 출석의 연속 상태 기록이 거부되어 출석 처리 전체가 실패한다.
- `game_reward_claims`의 일일 제한도 함께 보강했다. 두 건을 `fc26b3b`로 반영했다.

## 고민과 판단

- `attendances`에 KST 기준일 컬럼이 없어 연속 출석 판정의 원천 데이터가 없다는 점을 9월 23일 검토에서 잡았는데 DDL에 그대로 굳어 있었다. `attendance_streaks`가 KST 날짜로 상태를 들고 있으나 원천에서 재도출할 수 없어 상태가 틀어지면 복구할 방법이 없다. `attendance_date` 추가로 일일 중복 방지와 재계산을 함께 해결했다.
- 답변의 소속 검증을 복합 외래 키로 할지 애플리케이션 검증으로 둘지 고민했다. 초기 스키마에 이미 같은 목적의 복합 외래 키가 세 개 들어가 있어 방식을 통일하는 쪽을 택했다. 부모 테이블에 복합 UNIQUE를 추가하는 비용만 든다.
- 답변 유형별 XOR CHECK는 불가능했다. MySQL CHECK는 같은 행의 컬럼만 볼 수 있고 `question_type`은 문항 테이블에 있다. "선택지 또는 답변 문자열 중 하나는 있어야 한다"까지만 걸고 유형별 검증은 애플리케이션에 남겼다.
- `mission_submissions`의 완료 제출 1건 제한은 제안했다가 넣지 않았다. 제출을 행으로 쌓고 수정하지 않는 방식을 유지하기로 했다. 대신 완료 처리 전에 기존 완료 여부를 애플리케이션에서 확인해야 한다.
- `game_reward_claims`의 일일 제한은 기존 `UNIQUE (user_id, source_key)`만으로는 부족하다고 판단했다. `game.md`가 "보상 정책 변경으로 동일 보상 기준일의 지급 제한이 초기화되지 않는다"로 정하는데, `source_key`에 정책 식별자가 섞이면 정책 교체만으로 같은 날 두 번째 지급이 통과한다. `user_id`, `game_id`, `reward_date`가 이미 컬럼으로 있어 제약만 추가했다.

## 확인 결과 / 막힌 점

- 초기 스키마를 빈 DB에 적용해 실패 0을 확인했다. 결과는 UNIQUE 55개, FK 104개, CHECK 30개이며 초 단위 `datetime`은 0개, `datetime(6)`은 85개다.
- 제약 검사 25건이 모두 기대대로다. 연속 28·30·31일 통과, 32일과 음수 차단, 단계 29일 차단, 같은 게임 같은 날 두 번째 보상 차단, 같은 날 다른 게임 보상 통과를 확인했다. 같은 미션에 제출 4건(재도전 2건 + 완료 2건)이 그대로 들어가 오답 재도전이 막히지 않는 것도 확인했다.
- 생성 컬럼이 두 개였다. `event_entries.single_entry_guard`는 `int DEFAULT NULL`이라 애플리케이션이 값을 채운다. NULL로 넣으면 1회 제한이 동작하지 않는 것을 확인했다. 현행 유지로 정했으므로 응모 구현 시 테스트로 덮는다.
- `fc26b3b`는 기존 마이그레이션을 직접 수정했고 `dev`에 바로 push했다. `AGENTS.md`는 기존 마이그레이션 수정 금지와 `dev` 직접 push 금지를 정하고 있어 두 항목과 어긋난다. 초기 스키마 확정 전이고 현재 팀이 같은 방식으로 작업하고 있어 맞췄으나, 규칙과 실제 운영 방식을 일치시키는 논의가 필요하다.
- 기존 마이그레이션을 수정했으므로 이미 로컬 DB에 적용한 경우 Flyway 체크섬이 맞지 않는다. 스키마를 드롭하고 다시 생성해야 한다.
- `./gradlew test`와 빌드는 실행하지 않았다. 애플리케이션 코드 변경이 없고 프로젝트에 datasource 설정이 없어 Flyway가 실행되는 경로가 아니다. 검증은 별도 MySQL 컨테이너에 SQL을 직접 적용하는 방식으로 했다.
