### 응모권 차감·반환 서비스 마무리 (GD-133, PR #45)

- Flyway 버전이 열린 PR #16과 같은 `V017`이었다. 내 마이그레이션을 `V018`로 바꿨다(`7c3a4c7`). 병합 전 파일이라 새 마이그레이션을 더하지 않고 파일명을 바꿨다.
- CodeRabbit이 후보 조회 인덱스 `(user_id, status, expires_at, grade)`가 `ORDER BY expires_at, id`와 맞는지 `EXPLAIN`으로 확인하라고 지적했다. MySQL 컨테이너에 약 6만 행을 넣고 확인했다. 기존 인덱스는 `Using filesort`였고, 처음 생각한 `(user_id, grade, expires_at, status)`도 `status`가 `expires_at`과 PK 사이에 끼어 같은 `Using filesort`였다. `status`를 뺀 `(user_id, grade, expires_at)`는 정렬 없이 `Using index condition; Using where`로 읽혔다. 인덱스를 `ix_tickets_user_grade_expiry`로 바꿨다(`37d1d65`). 상태는 행에서 거른다.
- 반환 판정에 쓰는 내부 `private enum TicketState`를 `core/ticket/domain/RefundTicketState`로 옮겼다. `dev`의 enum 25개는 모두 독립 파일이고 중첩 enum이 없어 관례에 맞췄다.

### 이벤트 응모 API 구현 (GD-134, 브랜치 `feat/GD-134`, PR 없음)

- `POST /api/v1/events/{eventId}/entries`(E04)와 `GET /api/v1/events/{eventId}/eligibility`(E07)를 구현했다. #45가 병합되기 전이라 PR은 만들지 않고 브랜치에만 두었다.
- 응모 ID는 `Idempotency-Key` 헤더의 UUID이며 `event_entries.id`로 그대로 쓴다. 별도 멱등 테이블은 없다. 접수된 응모만 저장하고 신규는 201, 같은 키의 재요청은 200으로 기존 영수증을 돌려준다. 같은 키로 다른 본문이 오면 409 `ENTRY-009`다.
- 오류 코드는 `ENTRY-001`~`009`다(요청 형식, 관리자 응모 거절, 멤버십 미달, 이벤트 없음, 이벤트 미개방, 중복 응모, 한도 초과, 브론즈 필요, 멱등 충돌). 등급별 보유 부족은 `TICKET-006`을 그대로 전파한다.
- 처리 순서는 관리자 확인, 기존 응모(재요청) 확인, 이벤트 행 공유 잠금(`FOR SHARE`), 멤버십, 기간, 요청 형태, 응모자 행 PK 잠금, 한도, 응모 행 저장, 응모권 차감, 사용량 누적이다. 한 트랜잭션(`READ COMMITTED`)에서 확정하고 잠금 순서는 이벤트(공유), 응모자, 응모권으로 고정했다. 이벤트 행을 공유 잠금으로 읽어 응모끼리는 서로 막지 않고, 추첨 준비의 `FOR UPDATE`는 진행 중인 응모를 기다린다.
- 이벤트 유형별 규칙은 응모권 미사용(비어 있는 요청, 1회), 가중치 미적용(브론즈 1장만, 1회), 일반 가중치(누적 최대 5장), 월말 소진용(상한 없음, 보유량 이내)이다. 이벤트 읽기는 담당자 코드를 건드리지 않으려고 `events`를 읽는 네이티브 SQL 포트(`EntryEventReader`)를 따로 두었다.
- 응모 요청을 등급별 장수 맵 `tickets`로 받고 영수증에 등급별 요청·차감 장수를 담았다. CORS 허용 헤더에 `Idempotency-Key`를 추가했다(`api/src/main/resources/application.yaml`, `docs/02-api/cors.md`, `CorsConfigTest`).
- 스펙 `main`에 반영했다. `05-api/common.md`(`Idempotency-Key`는 UUID, `ENTRY-001`~`009`), `05-api/entry.md`(현행 구현 범위: 거절 이력 저장과 429는 후속), `02-domain/entry.md`, `00-requirements/pending-decisions.md`(응모·반환 항목 확정).
- 후속 이슈를 Jira에 만들어 두었다. 거절 이력 저장(GD-145), 응모 요청 속도 제한 429(GD-146).

## 고민과 판단

- 인덱스에 `status`를 넣으면 같은 만료 시각의 `(expires_at, id)` 순서가 깨진다. 같은 달 지급분은 모두 같은 시각에 만료하므로 이 순서가 실제로 중요하다.
- 반환 재요청 수정에서 처음에는 락을 잡은 직후 항상 반환 이력을 잠금 읽기로 다시 확인했다. 그러자 서로 다른 사용자의 동시 반환 테스트(`TicketCrossUserConcurrencyTest`)에서 교착이 났다. 반환 이력이 없는 구간에 공유 갭 락을 서로 잡은 뒤 이력 INSERT가 서로 막히기 때문이다. 확인을 상태가 이상할 때만 하도록 좁혔고, 정상 반환 경로에는 쿼리나 락이 늘지 않는다.
- 내부 전용 판정값은 사용하는 클래스 안에 `private`으로 두는 것이 낫다고 판단했으나, `dev`에 중첩 enum이 하나도 없는 것을 확인해 팀 관례에 맞췄다. 관례는 내 판단이 아니라 코드로 확인한다.
- 경로·헤더의 UUID는 Spring 기본 변환에 맡기는 것이 팀 전체(박지훈 님의 #16 포함) 방식이다. 이경주 님의 `CurrentUserArgumentResolver`는 `X-User-ID`를 축약 표현까지 막도록 엄격하게 검사한다. `Idempotency-Key`에 축약 표현이 통과해도 같은 문자열이면 같은 UUID여서 멱등 동작과 데이터에 문제가 없다고 보고, 공통 코드 변경이 필요한 일이라 지금은 그대로 두기로 했다.
- 반환은 이벤트 취소 때만 한다. 따라서 추첨 제외 반환은 만들지 않는다. 석종수 님의 추첨 스냅샷에는 제외 판정 코드(`DrawExclusionRepository`)가 남아 있어 정리 여부를 확인해야 한다.
