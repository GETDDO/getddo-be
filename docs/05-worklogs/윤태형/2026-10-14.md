## 고민과 판단

- PR의 base는 처음부터 `dev`로 한다. 다른 브랜치를 base로 만들었다가 바꾸면 이번처럼 병합 시점에 merge-base가 어긋나 승인이 반복 무효화된다. 규칙과 근거를 메모리에 남겼다.
- 거절 건의 요청 장수를 저장하는 안을 택한 이유는 스펙 계약(nullable이 아님)을 바꾸지 않기 위해서다. 비용은 컬럼 3개다.
- 등급별 합계와 요청 수량의 일치는 도메인에서 검증하고 DB CHECK는 두지 않았다. 추첨 테스트 시드가 요청 수량만 넣고 등급별 컬럼은 0인 행을 직접 만들기 때문이다. 새 행은 도메인 팩터리를 거치고 기존 행은 V026 백필이 사용 이력으로 맞춘다.
- 거절 이력 저장이 실패해도 사용자에게는 원래 거절을 돌려준다. 저장 실패는 원래 예외에 `suppressed`로 덧붙인다(core에는 로깅 의존성이 없다).
- 같은 응모 ID의 결과가 이미 있으면 거절 기록기가 `false`를 돌려주고 서비스가 요청을 다시 처리한다. 이렇게 하면 접수 영수증 재생이나 `ENTRY-009`, 저장된 같은 거절이 일관되게 나온다.
- 정리 기준은 "같은 동작을 검증하는 쪽을 하나로 합친다"로, 컨트롤러 단위와 API 통합이 겹치면 통합 쪽을 남기는 방향이다. 새로 쓴 컨트롤러 테스트에도 같은 기준을 적용해 헤더 401 테스트는 넣지 않았다.
