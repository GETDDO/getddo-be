### 미션 제출 API (GD-175, PR #71)

- #65(미션 모델·저장소)가 병합되어 Jira GD-167을 `완료`로 바꾸고 GD-48(미션 인계)은 사유를 적어 닫았다. 미션을 넘기지 않고 계속 맡기로 해서 GD-167·GD-174~177·GD-179·GD-180을 모두 윤태형에게 배정했다. 처음 이슈를 만들 때 담당자 지정이 적용되지 않았는데 배정했다고 잘못 보고했다가 확인 중에 발견해 바로잡았다.
- 시작 순서, 퀴즈 완료 조건, 멱등 처리는 사용자가 정했다. GD-175(제출)부터 하고, 퀴즈는 문항별 정답 누적, `Idempotency-Key`를 제출 ID로 쓴다.
- 구현: `POST /api/v1/missions/{missionId}/submissions`(M03). 서버가 채점하고 완료하면 보상 청구와 응모권 지급까지 한 트랜잭션(`READ COMMITTED`)으로 확정한다. 퀴즈는 `quiz_question_progress`에 문항별 정답을 누적하고 남은 문항을 모두 맞히면 완료한다. 이미 맞힌 문항에 다시 보낸 답변은 채점·저장하지 않고 무시하며, 처리할 답변이 없으면 400이다. 설문은 필수 문항을 모두 채워야 완료하고 비면 400으로 거절한다. 단답형은 NFC·앞뒤 공백·연속 공백·대소문자를 정규화해 비교한다(구현 제안).
- 같은 사용자의 동시 완료는 제출 PK, `(user_id, quiz_question_id)`, `(user_id, mission_id)` 유일 제약이 직렬화한다. 바깥 서비스(`MissionSubmissionService`)가 트랜잭션 없이 유일 제약 위반(MySQL 1062)과 잠금 실패를 새 트랜잭션에서 한 번 다시 처리해 먼저 확정된 결과를 읽는다(`EntryService`와 같은 방식). 정답 문항은 문항 ID 순서로 기록해 교착을 피한다.
- 제출 ID를 클라이언트가 정하도록 `MissionSubmissionEntity`를 `Persistable`로 바꾸고 `MissionSubmission.of`가 제출 ID와 접수 시각을 받게 했다. 이 과정에서 기존 테스트 두 개가 "저장 전에는 ID가 없다"는 옛 전제를 담고 있어 새 의미에 맞게 고쳤다.
- 같은 키 재전송의 본문 비교는 저장된 답변으로는 할 수 없다. 이미 정답으로 완료한 문항의 답변은 저장하지 않아 처음 요청을 복원하지 못하기 때문이다. 그래서 처음 요청의 해시(사용자·미션·답변을 문항 ID 순으로 정렬한 SHA-256)를 `mission_submissions.request_hash`(V025)에 보존해 비교한다. 선택지·입력 문자열은 원문 그대로 반영하고 공백뿐인 입력은 없는 것으로 본다(사용자가 해시 컬럼 추가를 선택).
- 검증: 단위(채점·완료 판정 10, Recorder 9, 서비스 재시도 5, 컨트롤러 6, 요청 해시 5), 실제 MySQL 통합(완료·누적·재전송·재제출·설문·기간 경계·API 전 구간), 지급 서비스를 실패시켜 제출·청구·정답 진행이 함께 취소되는지 확인하는 롤백 테스트, 동시성 5개(각 15회 반복, 교착 없음). 서비스의 중복 키 재시도를 빼면 동시성 테스트 75회 중 60회가 실패하는 것을 확인한 뒤 복원했다.

### 조직 이사 (GETDDO → Uplus-GETDDO)

- CodeRabbit 무료 기간이 끝나 저장소를 `Uplus-GETDDO` 조직으로 옮겼다. 팀장이 진행했고, 확인해 보니 복사가 아니라 이전(transfer)이다. 옛 주소(`GETDDO/getddo-be`, `getddo-spec`, `getddo-fe`)가 새 조직으로 연결되고, 새 `dev`는 옛 `dev`와 커밋 해시까지 같고, PR 번호와 위키도 그대로다. 문서 속 옛 링크는 리다이렉트로 동작한다.
- 내 권한이 처음에는 읽기 전용이었다가 세 저장소 모두 admin으로 바뀐 것을 확인했다. 로컬 `origin`을 새 주소로 바꿨고 `getddo-spec`의 `origin`도 바꿨다. 새 저장소에 없던 라벨(`feature`, `fix`, `refactor`, `docs`, `test`, `bug`, `skip-review`)을 옛 저장소와 같은 이름·색으로 만들었다.
- CodeRabbit은 새 조직에서 동작한다(새 PR에 리뷰가 달리고 설정의 스펙 저장소 경로는 #74에서 고쳐졌다). 자동 리뷰는 `dev`가 base인 PR만 대상이라 다른 브랜치를 base로 한 PR에는 수동으로 `@coderabbitai review`가 필요하다.
- Jira 연동은 확인하지 못했다. 새 조직에 Atlassian 앱이 설치된 것은 보이지만 이슈의 개발 정보가 비어 있고 새 브랜치·PR이 이슈에 반영되지 않았다. 연동이 되기 전까지 Jira 상태는 수동으로 바꾼다.
- 옛 조직 주소가 남은 파일: `getddo-be`(워크로그 제외) 25개 파일 85곳, `getddo-spec` 5개 파일 10곳. 리다이렉트가 있어 급하지 않고 워크로그는 과거 기록이라 그대로 둔다. 내일 `[docs]` PR로 한 번에 바꿀 예정이다.
- 마이그레이션 번호: 새 `dev`에는 `V021~V023`까지 있고 열린 PR이 `V020`(#73), `V024`(#69)를 쓰고 #71의 `V025`는 병합됐다. `outOfOrder` 설정이 없어 이미 낮은 번호를 적용한 DB가 있으면 오류가 나지만, 아직 어떤 DB도 적용하지 않았으므로 번호가 겹치지만 않으면 순서는 상관없다. DB를 처음 띄운 뒤부터는 새 마이그레이션이 그때의 최고 번호보다 높아야 한다.

### 미션 조회 API (GD-174 M01·M02 → PR #75, GD-176 M04 → PR #76)

- GD-174: `GET /api/v1/missions`(목록)와 `GET /api/v1/missions/{missionId}`(상세)를 구현했다. 목록은 `page`·`size`(1~100)·`missionType`을 받고, 페이지의 미션 ID만 모아 사용자의 완료 제출을 한 번에 조회해 `completed`를 만든다. 상세는 설명과 문항·선택지를 표시 순서로 돌려주고 없는 미션은 404 `MISSION-003`이다.
- 계약 결정(스펙이 담당자 계약으로 남긴 부분, 사용자가 선택): `rewardTicketCount`는 미션 보상이 항상 응모권 1장이라 1로 고정해 유지한다. 목록은 `DRAFT`가 스키마에 없으므로 `ACTIVE`·`ENDED`를 모두 시작 시각 내림차순으로 보여 주고 진행 여부는 `startsAt`·`endsAt`·`completed`로 판단하게 한다. 퀴즈 문항의 `required`는 모든 문항을 맞혀야 완료하므로 항상 true, `imageUrl`은 이미지 저장소가 정해지기 전이라 이벤트와 같이 null이다.
- 사용자 응답에는 정답(`correctAnswer`, 선택지의 정답 여부)을 싣지 않는다. 응답 DTO를 별도 타입으로 두고 정답 필드를 읽지 않으며, 응답 본문에 비밀 정답 문자열과 `correct`가 없는지 테스트로 막았다. 문항 응답에 `correctAnswer`를 일부러 넣으면 테스트가 실패하는 것을 확인한 뒤 되돌렸다.
- `MissionController`의 클래스 매핑을 `/api/v1/missions`로 바꾸고 제출 경로를 `/{missionId}/submissions`로 옮겼다. 실제 M03 URL은 그대로다.
- GD-176: `GET /api/v1/missions/{missionId}/submissions/me`를 구현했다. 요청 사용자의 제출을 최신순(`createdAt` 내림차순, 같으면 ID 내림차순)으로 돌려주고, 오답은 `isCompleted=false`, `reward=null`로, 완료한 제출에는 그 제출의 보상 청구로 확정된 응모권 지급 결과를 붙인다. 없는 미션은 404다.
- 제출 결과를 만드는 로직(완료 제출의 보상 청구 → 응모권 지급 조회)을 `MissionSubmissionRecorder`의 private 메서드에서 `MissionSubmissionResultReader`로 옮겨 M03 재전송 응답과 M04가 같은 규칙을 쓴다. 동작은 바꾸지 않았고 기존 Recorder 단위 테스트와 제출 서비스 통합 테스트는 그대로 통과한다. 완료한 제출에 청구나 지급 결과가 없으면 숨기지 않고 실패하며 메시지에 제출·사용자·미션 ID를 담는다.
- 검증: `MissionQueryServiceTest` 5, `MissionSubmissionQueryServiceTest` 7, `MissionControllerTest` 15, 실제 MySQL 통합 `MissionQueryServiceIntegrationTest` 5·`MissionSubmissionQueryServiceIntegrationTest` 5, 필터 체인과 DB를 거치는 `MissionApiIntegrationTest` 6. 저장소 정렬의 ID 순서를 뒤집으면 시작 시각·제출 시각이 같은 경우를 검증하는 통합 테스트가 실패하는 것을 확인한 뒤 되돌렸다. 두 PR 모두 전체 `./gradlew build`가 통과했다(각 20분 남짓). 이후 리뷰 반영분은 관련 단위·통합 테스트만 다시 돌렸다.
- 코드 리뷰(서브 에이전트)는 두 PR 모두 승인이었고 LOW만 있었다. 반영한 것은 오류 메시지에 식별자 추가, 정답 비노출 단언 강화, 불변식 위반과 경계값 테스트 추가다.
- CodeRabbit 지적은 #75에서 1건(시작 시각이 같은 미션의 ID 정렬 검증), #76에서 5건(경계값, 같은 시각 정렬, 메시지 검증, 다른 사용자 비노출, `reward`가 명시적 null인지)이었고 모두 테스트 보강이라 타당한 것을 고쳤다. DB의 `BINARY(16)` 정렬은 부호 없는 바이트 사전식 비교이고 Java `UUID.compareTo`와 다를 수 있어 테스트에서 직접 바이트로 비교한다. #75는 CodeRabbit이 승인했고 #76은 지적이 모두 해결됐다. 두 PR 모두 사람 리뷰를 기다린다.
- #76은 #75의 `MissionController` 변경 위에 만들어서 처음에는 base를 `feat/GD-174`로 두었다가 CodeRabbit 자동 리뷰가 꺼진다는 것(`dev` 대상만 자동 리뷰)을 확인하고 `dev`로 바꿨다. 이 때문에 #76의 diff에 #75의 파일이 섞여 있고, #75가 먼저 병합되어야 M04 변경만 남는다.
- 스펙 `05-api/mission.md`에 "현행 구현 범위(GD-174, M01·M02)"와 "(GD-176, M04)"를 `main`에 반영했다. `api-schema-mapping.md`에 M01·M02·M04 행을 추가했다.

### 거절 이력 탐색 (GD-145, 구현 보류)

- E05/E06 거절 이력을 저장하는 설계를 코드와 스펙, 문서로 확인했다. 아직 구현하지 않았다. 결정할 것이 많아 팀원과 먼저 합의하기로 했다.
- 확인한 사실: 응모 처리는 예외가 나면 전체가 롤백되어 거절 기록을 같은 트랜잭션에 쓸 수 없다. 바깥 서비스가 예외를 받은 뒤 별도 트랜잭션(`REQUIRES_NEW`)의 전용 서비스로 기록하고 원래 오류를 다시 던지는 구조가 맞다. `event_entries`는 `participant_id`가 NOT NULL이고 `event_id`·상태·거절 컬럼이 없다. 추첨 스냅샷(`DrawSnapshotSourceReader`)의 응모 조회에는 상태 필터가 없어 지금은 참여자 조인이 거절 건(`participant_id` NULL)을 우연히 걸러 줄 뿐이다. 직접 INSERT하는 테스트 시드가 약 12개 파일이다.
- 백엔드 문서가 서로 다르다. `drawing-selection-storage.md`는 "성공만 저장, 상태 컬럼 없음"이고 석종수의 9/23·9/24 ERD 기록은 "거절 건 보존, `participant_id` NULL, `rejection_code`"다.
- 합의가 필요한 것: 저장 방식(`event_entries` 확장 vs 별도 거절 테이블, 사용자는 확장을 선택), `event_id` 필수 여부(시드 수정 vs 조회 이중 경로), 스펙이 말하지 않은 거절(404, 409 키 충돌, 429)을 저장할지, 속도 제한 전 거절 이력 상한. 정리한 협의 메시지를 내일 팀원에게 전달한다.

## 고민과 판단

- 마이그레이션 테스트의 개수 단언을 없애는 것은 충돌 방지와 안전망의 맞바꿈이다. 안전망이 어디까지 남는지(테이블 44개 단언, 객체별 단언, Flyway 체크섬 검증)를 확인한 뒤 제거하는 쪽이 낫다고 판단했다.
- CodeRabbit이 Javadoc 문구를 한 줄씩 파고들어 PR #63에서만 아홉 번 지적했다. 단정적인 표현(롤백된다, 첫 폴링이 처리한다)이 지적을 불렀다. 문서와 Javadoc에는 코드가 보장하는 것만 적는 것으로 방향을 바꿨다.
- 붙여 받은 검토 문서는 사실이 많았지만 이미 끝낸 일(기간 판정 분리)과 사실과 다른 전제(충돌 상태, 이미 있던 테이블 개수 단언)가 섞여 있었다. 판단 전에 파일로 확인하는 쪽이 낫다.
- 미션 제출에서 이미 맞힌 문항만 다시 보내면 400으로 두었는데 정상 결과(200, 미완료)로 돌려주는 방안도 있다. 그러려면 저장하지 않는 제출의 ID·시각을 정해야 해서 이번에는 400으로 두고 PR 본문에 남겼다.
- 완료 조건을 문항별 누적으로 하면 `MissionSubmission`의 "완료 제출은 모두 정답" 규칙과 부딪힐 수 있어, 이미 맞힌 문항의 답변은 저장하지 않는 쪽으로 풀었다.
- 완료한 제출 둘이 한 페이지에 있으면 M04가 500으로 실패한다. 청구가 사용자·미션당 하나뿐이고 제출과 같은 트랜잭션으로 보장되므로 정상 데이터에서는 일어나지 않고, 숨기면 `isCompleted=true`인데 보상이 없는 모순된 응답이 되기 때문에 실패하게 두었다. M03 재전송 경로도 같은 방식이다.
- 쌓은 PR(#76)의 base를 `dev`가 아닌 브랜치로 두면 diff는 작아지지만 CodeRabbit 자동 리뷰가 꺼진다. 자동 리뷰를 놓치지 않는 쪽이 낫다고 보고 `dev`로 바꿨다.
