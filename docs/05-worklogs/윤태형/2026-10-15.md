### 응모 마감을 커밋 직전까지 확인 (GD-205 → PR #101)

- 응모 서비스의 마지막 마감 확인과 실제 커밋 사이에 마감 시각을 넘으면, 마감 뒤에 확정된 응모가 남을 수 있었다. `EntryRecorder`가 응모자 누적 수량을 올린 직후 같은 트랜잭션에 커밋 직전 동작(`beforeCommit`)을 등록해 마감을 한 번 더 확인하고, 넘었으면 `ENTRY-005`로 롤백한다. 롤백 뒤에는 거절 이력만 남는다.
- DB가 커밋 시각을 커밋 전에 알려 주지 않아, 마지막 확인과 커밋 확정 사이의 간격은 구현으로 없앨 수 없다. 이를 공용 도메인 명세 `02-domain/entry.md`에 "마감 판정 예외(GD-205, 사용자 승인)"로 반영하고 ADR-0006에서 링크했다. 이 예외 문서가 없어서 석종수의 #90(GD-131) CI가 실패하고 있었고, 반영 뒤 #90이 `dev`를 합쳐 병합됐다.
- 통합 테스트 `EntryCommitBoundaryIntegrationTest` 3개: 커밋 직전에 마감을 넘기면 `ENTRY-005`로 롤백(응모·차감·응모자 행이 남지 않고 거절 이력만 남음), 마감 1마이크로초 전이면 정상 확정, 마감 뒤 거절된 응모 ID를 다시 보내도 처음과 같은 `ENTRY-005`.

### 사용자별 요청 빈도 제한 (GD-146 → PR #96)

- `@RateLimited(policy, scopeVariable)` + `RateLimitInterceptor`(`/api/**`)가 사용자별로 센다. `X-User-ID` UUID 형식만 인식하고 헤더가 없으면 제한하지 않아 기존 사용자 문맥 검증이 401·400을 처리한다. 한도를 넘으면 429, `COMMON-006`, `Retry-After`(남은 초)를 돌려주고 CORS 노출 헤더에 `Retry-After`를 넣었다.
- 수치(창 1분): 응모 사용자 20회·이벤트당 10회, 출석 5회, 미션 제출 사용자 20회·미션당 5회, 게임 결과 10회(G04 컨트롤러가 없어 아직 미적용). 정책은 `application.yaml`에서 조정하고 `RATE_LIMIT_ENABLED=false`로 끌 수 있다.
- 제한기는 `RateLimiter` 인터페이스 뒤에 두고 지금은 서버 메모리 구현(`InMemoryRateLimiter`)을 쓴다. 제한기가 실패하면 요청을 막지 않고 통과시킨다.
- CodeRabbit 지적 10건을 코드와 대조해 반영하고 스레드별로 답글을 달아 resolve했다. `dev`를 합칠 때 `docs/02-api/README.md` 링크 줄이 충돌해 풀었다. 전체 빌드 통과(18분 56초, 1988개 실패 0). 스펙 `common.md`에 429 행을 반영했다.
- 이경주 확인(`COMMON-006` 번호·수치) 뒤 병합됐다. Jira GD-146을 완료로 바꾸고, 스펙 `mission.md`의 "빈도 제한은 후속 작업" 문구를 적용된 사실로 고쳤다.

### Redis 기반 요청 빈도 제한 (GD-208 → PR #107, 리뷰 대기)

- 서버가 2대로 늘고 Redis가 오늘 저녁 도입된다는 말에 맞춰 새 이슈 GD-208을 만들었다(에픽 GD-43, 스프린트 4). #96의 `RateLimiter`에 `RedisRateLimiter`를 추가했다. 서버 2대의 횟수가 하나로 합쳐진다.
- 횟수 증가와 첫 요청 때 만료 설정을 Lua 스크립트 하나로 실행해 동시 요청도 정확히 센다. 만료가 빠진 키는 다음 호출에서 다시 건다. 창은 Redis 서버 시계로 재서 서버 간 시계 차이와 무관하다.
- 저장소는 `RATE_LIMIT_STORE`(`memory` 기본, `redis`)로 고른다. 접속 정보는 `REDIS_HOST`·`REDIS_PORT`·`REDIS_PASSWORD`·`REDIS_SSL_ENABLED`. 설정을 안 바꾸면 지금과 똑같이 메모리 구현으로 동작한다. 명령 제한 300ms, 연결 제한 500ms로 두고 실패하면 요청을 통과시킨다.
- 테스트(실제 Redis 컨테이너): 서버 2대를 흉내 낸 합산, 키 독립, 창 초기화, 동시 50건 중 10건 허용, 키 항상 만료, 접속 불가 시 5초 안에 예외. 앱 전체를 `store=redis`로 띄운 429 확인과 Redis가 죽은 상태에서 429 없이 통과하는 것도 확인했다. 설정 전환 단위 테스트 4개. 전체 빌드 통과(29분 41초).
- CodeRabbit 3건: 다른 미션 허용 검증 추가(반영), 한도 초과 요청도 Redis는 `INCR`로 센다는 점을 문서에 명시(문서를 구현에 맞춤), TLS 기본값을 `true`로 바꾸라는 지적은 반영하지 않고 `false`를 유지하며 위험을 문서에 못 박음.

## 고민과 판단

- 관리자 응모권 조회가 내 영역인지 확인했다. 스펙 `ticket.md` 머리말에 "주 담당 윤태형"이 있고 담당 문서 D가 응모권 이력 조회를 갖지만, C(전민규)의 "사용자·이벤트·응모·운영 내역의 관리자 통합 조회"와 겹칠 수 있다. 데이터와 SQL은 내 도메인이라 구현은 내가 했고, 병합 뒤 전민규에게 중복 여부를 확인하기로 했다.
- Redis 기본 TLS는 `false`로 유지했다. 기본이 `true`면 TLS 없는 Redis에서 핸드셰이크가 실패하고, 제한기 실패는 요청을 통과시키는 설계라 에러 없이 제한만 조용히 풀린다. Redis 접속 방식이 확정되지 않았다. 대신 비밀번호를 쓰는 Redis가 사설망 밖이면 `REDIS_SSL_ENABLED=true`가 필수라고 문서와 런북에 적었다.
- AO09는 요청마다 `tickets` 전체를 비교한다. 대량 데이터의 성능은 측정하지 않았으므로 운영 데이터가 커지면 증분 확인이나 배치로 바꾼다(`admin-ticket-inspection.md`에 기록).
- Redis 제한기는 한도를 넘은 요청도 `INCR`로 올린다. 키가 창이 끝나면 사라져 문제가 없고 판정과 `Retry-After`는 메모리 구현과 같아서, 조건부 증가 스크립트로 바꾸지 않고 문서를 고쳤다.
