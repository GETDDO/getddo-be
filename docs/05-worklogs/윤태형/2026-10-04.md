## 오늘 한 일

### 응모권·출석 도메인 `@EqualsAndHashCode` 제거와 출석 `refresh` 정리 (GD-94)

- 응모권·출석 core 도메인 21개 클래스에서 `@EqualsAndHashCode`를 뺐다. 운영 코드는 도메인 객체의 `equals`를 쓰지 않고, JPA가 요구하던 복합 키 클래스는 GD-88에서 없어졌다.
- 테스트는 PR #18처럼 값을 비교하는 방식으로 바꿨다.
  - 객체 비교: `usingRecursiveComparison()`
  - 목록 비교: `usingRecursiveFieldByFieldElementComparator()`
  - 같은 객체 반환 확인: `isSameAs`
  - 서비스 안에서 새로 만드는 인자의 Mockito 매칭: `refEq`
- PR #18로 Auditing 시각이 마이크로초로 잘리게 되어, 출석 저장 직후의 `refresh`와 쓰지 않게 된 `EntityManager` 필드를 지웠다.

### 응모권 조회 API 연결 (GD-73, PR #22)

- T01 `GET /api/v1/tickets/wallets/me`, T02 `GET /api/v1/tickets/ledger/me`를 `@CurrentUser(membershipRequired = false)`로 연결했다. 응답 DTO는 record + `from`이고 `expiryMonth`는 `YYYY-MM`으로 내보낸다.
- `size` 0이나 빈 커서가 공용 `CursorQuery`의 `IllegalArgumentException`으로 500이 되던 경로를 서비스에서 `TICKET-004`로 바꿨다.

### 출석 API 연결 (GD-95, PR #23)

- AT02 `POST /api/v1/attendances`를 연결했다. 새 출석은 201, 같은 날 재요청은 200이며 응답 본문은 같다.

### 동시성 통합 테스트 보강 (GD-96)

- CI에서 동시성 테스트가 간헐적으로 잠금 대기를 감지하지 못하고, 실패 후 정리가 안 돼 다른 테스트가 연쇄 실패했다(재실행하면 통과). 팀원 분석을 따라 두 가지를 고쳤다.
  - `LockWaitProbe`: `information_schema.innodb_trx`는 마지막 조회 후 0.1초가 지나야 캐시를 갱신하는데 20ms 간격으로 읽어 오래된 상태를 계속 볼 수 있었다. 실시간인 `performance_schema.data_lock_waits`로 바꿨다.
  - 스레드풀 7곳: `shutdownNow()`만 하던 것을 latch 해제 후 `ConcurrentTasks.shutdownAndAwait`로 작업 종료를 확인하고 정리하게 했다.

## 고민과 판단

- 앞으로 값 객체를 `Set`·`Map`·`contains`에 쓰면 그 클래스에만 `equals`·`hashCode`를 다시 구현한다. `code-style.md`와 ADR-0002는 "값 비교가 필요하면 구현"이라는 조건부 규칙이라 고치지 않았다.
- PR #22·#23의 CodeRabbit 지적에 따라 API 통합 테스트가 실제 시계에 의존하지 않게 했다. 응모권 조회는 만료 시각을 지금 ±30일로 두어 월 경계와 무관하게 했고, 출석은 클래스 전용 고정 시계(`@Primary Clock`)를 썼다.
- 출석 응답의 보상에는 명세 초안대로 일일·단계 구분 필드를 넣지 않았다. 도메인에는 `rewardType`·`milestoneDays`가 있어 명세 확정 시 추가할 수 있다.
- 같은 인스턴스끼리 비교해서 통과하던 단언은 의도대로 두었다. 연속 현황이 역순 날짜에서 자기 자신을 돌려주는지 보는 단언은 `isSameAs`로 바꿔 의도를 드러냈다.
