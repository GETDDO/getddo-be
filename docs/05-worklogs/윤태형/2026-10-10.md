### 응모권 차감·반환 서비스 (GD-133, PR #45)

- 이벤트 응모가 호출할 `TicketUseService`(차감)와 `TicketRefundService`(반환)를 만들었다. 응모(E04)와 이벤트 취소·제외에서 부르는 연결은 아직 없다. 만료(EXPIRE)는 다음 PR이다.
- 차감은 처음에 서버가 만료 임박순·낮은 등급 먼저 골라 쓰는 임시 구현으로 만들었으나, 사용자가 등급별로 쓸 장수를 직접 고르는 방식으로 바꿨다. 등급마다 현재 사용 가능한 장수가 상한이고, 같은 등급 안에서는 만료가 이른 응모권부터 쓴다. 이 규칙과 "반환은 같은 응모권이 등급 그대로 돌아온다"를 스펙 `main`에 확정으로 반영했다(`02-domain/ticket.md`, `pending-decisions.md`, `05-api/ticket.md`, 스펙 `04-worklogs`). 응모 요청·응답 형태(E04)도 이어서 확정해 스펙 `main`에 반영했다. 요청은 등급별 장수 맵 `tickets`(합계 필드 없음), 응답에는 등급별 요청·차감 장수를 더하고, 가중치 미적용 이벤트는 비싼 등급을 실수로 쓰지 않도록 브론즈 1장만 허용한다(`05-api/entry.md`, `02-domain/entry.md`, `05-api/common.md`).
- 반환 만료는 반환한 KST 월의 다다음 달 1일 00:00 KST이고, 같은 응모를 다시 차감·반환하면 추가 처리 없이 기존 결과를 돌려준다.
- 코드 리뷰 에이전트(`code-reviewer`) 리뷰에서 잠금 방식의 교착 가능성이 나왔다. 서로 다른 사용자가 서로 다른 응모(UUID v7)로 동시에 차감·반환하는 테스트를 만들어, 처음 구현이 모두 `Deadlock found`로 실패하는 것을 확인한 뒤 고쳤다.
- CodeRabbit 지적 중 잠금 대기 중 만료 재판정(Major), `OFFSET` 후보 페이지의 건너뜀(Major), 필수 값 검증, 방어적 복사, 다중 등급 역순 잠금 경쟁 테스트를 반영했다.
- 마지막 리뷰 라운드에서 직전에 넣은 "잠금 대기 중 만료된 선택을 뒤에 만료되는 응모권으로 대체하는 재시도"가 이전 시도의 잠금을 쥔 채 다른 등급을 다시 잠가 잠금 순서가 뒤집히고 교착할 수 있다는 지적(Major)을 받아, 재시도를 없애고 만료를 발견하면 `TICKET-006`으로 실패시키도록 되돌렸다. 같은 달 지급분은 모두 같은 시각에 만료해 대체할 수 있는 경우가 드물다. 호출 트랜잭션이 `READ COMMITTED`여야 한다는 규약은 `READ COMMITTED`는 성공하고 `REPEATABLE READ`는 `TICKET-006`이 나는 통합 테스트 2건으로 고정했다.
- 이 저장소의 CodeRabbit은 `request_changes_workflow: true`라 열린 스레드가 모두 resolved돼야 `APPROVED`로 바뀌고, 고쳐도 스레드가 자동으로 닫히지 않는다.

## 고민과 판단

- 응답은 월별 지갑 대신 등급·만료 시각별 묶음으로 둔다. 응모권 한 장 단위의 DB 구조와 맞고, 프론트가 목 데이터 단계라고 보아 호환 필드는 두지 않기로 했다. 프론트가 옛 스펙으로 화면을 만들었는지는 확인하지 못했다.
- AT01·AT03의 계산 규칙은 스펙에 없어 10/04에 정한 규칙 6개를 그대로 적용했다. 스펙 `05-api/attendance.md`에는 아직 반영하지 않았다.
- 역순 커밋 문제(GD-129)는 이 PR의 조회 코드로 고칠 수 없고, 쓰기 경로를 고쳐야 통과하는 테스트를 이 PR에 넣을 수 없어 별도 이슈로 분리했다.
- 동시성·시간 의존 테스트는 고정 시계와 신호 동기화만 쓰고 반복 실행으로 확인한다.
- 응모권 잠금: 잠금을 쥔 뒤 이력을 `FOR UPDATE`로 다시 확인하면 빈 결과에서 gap lock이 잡혀 이력 INSERT가 교착했고, `tickets` 범위 `FOR UPDATE`도 이웃 사용자 행에 next-key lock을 잡아 교착했다. 후보 ID를 잠그지 않고 읽은 뒤 PK로 한 장씩 `refresh(PESSIMISTIC_WRITE)`로 잠그는 방식으로 바꿨고, 후보 페이지는 `(expires_at, id)` 커서로 읽는다. 반환은 이력이 아니라 잠근 응모권 상태(`RETURNED`이고 버전 = 사용 버전 + 1)로 이미 반환됐는지 판정한다.
- 같은 응모 ID의 동시 차감은 서비스가 막지 않는다. 이력을 잠가 재확인하는 방식이 교착의 원인이어서 뺐고, 응모(E04)가 응모 행 저장으로 직렬화하고 저장이 실패하면 `use`를 부르지 않는 규약으로 Javadoc에 남겼다. E04 구현 때 중복 응모 INSERT 테스트가 필요하다.
- 차감 방식은 처음에 서버 자동 선택을 "팀 확정 전 임시 기본값"으로 정했는데 실제 의도와 달랐다. 정책 결정은 구현 편의로 정하지 않고 의도를 먼저 확인한다. 같은 달 지급분은 모두 같은 시각에 만료하고 반환분만 다르므로, 선택 단위는 만료 시각별 묶음이 아니라 등급 + 장수로 단순화했다.
- 반환 응모권의 등급 보존은 응모권이 한 장 한 행이고 등급이 지급 때 한 번 정해져 바뀌지 않으므로 반환이 같은 응모권을 되살리는 것으로 정리된다. 스펙에서 확정했다.
