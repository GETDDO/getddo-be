### 멘토링 자료: 잠금 방식 직접 측정과 README·Wiki

- 같은 서비스 코드에 잠금 방식만 바꿔 로컬 MySQL 8.4에서 비교했다(측정 코드는 임시, 저장소 미포함, 기준 dev `9bc9ea00`). 이벤트 행 `FOR SHARE` 102건/초 대 `FOR UPDATE` 23건/초, 만료 워커 4대 `SKIP LOCKED` 약 3.5초 대 일반 `FOR UPDATE` 약 20.9초(중복·누락 0), 차감 PK 단위는 격리 수준과 무관하고 범위 잠금은 `REPEATABLE_READ`에서만 약 37% 느림, 반환 이력 항상 잠금 읽기는 `REPEATABLE_READ`에서 60회 중 60회 교착(현재 방식 0회).
- 교착은 `SHOW ENGINE INNODB STATUS`로 원인을 확인했다: `ticket_histories`의 `uq_ticket_histories_refund_source`에서 두 트랜잭션이 아직 없는 구간을 읽기 잠금으로 잡은 뒤 각자 INSERT하려다 서로 막혔다.
- README(PR #109) 윤태형 담당 블록(출석·미션·응모권·이벤트 응모)과 요청 빈도 제한 블록에 큰 흐름과 핵심 선택·측정 한 줄을 채우고, 표·시퀀스·측정 상세는 Wiki 새 페이지 `Mentoring-Domain-Flows`로 옮겼다. 사이드바에 링크를 추가했다.

## 고민과 판단

- **폴백을 PR에 넣지 않은 이유**: 장애 시 한도를 어떻게 할지는 팀이 정할 정책인데 스펙에 항목이 없고, 구조를 혼자 정하는 것으로 판단했다. 원래 설계(스위치 + 장애 시 요청 통과)로 되돌리고 폴백은 합의 뒤 별도 PR로 제안하기로 했다.
- **스위치 유지**: Redis 주소만으로 자동 선택하면 이경주의 추가 작업은 없지만, #111 `application.yaml`의 호스트 기본값 `localhost`를 빼야 하고 선택이 암묵적이 된다. 명시적 설정을 유지했다.
- **인메모리 구현 유지**: 로컬 개발과 Redis 없이 실행하는 통합 테스트가 쓰고, Redis를 쓰지 않는 환경의 기본 동작이기 때문이다.
- **README는 큰 흐름만**: 표·시퀀스는 길어 README 가독성을 해치므로 Wiki로 옮기고 링크했다.
