# 요구사항

이 문서는 도메인별로 절을 나눠 작성합니다. 각 담당자는 자신의 절만 채우고, 다른 절은 해당 담당자가 채웁니다.

우선순위 기준: **P0 = 없으면 과제 미달**, **P1 = 완성도 핵심**, **P2 = 여유 시**.

---

## 응모권 · 일회성 미션 · 게임 (담당: 윤태형)

### 배경

응모권(ticket)은 사실상 돈에 준하는 자산이다. 다음 사고가 절대 발생해서는 안 된다.

| 사고 유형 | 구체적 상황 | 결과 |
|---|---|---|
| 중복 적립 | 출석 버튼 연타, 새로고침, 자정 경계 요청 | 응모권이 무상 복제됨 (자산 누수) |
| 중복 차감 / 누락 | 응모 버튼 동시 요청 | 응모권만 사라지고 응모는 안 됨 (고객 클레임) |

응모권은 **회원 단위 전역 단일 지갑**이다 — 여러 이벤트가 동시에 열려도 어느 이벤트의 미션으로 벌었든 어느 이벤트에나 쓸 수 있고, 이벤트가 끝나도 소멸하지 않는다(상세 근거는 `decisions/ticket-mission-game.md` ADR-24). 다만 **매달 초기화 시점에 그 시점 잔여 잔액은 소멸**한다(달력 단위의 별도 규칙, 이벤트 단위 규칙과 다른 층위).

### 기능 요구사항

**미션 (일회성)** `P0`
- 미션 목록 조회: 플랫폼 전체 미션(`event_id` NULL, 예: 계정 단위 행동 미션)은 홈에, 이벤트 소속 미션(퀴즈·설문·초대·기업연동)은 이벤트별로 그룹핑하여 조회. 미션명, 보상 응모권 수, 주기(`DAILY`/`ONCE`), 내 수행 여부 표시.
- 미션 수행 → 지급(원장 append + 잔액 갱신, 단일 트랜잭션). 어느 미션이든 동일한 전역 응모권 원장에 적립.
- 중복 지급 방지: 같은 `(user, mission, business_date)` 재요청은 `409 MISSION_ALREADY_COMPLETED`. 플랫폼 전체 미션은 전역으로 하루 1회만 인정.
- 운영자: 미션 등록/수정/활성화 토글, 지급 내역 조회.
- 기업 시스템 연동 미션(`EXTERNAL_VERIFY`) `P2`: 수행 버튼 클릭 시 서버가 Mock 기업 API를 동기 호출해 즉시 판정. 미달성이면 재시도 가능 안내.
- **미션 유형은 출석·게임을 제외한 5종**: `ACTION`(단순 행동, self-report) / `QUIZ`(정답 일치 시에만 지급) / `SURVEY`(제출 시 지급, 정오답 없음) / `REFERRAL`(친구 초대) / `EXTERNAL_VERIFY`(기업 시스템 연동). 전부 AI·사람 검수 없이 즉시 자동 판정한다 — 사진 인증·수동 승인 미션은 채택하지 않는다(최종 결정, 재검토 없음. 근거는 `decisions/ticket-mission-game.md`).
- ⚠️ **출석체크는 이 도메인 밖이다.** 출석 인정·중복 방지는 별도 팀원 담당(`AttendanceService`) — 이 도메인은 그 서비스가 호출하는 응모권 지급 함수만 제공한다.
- ⚠️ **이벤트 응모(Entry 제출)도 이 도메인 밖이다.** 무료·유료·추가 응모 처리는 별도 팀원 담당 — 이 도메인은 그 서비스가 호출하는 응모권 차감/환급 함수만 제공한다.

**게임** `P0`
- 홈 화면에서 모든 게임을 순환 없이 동시에 조회하고 횟수 제한 없이 플레이한다.
- 서버가 점수와 성공 여부를 판정해 개인 최고점·누적 점수를 갱신한다(성공 여부와 무관하게 항상 갱신).
- 그 플레이가 **성공**이고 오늘 게임 보상(전체 게임 통틀어 1장)을 아직 못 받았으면 즉시 지급한다. 실패한 플레이는 몇 번을 해도 지급하지 않는다. 성공해도 하루 1장 이상은 지급하지 않는다(차등 지급 없음).
- [추가 검토 필요] 제공할 게임 종류·규칙(후보: 타코야끼 만들기), 게임별 "성공" 판정 기준의 구체적 정의, 결과 유효성 검증(치팅 방지) 방식, 랭킹/주간 랭킹 보상 유지 여부.

**응모권 관리** `P0`
- 보유 응모권 실시간 조회 — 전역 단일 잔액. 홈 상단·이벤트 화면 어디서나 같은 숫자.
- 적립/사용 내역 조회(커서 페이지네이션, 사유/증감/잔액/시각/연관 이벤트 표시).
- 원장 정합성: append-only(DB 트리거로 UPDATE/DELETE 차단). `user_id` 단위로 `SUM(delta) == balance == 마지막 행의 balance_after`.
- 정합성 검증 API/화면: 전체 유저 대상 3중 대조 결과를 운영자 화면에서 확인(불일치 0건 시연).
- **응모권 월간 초기화**: 매달 초기화 시점에 잔여 응모권을 `MONTHLY_RESET` 사유로 소멸시키는 배치. 운영자 화면에서 실행 이력 확인 가능. [재확인 필요] 초기화 기준 시각·시간대(현재 KST 매월 1일 00:00으로 가정).
- 월말 무제한 이벤트 지원: 초기화 직전 응모권 소진 기회를 위해, 응모 시 투입 상한이 없는(`max_tickets_per_user = NULL`) 이벤트를 열 수 있다. [재확인 필요] 이 이벤트가 매달 자동 생성인지 운영자가 매번 등록하는지 — 현재는 수동 등록을 권장(YAGNI).
- **이벤트 취소 시 응모권 환급**: 이벤트가 취소되면 그 이벤트의 유효 응모 전체가 비동기 배치로 환급된다(같은 트랜잭션이 아님 — 대량 처리를 짧은 트랜잭션으로 유지하기 위함). 배치가 여러 번 실행돼도 중복 환급되지 않는다. 어뷰징으로 이미 제외 처리된 응모는 환급 대상이 아니다.
- [보류, 2026-09-17] 부정하게 적립된 응모권 자체를 무효화(회수)하는 정책 — 메커니즘(보정 원장)은 있으나 트리거 조건·판단 주체가 미정.

### 비기능 요구사항 (이 도메인 관련분)

| 항목 | 목표 |
|---|---|
| 정합성 | 동시 요청 100건 부하에서 원장 불일치 0건, 중복 적립/차감 0건 |
| 테스트 커버리지 | 전체 80% 이상, 원장 패키지(`core.ticket.*`) 90% 이상 |

### 인수 기준 (이 도메인 관련분)

- [ ] 출석/미션 중복 적립 방지가 DB 제약 수준에서 보장되고, 동시성 테스트(100 스레드)로 증명된다.
- [ ] `ticket_ledger`는 UPDATE/DELETE가 DB 레벨에서 거부된다(트리거 테스트 존재).
- [ ] 전체 유저 원장 정합성 검증 API가 불일치 0건을 반환한다.
- [ ] 응모권 잔액·원장 3중 대조가 `user_id` 단위(전역)로 불일치 0건을 반환한다.
- [ ] 이벤트 A에서 번 응모권으로 이벤트 B에 응모하면 성공하고, 이벤트 종료 후에도 잔여 응모권은 소멸하지 않는다.
- [ ] `tickets_per_entry=0`인 무료 응모는 응모권 잔액과 무관하게 성공하며, 응모 후 `ticket_ledger`에 행이 추가되지 않는다.
- [ ] 이벤트를 취소하면 그 이벤트의 유효 응모 전체가 환급되고, 제외된 응모는 환급되지 않으며, 환급 배치를 동시에 여러 번 실행해도 중복 환급되지 않는다(멱등).
- [ ] 월간 초기화 배치 실행 후 잔액이 0이 되고, 초기화 원장 행이 그 달 기준 정확히 1건 생성되며, 중복 실행에도 추가 소멸 없다.
- [ ] 게임에서 성공한 플레이가 있으면 하루 1장 지급되고, 실패만 반복하면 0장이며, 같은 날 여러 번 성공해도 1장을 넘지 않는다.
