# 게임 결과·일일 보상·내 통계 — GD-159 / GD-160 / GD-161

공용 경로·권한·공개 필드는 [색깔 게임 계약](https://github.com/Uplus-GETDDO/getddo-spec/blob/main/05-api/game-color-word-draft.md)과 [게임 API](https://github.com/Uplus-GETDDO/getddo-spec/blob/main/05-api/game.md)가 원본이다. 아래는 백엔드 구현과 검증 근거다. GD-155 목록·상세 PR과 독립적으로 기존 G03·GD-157·GD-170 기반을 사용한다.

## 처리 이유와 저장 순서

1. G04는 공통 사용자 문맥으로 확인한 활성 USER만 받는다. 부재·타인·게임 불일치·토큰 오류를 같은 공개 오류로 숨긴다. 토큰 원문은 저장·로그·응답에 다시 싣지 않는다.
2. HTTP 경계에서 필수 `answer`와 명시적 null, 소문자 색 enum, 정수 범위를 구분한다. JSON 표현 대신 각 답변의 순서·색·시간을 고정 길이로 해시해 키 순서·공백에 영향받지 않는다. 플레이 횟수를 제한하지 않고 결과 요청 본문과 기록 수만 제한한다.
3. `GamePlayResultService`는 트랜잭션 밖에서 소유권·토큰을 먼저 확인한다. `GamePlayResultRecorder`가 별도 Bean으로 READ COMMITTED 트랜잭션을 연다. `FOR UPDATE NOWAIT`의 MySQL 3572만 실제 처리 중으로 구분하고, 롤백이 끝난 뒤 202로 변환한다. DB 장애·지급 실패를 처리 중이나 INVALID로 숨기지 않는다.
4. 확정된 플레이는 입력 해시가 같으면 최초 완료·해당 플레이 청구의 지급 결과를 반환한다. 다르면 충돌이다. 최신 게임 규칙·현재 날짜·다른 플레이의 청구로 최초 결과를 다시 계산하지 않는다.
5. 신규 결과는 저장된 스냅샷으로 기존 `ColorWordValidator`가 판정한다. 무효 결과는 null 점수로 확정하고 통계·지급을 호출하지 않는다. 0점도 유효 결과다.
6. 유효 결과는 플레이 → 사용자·게임 통계 순서로 잠근다. 통계가 없으면 기존 테이블에 생성한다. 없는 범위를 미리 잠그지 않으며 UNIQUE 생성 경합·교착은 전체 롤백 후 새 트랜잭션에서 한 번만 재시도한다.
7. 통계 잠금을 확보한 뒤 공통 시계의 마이크로초 완료 시각을 구하고 그 시각의 KST 보상일을 고정한다. 유효 점수·횟수를 한 번 반영한다. 최소 점수를 넘은 한 판만 일일 청구 후보이며 낮은 점수를 누적해 보상하지 않는다.
8. 사용자·게임·보상일의 기존 청구가 없을 때만 적용 가능한 공용 GAME 정책을 읽고 게임 청구를 저장한다. 공통 Entity UUID v7·Auditing과 MapStruct를 사용하며 신규 테이블·기존 Flyway 변경은 없다. 정책 부재·손상은 지급 성공으로 보정하지 않는다.
9. 기존 `TicketGrantService.grant`가 같은 트랜잭션에서 청구를 검증하고 등급·장수·만료·이력을 확정한다. 게임이 응모권 테이블을 직접 변경하지 않는다. 실패하면 플레이 완료·통계·청구·응모권이 모두 롤백된다.
10. G05는 같은 읽기 스냅샷에서 본인 집계·현재 KST 날짜의 청구를 읽는다. 비활성 게임의 과거 통계는 보존하고, 조회로 통계 행·지급을 만들지 않는다. 누적 점수는 자정에도 유지하며 일일 지급 여부만 다음 KST 날짜로 바뀐다.

관련 단위·DTO·MySQL 통합 테스트 1차 실행에서 지급 서비스 스파이 설정이 MANDATORY 프록시를 호출해 실패했다. 테스트에서 실제 스파이 대상에 실패를 주입하도록 수정했고, 재실행은 성공했다. 이는 운영 트랜잭션 코드를 우회하거나 테스트를 비활성화한 변경이 아니다. G05 경계 테스트를 더한 전체 `test build`는 2026-10-15 실제 MySQL 환경에서 BUILD SUCCESSFUL(19분 49초)로 완료했다. JUnit XML 기준 2,059개가 통과했고 실패·오류·건너뜀은 모두 0개다(core 단위 788, api 단위 286, api 통합 178, DB 단위 50, DB 통합 757). 신규 결과 API 통합 7개가 포함된다. 변경하지 않은 작업의 up-to-date 결과도 포함하므로 모든 테스트를 강제 재실행했다고 표현하지 않는다.

## 배포·연동 후속

- 새 DB 구조는 추가하지 않는다. 운영 DB의 기존 게임·플레이 맥락·GAME 정책과 마이그레이션 적용 여부는 배포 담당과 확인해야 한다. 정책 행을 운영 DB에 임의 생성하지 않는다.
- G04와 G05의 신규 오류·한도·권한·재시도는 공용 spec의 사용자 선택을 먼저 공유한다. 실제 FE 연결·장시간 정상 플레이·운영 부하는 로컬 MySQL 성공과 구분한다.
- 공통 요청 제한 GD-146이 dev에 병합되어 G04 Controller에 기존 `@RateLimited(policy = "game-result")`를 연결했다. 사용자별 1분 10회이며 재시도도 요청 횟수에 포함한다. 초과 시 기존 `COMMON-006`·`Retry-After`를 사용하고 제한기·운영 수치는 변경하지 않았다. 실제 결과 통합 테스트에서도 제한을 켜 최초 결과/보상·11번째 거절·타인 분리·통계 조회·59초/60초 경계와 중복 지급 방지를 검증한다. 2026-10-15 이 연결을 포함한 실제 결과 API MySQL 통합8개가 성공했다(51초, 실패·오류·건너뜀0). 해당 변경의 전체 검증 결과는 PR과 당일 워크로그에서 별도 확인한다.
- GD-163의 지급 전 차단과 GD-164의 사후 점수 보정은 별도 담당 계약을 확인한다. 기존 무효 판정 외의 의심 임계값을 만들거나 응모권 회수를 추가하지 않는다.
- G04는 활성 USER만 완료·보상할 수 있다. G03의 ADMIN 시작 허용을 결과 자격으로 확대하지 않는다. 타꼬런·관리자 게임 등록은 별도 후속이다.

## FE 담당자 연결 안내

확인한 FE dev의 `src/features/playGame/api/queries.ts`는 아직 `{score}`를 전송하고, `model/types.ts`도 이전 결과 타입을 사용한다. 아래는 연결 순서이며 실제 FE 변경·시연 완료 기록이 아니다. 공개 필드·정확한 경로·색깔별 기록 형식은 위 공용 원본을 따른다.

1. GD-155 PR #100의 목록·상세에서 실제 DB 게임 UUID와 code를 얻는다. 임시 UUID를 고정하지 않는다.
2. 시작 때 G03을 호출하고 해당 플레이의 서버 규칙·게임 생성 정보·토큰을 보관한다. 토큰을 로그·주소·사용자 화면에 출력하지 않는다.
3. 게임 중 사용자의 선택·타임아웃·진행 시간을 채택된 `validationData.answers` 형식으로 기록한다. 화면에서 계산한 점수를 서버의 확정 점수로 제출하지 않는다.
4. 종료 때 G04에 같은 플레이·토큰·입력 기록을 보낸다. 네트워크 실패나 202 뒤의 재요청은 같은 기록을 유지한다. 결과 화면 재렌더로 입력을 추가하거나 새 플레이를 발급하지 않는다.
5. 200의 서버 판정 점수와 해당 플레이의 reward만 표시한다. VALID의 reward가 null인 경우는 정상이며, 프론트에서 별도 지급 요청을 만들지 않는다. 실패·충돌·무효 결과를 지급 성공으로 표시하지 않는다.
6. 완료 후 G05와 기존 응모권 조회를 새로 읽는다. 누적 통계와 오늘 지급 여부는 별개 값으로 표시한다.

실제 화면 검증에는 정상 0점·보상 미달·최소 점수 충족·이미 당일 지급·동일 결과 재시도·202·일자 변경을 포함한다. 타꼬런은 아직 별도 판정 계약이 필요하며 색깔 기록 형식을 그대로 적용하지 않는다. 2026-10-15 사용자 선택에 따라 이 작업에서는 BE PR·연동 안내서를 완성하고, 실제 FE 수정·연결은 FE 담당자가 진행한다.

## CodeRabbit 후속 확인 — 공통 시간 변환 재사용

G05의 다음 자정 계산은 별도 ZoneId 대신 기존 `TimeProvider.toUtc(date.plusDays(1).atStartOfDay())`를 재사용한다. 공통 클래스의 API·시간대는 변경하지 않았다. 수정 후 TimeProvider 단위 10개와 결과 API 실제 MySQL 통합 7개가 46초에 성공했다. 위 2,059개 전체 검증은 최초 구현 `b676a116` 기준이며, 후속 수정의 전체 재검증은 별도로 확인한다.
