# 이벤트 삭제 — GD-61

- 상태: 검토 대기 — 구현 및 알림 연동, 담당자 확인 전
- 공용 기준: [이벤트 규칙](https://github.com/GETDDO/getddo-spec/blob/main/02-domain/event.md), [AE05](https://github.com/GETDDO/getddo-spec/blob/main/05-api/event.md)

`DELETE /api/v1/admin/events/{eventId}`는 요청 본문 없이 호출하며, 성공 시 HTTP 200과 `ResponseEnvelope.success(null)`을 반환한다. UUID 변환·사용자 문맥은 기존 Spring 바인딩과 `@CurrentUser`를 사용하고, 삭제 조건은 `EventDeletionService`에서 검사한다.

## 처리 흐름

1. DB의 사용자 역할·활성 상태를 확인한다.
2. 기존 `findByIdForUpdate`로 미삭제 이벤트를 잠금 조회한다. 없는 이벤트와 삭제 재요청은 EVENT-007로 처리한다.
3. 잠금 획득 후 현재 시각을 확인한다. 시작 시각에 도달했거나 응모자 기록이 있으면 EVENT-013으로 거절한다.
4. 마이크로초 정밀도의 `deleted_at`을 기록하고 flush한다. 이벤트·경품 행을 물리 삭제하지 않는다.
5. 같은 트랜잭션에서 `EventChangeNotificationService.stopForDeletedEvent`를 호출해 남은 시작 알림 생성을 중지한다. 중지에 실패하면 이벤트 삭제도 롤백한다.
6. 같은 트랜잭션에서 공통 `AuditLogService.record`로 삭제 이력을 추가한다. 감사 기록 실패 시 이벤트 삭제·알림 중지·감사 이력을 모두 롤백한다.

응모자 기록은 최초 성공 응모에서 응모 행·차감과 같은 트랜잭션으로 생성된다. 이 기록이 있으면 삭제를 거절하며, 기록이 불완전하게 남은 경우에도 임의로 정리하거나 삭제를 허용하지 않는다. 이력 검사는 `FOR SHARE`로 최신 값을 읽어 관리자 조회에서 만들어진 이전 REPEATABLE READ 스냅샷의 영향을 받지 않는다. 이벤트의 쓰기 잠금은 응모의 이벤트 공유 잠금과 충돌하므로 삭제 조건 확인과 신규 응모 확정이 동시에 진행되지 않는다.

수정과 달리 삭제에는 SCHEDULED 상태 조건을 추가하지 않는다. 시작 전이고 응모 이력이 없다면 취소 이벤트도 삭제할 수 있다. 시작 시각과 같은 순간부터는 삭제를 거절한다.

| 오류 | HTTP | 의미 |
| --- | --- | --- |
| EVENT-005 | 401 | 등록된 사용자 정보 없음 |
| EVENT-006 | 403 | 활성 관리자 아님 |
| EVENT-007 | 404 | 없거나 이미 삭제된 이벤트 |
| EVENT-013 | 409 | 시작 시각 도달 또는 응모 이력 존재 |

기존 GD-59 조회와 GD-60 수정은 미삭제 이벤트만 대상으로 하므로 삭제 후 사용자·관리자 목록·상세와 수정 대상에서 제외된다. 기존 응모 경로도 `deleted_at`을 검사한다.

## 삭제 감사 기록

기존 `events.deleted_at`은 현재 삭제 상태이고, `audit_logs`의 신규 행은 해당 변경 이력이다. 이벤트의 `status`는 변경하지 않는다. 기존 공통 감사 기반을 사용하며 별도 테이블·컬럼은 추가하지 않는다.

| 값 | 삭제 기록 |
| --- | --- |
| actorId | 삭제 권한을 검증한 관리자 UUID |
| action / targetType / targetId | `EVENT_DELETE` / `EVENT` / 삭제한 이벤트 UUID |
| beforeData | `{"deletedAt":null}` |
| afterData | `{"deletedAt":"실제 저장한 마이크로초 정밀도의 UTC 시각"}` |
| reason / requestId | 현재 삭제 요청에 해당 입력이 없어 null |
| createdAt | 공통 Clock으로 생성한 감사 기록 시각 |

권한·시작 시각·응모 이력 등의 조건으로 삭제가 거절되면 감사 이력도 남기지 않는다. 삭제 재요청은 404이며 최초 삭제 시각과 이력 1개를 유지한다. 동시 삭제도 이벤트 잠금으로 한 번만 성공한다. [공통 감사 기록 계약](audit-recording.md)을 따른다.

## 연결 기능과 명세 차이

- 배너: [공용 배너 수동 삭제 정책](https://github.com/Uplus-GETDDO/getddo-spec/blob/main/03-decisions/021-manual-banner-deletion.md)에 따라 이벤트 삭제와 별개로 관리자가 수동 삭제한다. GD-61은 banners 컬럼·FK·배너 자동 삭제를 추가하지 않으며, 배너가 남아 있다는 이유로 이벤트 삭제를 제한하지 않는다.
- 알림: 2026-10-13 사용자 확인에 따라 이미 생성된 알림은 별도로 변경·삭제하지 않으며, 삭제 후 미생성 시작 알림이 생성되지 않도록 한다. 삭제를 취소로 취급하거나 별도 삭제 안내 알림을 등록하지 않는다. 기존 시작 작업의 `payload.generationStoppedBy`에 `event-deleted:<이벤트 UUID>`를 기록해 선점·사용자별 추가 생성·늦은 완료 및 실패 기록을 차단한다. 작업의 성공·실패 상태와 기존 알림의 문구·읽음·모의 발송 결과는 유지한다. 새로운 시작 작업 등록과 관리자 생성 복구는 기존 미삭제 이벤트 조건으로 차단된다.

## 검증

알림 생성 저장소도 연결 이벤트를 `FOR SHARE`로 잠근 뒤 알림 작업을 `FOR UPDATE`로 잠근다. 삭제의 이벤트 → 작업 순서와 일치시키며, 이벤트 연결이 없는 알림은 기존처럼 작업만 잠근다. 삭제가 먼저 확정되면 작업의 중지 근거를 확인해 추가 생성을 거절하고, 알림 생성이 먼저 확정되면 생성된 알림을 보존한 뒤 삭제한다. 기존 문구·발송 정책과 작업 차수 검증은 유지한다.

단위 테스트는 시작 시각 경계·잠금 대기·응모 이력·관리자 권한과 삭제 저장 후 알림 중지·감사 기록 호출을 검사한다. API 계약 테스트는 200·data null과 UUID 변환 실패를 확인한다. MySQL 통합 테스트는 논리 삭제·경품 보존·조회 제외·삭제 재요청·동시 삭제·과거 스냅샷 이후 확정된 응모 검사, 대기·처리 중 시작 작업의 중지와 기존 알림 보존, 삭제 감사 이력의 처리자·대상·UTC 시각·전후 JSON 및 기록 실패 시 전체 롤백을 확인한다. 별도의 두 스레드와 InnoDB의 실제 잠금 대기를 확인하는 테스트로 알림 생성 선행·삭제 선행 경합을 모두 검증한다. 실행 결과는 당일 공용 워크로그에 기록한다.
